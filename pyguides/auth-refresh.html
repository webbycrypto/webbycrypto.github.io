Refresh Token Rotation

Short-lived access tokens are secure but frustrating if users get logged out every hour. Refresh tokens solve this — they automatically issue new access tokens without re-entering a password, and rotate on every use so theft is detectable.

1

Why Access Tokens Expire

If an access token is stolen — from a log, a network intercept, a compromised device — the attacker can use it as long as it's valid. A token expiring in 1 hour limits the damage window to 1 hour. A token that never expires gives the attacker permanent access. Short expiry is a security property, not a bug.

The tradeoff: 15-minute expiry = very secure, but users get logged out constantly. 7-day expiry = convenient, but stolen tokens are dangerous for days. Refresh tokens let you have both: short access token (secure) + automatic renewal (convenient).
2

The Two-Token Pattern

Login issues two tokens. The access token is short-lived and used for API calls. The refresh token is long-lived and used only to get new access tokens — it never goes in an API call header.

text
LOGIN
  Client sends: email + password
  Server returns: access_token (60 min) + refresh_token (30 days)
  Client stores both.

EVERY API CALL
  Client sends: Authorization: Bearer <access_token>
  Server verifies, responds.

ACCESS TOKEN EXPIRES (60 min later)
  Client sends: POST /auth/refresh  with refresh_token
  Server: validates refresh_token, issues NEW access_token + NEW refresh_token
          (old refresh_token is now revoked — this is "rotation")
  Client stores the new pair.

REFRESH TOKEN EXPIRES OR USER LOGS OUT
  Client must log in again with email + password.
3

RefreshToken Table

Store refresh tokens in the database (not just as JWTs) so you can revoke them. Store the token hashed — if the tokens table is breached, raw tokens can't be used.

python
import secrets
from sqlalchemy import Column, Integer, String, Boolean, DateTime, ForeignKey
from datetime import datetime, timedelta, timezone

REFRESH_TOKEN_EXPIRE_DAYS = 30

class RefreshToken(Base):
    __tablename__ = "refresh_tokens"

    id         = Column(Integer, primary_key=True)
    token_hash = Column(String, unique=True, nullable=False, index=True)
    # Store the hash, not the raw token — same reason as passwords
    user_id    = Column(Integer, ForeignKey("users.id"), nullable=False)
    expires_at = Column(DateTime, nullable=False)
    revoked    = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

# Helper: generate a raw token and its hash
def make_refresh_token():
    raw   = secrets.token_urlsafe(64)  # 64 bytes → ~86 chars, cryptographically random
    hashed = pwd_context.hash(raw)       # same bcrypt context from auth.py
    expires = datetime.now(timezone.utc) + timedelta(days=REFRESH_TOKEN_EXPIRE_DAYS)
    return raw, hashed, expires           # return raw to send to client, store hashed

Login Issues Both Tokens

After verifying the password, create both tokens and store the refresh token in the database.

python
@app.post("/login")
def login(email: str, password: str, db: Session = Depends(get_db)):
    user = db.query(models.User).filter(models.User.email == email).first()
    if not user or not verify_password(password, user.hashed_password):
        raise HTTPException(status_code=401, detail="Invalid email or password")

    # Create short-lived access token
    access_token = create_access_token(data={"sub": str(user.id)})

    # Create long-lived refresh token and store in DB
    raw_refresh, hashed_refresh, expires = make_refresh_token()
    db.add(models.RefreshToken(
        token_hash=hashed_refresh,
        user_id=user.id,
        expires_at=expires,
    ))
    db.commit()

    return {
        "access_token":  access_token,
        "refresh_token": raw_refresh,   # send the raw token to client
        "token_type":    "bearer",
    }

POST /auth/refresh

The client calls this endpoint when the access token expires. It validates the refresh token, issues a new access token, and rotates the refresh token (issues a new one and revokes the old).

python
@app.post("/auth/refresh")
def refresh(refresh_token: str, db: Session = Depends(get_db)):
    # Find a matching, non-revoked, non-expired token in the DB
    # We can't query by hash directly (hash changes per call), so fetch recent ones
    now = datetime.now(timezone.utc)
    candidates = db.query(models.RefreshToken).filter(
        models.RefreshToken.revoked == False,
        models.RefreshToken.expires_at > now,
    ).all()

    # Find the one whose hash matches
    token_row = None
    for row in candidates:
        if pwd_context.verify(refresh_token, row.token_hash):
            token_row = row
            break

    if not token_row:
        raise HTTPException(status_code=401, detail="Invalid or expired refresh token")

    # Revoke old token (rotation)
    token_row.revoked = True

    # Issue new access token
    new_access = create_access_token(data={"sub": str(token_row.user_id)})

    # Issue new refresh token
    raw_new, hashed_new, expires_new = make_refresh_token()
    db.add(models.RefreshToken(
        token_hash=hashed_new,
        user_id=token_row.user_id,
        expires_at=expires_new,
    ))
    db.commit()

    return {
        "access_token":  new_access,
        "refresh_token": raw_new,
        "token_type":    "bearer",
    }

Rotation + Theft Detection

Rotation means each refresh token can only be used once. The moment it's used, it's revoked and a new one is issued. If a stolen token is used after the legitimate client already rotated it, the stolen token is already revoked — the attacker gets rejected.

python — detect revoked token reuse
# In /auth/refresh — check if someone is trying to use a revoked token
# This means either: (a) token was replayed, or (b) it was stolen

# Also search revoked tokens
all_candidates = db.query(models.RefreshToken).filter(
    models.RefreshToken.expires_at > now,  # not expired yet
).all()

for row in all_candidates:
    if pwd_context.verify(refresh_token, row.token_hash):
        if row.revoked:
            # Someone used an already-revoked token → possible theft
            # Revoke ALL tokens for this user (force re-login)
            db.query(models.RefreshToken).filter(
                models.RefreshToken.user_id == row.user_id,
                models.RefreshToken.revoked == False,
            ).update({"revoked": True})
            db.commit()
            raise HTTPException(
                status_code=401,
                detail="Token reuse detected. All sessions revoked. Please log in again."
            )
        token_row = row
        break

POST /auth/logout

Logout revokes the refresh token. Once revoked, the client can't get new access tokens — they'll need to log in again when the current access token expires.

python
@app.post("/auth/logout")
def logout(
    refresh_token:str,
    current_user: models.User = Depends(get_current_user),  # must be logged in
    db: Session = Depends(get_db),
):
    # Find and revoke the refresh token belonging to this user
    now = datetime.now(timezone.utc)
    candidates = db.query(models.RefreshToken).filter(
        models.RefreshToken.user_id == current_user.id,
        models.RefreshToken.revoked == False,
        models.RefreshToken.expires_at > now,
    ).all()
    for row in candidates:
        if pwd_context.verify(refresh_token, row.token_hash):
            row.revoked = True
            db.commit()
            break
    return {"message": "Logged out"}
    # Even if token not found, return 200 — logout should always succeed

Client Storage Tradeoff

Where the client stores tokens matters. Both options have tradeoffs — there is no universally correct answer.

text
localStorage / sessionStorage
  Easy to use from JavaScript.
  Vulnerable to XSS (cross-site scripting) attacks.
  If an attacker injects JS into your page, they can steal the token.
  Fine for: internal tools, low-risk apps, SPAs with strict CSP.

httpOnly Cookie
  Cannot be read by JavaScript — immune to XSS token theft.
  Sent automatically by the browser on every request.
  Vulnerable to CSRF (cross-site request forgery) if not protected.
  Add SameSite=Strict or a CSRF token to mitigate.
  Fine for: user-facing web apps where security is critical.

  FastAPI: set cookie in the response:
  response.set_cookie(
      key="refresh_token",
      value=raw_refresh,
      httponly=True,
      secure=True,       # HTTPS only
      samesite="strict",
      max_age=30*24*60*60
  )

Most SaaS apps use httpOnly cookies for refresh tokens
and localStorage for access tokens (since access tokens
expire quickly, the XSS window is small).
