Role-Based Access Control

Control who can do what. Add a role to the User model, build a reusable require_role() dependency, protect routes by role and by resource ownership — and learn how to combine both patterns.

1

What Is Role-Based Access Control?

Role-based access control (RBAC) assigns each user a role — like user or admin — and uses that role to decide what they can do. A regular user can read and edit their own data. An admin can read and edit everyone's data, access the admin panel, and perform destructive operations like deleting accounts.

Two access patterns: (1) Role — does this user's role permit this action? (2) Ownership — does this user own this resource? Most real apps combine both: a user can edit their own content (ownership), an admin can edit everything (role override).

role Column on User

Add a role enum column to the User model. Use a Python enum so the values are validated by SQLAlchemy and visible in code.

python
import enum
from sqlalchemy import Column, Integer, String, Boolean, DateTime, Enum

class UserRole(str, enum.Enum):
    user  = "user"
    admin = "admin"
    # Add more roles as needed: moderator = "moderator"

class User(Base):
    __tablename__ = "users"
    id              = Column(Integer, primary_key=True, index=True)
    email           = Column(String, unique=True, nullable=False, index=True)
    hashed_password = Column(String, nullable=False)
    is_active       = Column(Boolean, default=True)
    email_verified  = Column(Boolean, default=False)
    role            = Column(Enum(UserRole), default=UserRole.user)   # ← new
    created_at      = Column(DateTime, default=lambda: datetime.now(timezone.utc))

# To make the first admin: update directly in the DB or add a one-time script:
# db.query(User).filter(User.email == "you@example.com").first().role = UserRole.admin

require_role() Factory

A factory function returns a FastAPI dependency. This means you call require_role("admin") and it returns a function that FastAPI will call — which checks the current user's role. This pattern avoids duplicating the check in every route.

python
from fastapi import Depends, HTTPException, status
from models import User, UserRole

def require_role(*roles: str):
    """
    Returns a FastAPI dependency that checks the current user has one of the given roles.

    Usage:
        @app.delete("/users/{id}", dependencies=[Depends(require_role("admin"))])
        @app.post("/moderate", dependencies=[Depends(require_role("admin", "moderator"))])
    """
    def check_role(current_user: User = Depends(get_current_user)):
        if current_user.role not in roles:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"Required role: {' or '.join(roles)}",
            )
        return current_user   # return so routes can use the user if needed
    return check_role   # return the inner function — this is the dependency
Why a factory? If you just wrote def require_admin(user = Depends(get_current_user)) you'd have to write a separate function for each role combination. The factory pattern lets you call require_role("admin"), require_role("moderator"), or require_role("admin", "moderator") with the same function.
4

Admin-Only Route

Two ways to apply the dependency: in the route parameters (you get the user object) or in the dependencies=[] list (just enforces the check, doesn't inject the user).

python
from auth import require_role

# Inject the user — useful when you need current_user inside the route
@app.get("/admin/users")
def list_all_users(
    admin: models.User = Depends(require_role("admin")),
    db: Session = Depends(get_db),
):
    # Only admins reach here — non-admins get 403 before this runs
    users = db.query(models.User).all()
    return [{"id": u.id, "email": u.email, "role": u.role} for u in users]
python
# dependencies=[] — runs the check but doesn't inject the value
@app.delete("/admin/users/{user_id}", dependencies=[Depends(require_role("admin"))])
def delete_user(user_id: int, db: Session = Depends(get_db)):
    user = db.query(models.User).filter(models.User.id == user_id).first()
    if not user:
        raise HTTPException(status_code=404, detail="User not found")
    db.delete(user)
    db.commit()
    return {"deleted": user_id}

Resource Ownership

Roles control what type of action is allowed. Ownership controls which resources the user can act on. A user with role "user" should only be able to edit their own notes — not everyone else's.

python
@app.patch("/notes/{note_id}")
def update_note(
    note_id:      int,
    text:         str,
    current_user: models.User = Depends(get_current_user),
    db:           Session     = Depends(get_db),
):
    note = db.query(models.Note).filter(models.Note.id == note_id).first()
    if not note:
        raise HTTPException(status_code=404, detail="Note not found")

    # Ownership check: this note must belong to the current user
    if note.owner_id != current_user.id:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="You don't own this note"
        )

    note.text = text
    db.commit()
    return {"id": note.id, "text": note.text}

Ownership + Role Combined

Most real apps allow owners to edit their own resources AND admins to edit anything. Combine both checks with an or.

python
@app.delete("/notes/{note_id}")
def delete_note(
    note_id:      int,
    current_user: models.User = Depends(get_current_user),
    db:           Session     = Depends(get_db),
):
    note = db.query(models.Note).filter(models.Note.id == note_id).first()
    if not note:
        raise HTTPException(status_code=404, detail="Note not found")

    # Allow: owner OR admin
    is_owner = note.owner_id == current_user.id
    is_admin = current_user.role == models.UserRole.admin

    if not (is_owner or is_admin):
        raise HTTPException(status_code=403, detail="Not allowed")

    db.delete(note)
    db.commit()
    return {"deleted": note_id}

# Pattern: is_owner OR is_admin
# This appears in almost every real CRUD app with multi-user data

What's Next

You now have the complete auth stack: passwords, JWT tokens, refresh rotation, email verification, and role-based access. The natural next step is deployment — get your app running on a real server with HTTPS.

OAuth2 scopes: For API products (not user-facing apps), scopes are more granular than roles — e.g. read:contacts write:contacts. FastAPI has built-in OAuth2 scope support via SecurityScopes. Worth exploring once you're comfortable with the basics here.
Permissions table (fine-grained): For complex apps, roles become limiting. Add a permissions table and assign individual permissions (like can_export_data, can_invite_users) to users or roles. Same Depends pattern, different data model.
