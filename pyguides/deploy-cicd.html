GitHub Actions CI/CD

Automate your deploy. Push to GitHub → tests run → if green → code deploys to your server automatically. No more SSHing in and running scripts manually.

1

What CI/CD Is

CI (Continuous Integration) runs your tests automatically on every push. CD (Continuous Deployment) deploys your code automatically when tests pass. Together they mean: push to main → tests run → if green → live in production.

Why bother? Manual deploys are error-prone — you forget a step, push broken code, or deploy from the wrong branch. CI/CD makes deploys boring and reliable. Even on a solo project, it's worth the one-time setup.
2

The Deploy Flow

text
1. git push origin main
   → GitHub receives the push

2. GitHub Actions starts the workflow
   → Spins up a temporary Ubuntu runner (free for public repos)

3. (Optional) Run tests with pytest
   → If tests fail, stop here. Nothing deploys.

4. SSH into your server
   → Uses the deploy SSH key stored in GitHub Secrets

5. git pull origin main
   → Fetch the latest code on the server

6. source venv/bin/activate && pip install -r requirements.txt
   → Install any new dependencies

7. sudo systemctl restart myapp
   → Load the new code

8. Done. New version is live.

Generate a Deploy SSH Key

Create a new SSH key pair specifically for GitHub to use. Never reuse your personal SSH key — if the GitHub secret is ever leaked, you revoke just this key without affecting your own access.

bash
# Generate a new key pair specifically for CI/CD
ssh-keygen -t ed25519 -C "github-deploy" -f ~/.ssh/github_deploy
# No passphrase (GitHub Actions can't enter one interactively)

# View the PRIVATE key — paste this into GitHub Secrets
cat ~/.ssh/github_deploy
# -----BEGIN OPENSSH PRIVATE KEY-----
# b3BlbnNzaC1rZXktdjEA...
# -----END OPENSSH PRIVATE KEY-----

# View the PUBLIC key — add this to authorized_keys on the SERVER
cat ~/.ssh/github_deploy.pub
# ssh-ed25519 AAAAC3... github-deploy

# On the server: add the public key to authorized_keys
# (SSH into the server first)
echo "ssh-ed25519 AAAAC3... github-deploy" >> ~/.ssh/authorized_keys

GitHub Secrets

Secrets are encrypted variables that GitHub injects into your workflow. They're never visible in logs or to other users. You reference them as ${{ secrets.SECRET_NAME }} in the workflow file.

text — GitHub → Repo Settings → Secrets → Actions
Secret name: SSH_PRIVATE_KEY
Value: the full contents of ~/.ssh/github_deploy
       (the private key, including the -----BEGIN/END lines)

Secret name: SERVER_HOST
Value: your server's IP address or domain
       e.g. 203.0.113.42  or  yourdomain.com

Secret name: SERVER_USER
Value: the non-root username you created
       e.g. deploy

Secret name: SERVER_APP_PATH
Value: the path to your app on the server
       e.g. /home/deploy/apps/yourapp

Write the Workflow File

Create .github/workflows/deploy.yml in your project. GitHub Actions reads this file and runs it on every push to main.

yaml — .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]   # trigger on push to main only

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Deploy to server
        uses: appleboy/ssh-action@v1.0.3
        with:
          host:     ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key:      ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd ${{ secrets.SERVER_APP_PATH }}
            git pull origin main
            source venv/bin/activate
            pip install -r requirements.txt
            sudo systemctl restart myapp
            echo "Deploy complete"
yaml — with test step
name: Test + Deploy

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pip install pytest httpx
      - run: pytest tests/ -v
        env:
          DATABASE_URL: "sqlite:///./test.db"  # use SQLite for tests

  deploy:
    runs-on: ubuntu-latest
    needs: test          # only run if test job passes
    if: success()
    steps:
      - name: Deploy to server
        uses: appleboy/ssh-action@v1.0.3
        with:
          host:     ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key:      ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd ${{ secrets.SERVER_APP_PATH }}
            git pull origin main
            source venv/bin/activate
            pip install -r requirements.txt
            sudo systemctl restart myapp
appleboy/ssh-action: A GitHub Actions action that SSHs into your server and runs commands. It handles setting up the SSH key automatically. uses: appleboy/ssh-action@v1.0.3 pins a specific version so it doesn't break when updated.

Allow sudo systemctl restart in the Deploy Script

By default, the deploy user needs a password to run sudo. Since GitHub Actions can't enter a password, grant passwordless sudo for just the one command needed.

bash
# Edit the sudoers file safely
sudo visudo -f /etc/sudoers.d/deploy-restart

# Add this single line (replace "deploy" with your username):
# deploy ALL=(ALL) NOPASSWD: /bin/systemctl restart myapp

# This allows the deploy user to run ONLY this specific command
# without a password — no other sudo commands are allowed.
# More secure than granting full passwordless sudo.

Environment Variables in Actions

Your app's runtime secrets (DATABASE_URL, SECRET_KEY) live in /etc/myapp.env on the server — they don't go in GitHub Secrets. GitHub Secrets are only for things the CI process itself needs (SSH keys, server address). The deployed app reads its secrets from the server's env file as usual.

text
GitHub Secrets (for the CI/CD process itself):
  SSH_PRIVATE_KEY     → GitHub Actions uses this to SSH into the server
  SERVER_HOST         → IP or domain of the server
  SERVER_USER         → username on the server
  SERVER_APP_PATH     → path to the app folder

/etc/myapp.env (for the running app — on the server):
  SECRET_KEY          → FastAPI JWT signing key
  DATABASE_URL        → PostgreSQL connection string
  OPENAI_API_KEY      → AI API key
  RESEND_API_KEY      → Email API key

The difference:
  GitHub Secrets → used DURING the deploy (by Actions runners)
  /etc/myapp.env → used AFTER the deploy (by your FastAPI app)

What's Next

You now have a complete production pipeline: VPS → Nginx → HTTPS → systemd → auto-deploy. This is the foundation every professional FastAPI deployment is built on.

Docker: Package your app and all its dependencies into a container image. Docker ensures the same code runs identically on every machine — no "works on my laptop" problems. A natural next step once you're comfortable with the manual deployment approach.
Staging environment: Add a second server (or branch) for staging — push to staging branch → deploy to staging server → test → merge to main → deploy to production. Prevents untested code from hitting live users.
Notifications: Add a Slack or Discord notification step at the end of your workflow so your team (or just you) knows when a deploy succeeds or fails. appleboy/discord-action or rtCamp/action-slack-notify are simple options.
Database migrations in CI: Add an Alembic step to the deploy script: alembic upgrade head before systemctl restart myapp. This ensures schema changes are applied before the new code starts loading.
