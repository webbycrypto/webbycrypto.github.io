systemd Service + Production Env Vars

Keep uvicorn alive permanently. Write a systemd service file so the app auto-starts on boot, restarts on crash, and loads your secret environment variables from a protected file — never from a committed .env.

1

Why systemd?

When you ran uvicorn manually in the VPS guide, it died when you closed the SSH session. systemd is Linux's process supervisor — it starts processes on boot, restarts them if they crash, and logs their output. Think of it as a permanent background runner for your app.

What you get: (1) App starts automatically when the server reboots. (2) App restarts within seconds if it crashes. (3) Logs accessible via journalctl. (4) Environment variables injected securely from a file on disk with restricted permissions.
2

Write the Service File

A service file tells systemd what to run, as which user, in which directory, and what to do if it fails.

ini — systemd service file
[Unit]
Description=My FastAPI App
After=network.target    ; don't start until networking is up

[Service]
User=deploy             ; run as this user, not root
Group=deploy
WorkingDirectory=/home/deploy/apps/yourapp

; Load environment variables from a file (see Step 3)
EnvironmentFile=/etc/myapp.env

; Full path to the venv's uvicorn binary
ExecStart=/home/deploy/apps/yourapp/venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000

; Restart policy
Restart=always          ; restart if the process exits for any reason
RestartSec=5            ; wait 5 seconds before restarting

; Output logs to journald (readable with journalctl)
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target  ; start at normal boot
Create it: sudo nano /etc/systemd/system/myapp.service — paste, save, exit. Note: --host 127.0.0.1 keeps uvicorn bound to localhost only. Nginx handles external traffic.
3

Production Environment Variables

Your .env file is in your project directory and should never be committed to git. On the server, use a separate file in /etc/ with restricted permissions — only root can read it, but systemd runs as root so it can pass the variables to your app.

bash — create and secure the env file
# Create the env file
sudo nano /etc/myapp.env

# Contents (no quotes, no export, just KEY=VALUE):
# SECRET_KEY=your_production_secret_key_here
# DATABASE_URL=postgresql://user:pass@localhost/myapp
# OPENAI_API_KEY=sk-prod-...
# RESEND_API_KEY=re_...
# APP_BASE_URL=https://yourdomain.com

# Restrict permissions: only root can read/write
sudo chmod 600 /etc/myapp.env
sudo chown root:root /etc/myapp.env

# Verify permissions
ls -la /etc/myapp.env
# → -rw------- 1 root root ... /etc/myapp.env

# The deploy user cannot read this file directly
# But systemd (running as root) reads it and passes vars to your process
Never commit secrets to git. Add .env and *.env to your .gitignore. The production secrets live only in /etc/myapp.env on the server — not in your repo.
4

Enable + Start the Service

bash
# Tell systemd to reload service files (after creating/editing the .service file)
sudo systemctl daemon-reload

# Enable: start the service at boot
sudo systemctl enable myapp

# Start: start it now
sudo systemctl start myapp

# Check it started successfully
sudo systemctl status myapp
# → Active: active (running) ...

# Test: visit https://yourdomain.com — your app should be live

Check Status + View Logs

All app output (print statements, uvicorn logs, Python tracebacks) goes to journald. journalctl reads it.

bash
# Live logs (follow mode — like tail -f)
sudo journalctl -u myapp -f

# Last 100 lines
sudo journalctl -u myapp -n 100

# Logs since a specific time
sudo journalctl -u myapp --since "2024-06-01 10:00"

# Service status (shows recent logs too)
sudo systemctl status myapp

# Stop the service
sudo systemctl stop myapp

# Restart (useful after code changes)
sudo systemctl restart myapp

Restarting After a Deploy

When you pull new code, you need to restart the service so uvicorn loads the updated files. This is the manual deploy process — automated in the CI/CD guide.

bash — deploy.sh (run on the server)
#!/bin/bash
# deploy.sh — run this after SSH-ing to the server
set -e   # stop on first error

cd /home/deploy/apps/yourapp

# Pull latest code
git pull origin main

# Install any new dependencies
source venv/bin/activate
pip install -r requirements.txt

# Run database migrations (if using Alembic)
# alembic upgrade head

# Restart the app
sudo systemctl restart myapp

echo "Deploy complete. Checking status..."
sudo systemctl status myapp --no-pager

Multiple Workers

By default uvicorn uses one worker process. For better performance on a multi-core server, use --workers to spawn multiple worker processes.

ini — service file ExecStart
ExecStart=/home/deploy/apps/yourapp/venv/bin/uvicorn \
    main:app \
    --host 127.0.0.1 \
    --port 8000 \
    --workers 4
# Rule of thumb: 2 × CPU cores
# A 2-core server: --workers 4
# A 4-core server: --workers 8
# Note: SQLite doesn't work well with multiple workers — use PostgreSQL
bash — Gunicorn as process manager
# Gunicorn is a more mature process manager than uvicorn's built-in workers
# Use it when you need graceful zero-downtime restarts
pip install gunicorn

# In the service file ExecStart:
ExecStart=/home/deploy/apps/yourapp/venv/bin/gunicorn \
    main:app \
    -w 4 \
    -k uvicorn.workers.UvicornWorker \
    --bind 127.0.0.1:8000

# -w 4: 4 worker processes
# -k uvicorn.workers.UvicornWorker: use uvicorn's async worker
