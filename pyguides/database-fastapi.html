SQLite + PostgreSQL with FastAPI

Move beyond in-memory dicts and JSON files. Learn SQLAlchemy's ORM, define two related tables (Companies and Applications), and build a Job Application Tracker — a two-table status-flow app whose pattern repeats in CRMs, order systems, task boards, and almost every real project.

1

Why a Real Database?

The first two approaches in this series each have a scaling limit. An in-memory Python dict resets every time the server restarts — you lose all your data. A JSON file on disk persists, but breaks if two users write at the same time (a race condition). A real database solves both problems: it persists automatically, handles concurrent writes safely, lets you query millions of rows efficiently, and evolves its schema as your app changes.

StoragePersists on restartHandles concurrencyQueryableWhen to use
db = {}NoYes (single thread)Manual loopsQuick prototypes only
JSON fileYesNo (race conditions)Manual loopsSingle-user scripts
SQLiteYesYes (file lock)Full SQLDev, single-server apps
PostgreSQLYesYes (full ACID)Full SQLProduction, multiple workers
SQLite is a file. There is no server to install or start. The database is a single file on disk (jobs.db). It behaves like a full SQL database for everything you'll do in this guide. When you're ready for production, you swap one line in your .env and it works with PostgreSQL instead.

SQLAlchemy in 30 Seconds

SQLAlchemy is a Python library with two layers. The Core layer is a thin wrapper around SQL — you write SQL-ish expressions. The ORM layer lets you define tables as Python classes and write queries in Python. This guide uses the ORM, which is what most FastAPI apps use in practice.

text
1. ENGINE
   The connection to the database file/server.
   Created once at app startup from DATABASE_URL.
   SQLite:     sqlite:///./jobs.db
   PostgreSQL: postgresql://user:password@localhost/dbname

2. SESSION
   A short-lived connection you open per request.
   You make changes through a session.
   When you call db.commit(), changes are saved to disk.
   When the request ends, the session closes.

3. MODELS (your tables)
   Python classes that inherit from Base.
   Each class = one database table.
   Each attribute = one column.
   SQLAlchemy reads the classes and knows how to
   create the tables and translate queries.

Project Setup

Split the database code across three files so each has one job. This is the standard FastAPI + SQLAlchemy layout and is what you'll see in almost every real project.

text
job-tracker/
├── main.py        ← FastAPI app + all routes
├── database.py    ← engine, SessionLocal, get_db() dependency
├── models.py      ← Company and Application table definitions
├── .env           ← DATABASE_URL
└── jobs.db        ← created automatically by SQLAlchemy on first run

Optionally add:
└── schemas.py     ← Pydantic models for request/response validation
                     (not required for a learning project — we use
                      plain parameters in this guide)
Why separate files? If you put everything in main.py, circular imports break things quickly — main.py imports models, models import the Base from database, database imports from main... Keeping them separate avoids this entirely.
4

database.py — Connecting to the DB

Three things happen in this file: the engine is created (the connection to the DB), the session factory is defined (how to open a session per request), and get_db() is written — a FastAPI dependency that automatically opens a session at the start of a request and closes it when the request finishes, even if an error occurs.

python
# database.py
import os
from sqlalchemy import create_engine
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.orm import sessionmaker
from dotenv import load_dotenv
load_dotenv()

DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./jobs.db")
# The default is SQLite so the app works without any .env file at all

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False} if "sqlite" in DATABASE_URL else {},
    # check_same_thread=False is SQLite-only — it allows FastAPI's async
    # thread pool to reuse the same SQLite connection. Not needed for PostgreSQL.
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
# autocommit=False  → changes only save when you call db.commit() explicitly
# autoflush=False   → don't auto-send pending changes before every query

Base = declarative_base()
# Base is the parent class all your models will inherit from

def get_db():
    """FastAPI dependency: open a DB session, yield it, then close it."""
    db = SessionLocal()
    try:
        yield db       # FastAPI injects this into routes that ask for it
    finally:
        db.close()   # always closes, even if an exception was raised
.env — SQLite vs PostgreSQL
# SQLite — no server needed, just a file on disk (dev)
DATABASE_URL=sqlite:///./jobs.db

# PostgreSQL — local server (dev with Docker or local install)
# DATABASE_URL=postgresql://postgres:password@localhost:5432/jobs

# PostgreSQL — hosted (production, e.g. Supabase, Render, Railway)
# DATABASE_URL=postgresql://user:pass@db.xyz.supabase.co:5432/postgres

# The ORM code in models.py and all your routes stay EXACTLY the same.
# Only this one line changes between SQLite and PostgreSQL.
What is yield? A function that uses yield instead of return is a generator. FastAPI uses this pattern for dependencies — code before the yield runs before the route, the yielded value is injected into the route, and code after the yield (in the finally block) runs after the route finishes. It's guaranteed cleanup.

models.py — Two Tables

Each table is a Python class. Columns are class attributes using SQLAlchemy types. The ForeignKey links the two tables. The relationship() lets you navigate between them in Python — application.company returns the full Company object without writing a JOIN yourself.

python
# models.py
from sqlalchemy import Column, Integer, String, DateTime, ForeignKey, Enum
from sqlalchemy.orm import relationship
from datetime import datetime, timezone
import enum
from database import Base

# ── Status enum — defines the allowed values for Application.status ──
class AppStatus(str, enum.Enum):
    applied    = "applied"
    interview  = "interview"
    offer      = "offer"
    rejected   = "rejected"
    withdrawn  = "withdrawn"

# ── TABLE 1: Company ──────────────────────────────────────────────────
class Company(Base):
    __tablename__ = "companies"          # actual SQL table name

    id         = Column(Integer, primary_key=True, index=True)
    name       = Column(String, nullable=False, unique=True)
    website    = Column(String, nullable=True)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

    # Relationship: from a Company, get its list of Applications
    applications = relationship("Application", back_populates="company")

# ── TABLE 2: Application ─────────────────────────────────────────────
class Application(Base):
    __tablename__ = "applications"

    id           = Column(Integer, primary_key=True, index=True)
    company_id   = Column(Integer, ForeignKey("companies.id"), nullable=False)
    role         = Column(String, nullable=False)
    status       = Column(Enum(AppStatus), default=AppStatus.applied)
    applied_date = Column(DateTime, default=lambda: datetime.now(timezone.utc))
    notes        = Column(String, nullable=True)

    # Relationship: from an Application, get its Company object
    company = relationship("Company", back_populates="applications")
    # Usage: application.company.name  → no JOIN needed in code
text — column types
Column(Integer, primary_key=True, index=True)
  → Auto-incrementing integer ID. index=True speeds up lookups by ID.

Column(String, nullable=False)
  → Text field, required. nullable=True means the value can be NULL.

Column(String, unique=True)
  → Text field, must be unique across all rows (like an email or username).

Column(DateTime, default=lambda: datetime.now(timezone.utc))
  → Stores a date and time. The lambda means "call this function at insert
    time" — not at class definition time, which would freeze the timestamp.

Column(Enum(AppStatus), default=AppStatus.applied)
  → Only allows the values defined in the AppStatus enum.
    Stored as a string in the DB, validated by SQLAlchemy.

Column(Integer, ForeignKey("companies.id"), nullable=False)
  → Links this column to the "id" column in the "companies" table.
    If you try to insert a company_id that doesn't exist, the DB rejects it.
text — status flow
                ┌──────────┐
                │ applied  │  ← initial status on create
                └────┬─────┘
                     │
              ┌──────▼──────┐
              │  interview  │
              └──┬──────┬───┘
                 │      │
          ┌──────▼─┐  ┌─▼──────────┐
          │ offer  │  │  rejected  │
          └────────┘  └────────────┘

  Any status → withdrawn  (pulled out before decision)

This pattern is identical to:
  CRM deals:    lead → qualified → proposal → closed_won / closed_lost
  Orders:       pending → processing → shipped → delivered / cancelled
  Tasks:        todo → in_progress → review → done / blocked

Creating Tables

One line tells SQLAlchemy to look at all your models and create the corresponding tables in the database if they don't already exist. Put it in main.py so it runs on startup.

python
# main.py
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session
from database import engine, get_db, Base
import models   # importing models registers them with Base

app = FastAPI()

# Create all tables that don't yet exist
# This is safe to run every startup — it skips tables that already exist
Base.metadata.create_all(bind=engine)

# After running uvicorn for the first time, check your project folder —
# you'll see jobs.db has been created. That file IS the database.
Dev only — use Alembic in production. create_all() creates missing tables but never modifies existing ones. If you add a new column to a model in production, the table already exists and create_all() does nothing — the column won't appear. Use Alembic migrations for any schema change in production: alembic revision --autogenerate -m "add notes column" then alembic upgrade head.

Adding a Company

The write cycle has three steps: db.add() stages the new object, db.commit() saves it to disk, and db.refresh() reloads the object from the database to get the auto-generated id back. Without refresh(), the id field is still None.

python
@app.post("/companies")
def create_company(
    name:    str,
    website: str = None,
    db: Session = Depends(get_db),   # FastAPI injects the DB session here
):
    # Check for duplicate name before inserting
    existing = db.query(models.Company).filter(
        models.Company.name == name
    ).first()
    if existing:
        raise HTTPException(status_code=400, detail="Company already exists")

    company = models.Company(name=name, website=website)

    db.add(company)        # stage: "I want to save this object"
    db.commit()            # write: actually saves to the database file
    db.refresh(company)    # reload: fetches the auto-generated id from the DB

    return {"id": company.id, "name": company.name, "website": company.website}

# Test: POST http://localhost:8000/companies?name=Google&website=google.com
# Or via /docs page — FastAPI auto-generates a form for every route
text — write cycle
company = Company(name="Google")
  → Python object exists in memory only. DB knows nothing yet.
  → company.id is None

db.add(company)
  → SQLAlchemy marks this object as "pending".
  → Still nothing written to disk.

db.commit()
  → SQL: INSERT INTO companies (name, ...) VALUES ('Google', ...)
  → Row is written to the database.
  → The database assigns id = 1 (auto-increment).
  → But company.id in Python is STILL None — Python doesn't know yet.

db.refresh(company)
  → SQL: SELECT * FROM companies WHERE id = 1
  → SQLAlchemy re-reads the row and updates the Python object.
  → Now company.id = 1 ✓

This is why refresh() matters: whenever you need the DB-generated
id (or any server-side default) immediately after an insert.
Depends(get_db): This is FastAPI's dependency injection. Instead of creating a DB session inside the route function, you declare it as a parameter with Depends(get_db). FastAPI calls get_db() automatically, passes the session in, and runs the cleanup (finally: db.close()) after the route finishes.

Adding an Application

Before creating an Application, validate that the referenced Company exists. If someone passes a company_id that doesn't exist in the DB, raise a 404 instead of letting the database raise a foreign key error — a 404 is a much clearer message for the caller.

python
from models import AppStatus

@app.post("/applications")
def create_application(
    company_id: int,
    role:       str,
    notes:      str = None,
    db: Session = Depends(get_db),
):
    # Step 1: verify the company exists
    company = db.query(models.Company).filter(
        models.Company.id == company_id
    ).first()
    if not company:
        raise HTTPException(
            status_code=404,
            detail=f"Company with id {company_id} not found"
        )

    # Step 2: create the application
    application = models.Application(
        company_id=company_id,
        role=role,
        notes=notes,
        status=AppStatus.applied,   # always starts as "applied"
    )
    db.add(application)
    db.commit()
    db.refresh(application)

    return {
        "id":           application.id,
        "company":      company.name,
        "role":         application.role,
        "status":       application.status,
        "applied_date": application.applied_date,
    }

# Test: POST /applications?company_id=1&role=Backend+Engineer
Pattern to memorise: Any time a route creates a record that references another table (company_id, user_id, project_id), always do a db.query(...).first() check first and raise 404 if missing. This pattern is in every real project.

Reading with Filters

Filters are chained using .filter(). Multiple .filter() calls combine with AND. Optional filters — where the query param might not be provided — use a conditional to only apply the filter if the value was given.

python
from fastapi import Query
from typing import Optional

@app.get("/applications")
def list_applications(
    status:     Optional[AppStatus] = Query(None),  # filter by status
    company_id: Optional[int]       = Query(None),  # filter by company
    db: Session = Depends(get_db),
):
    query = db.query(models.Application)

    # Only apply each filter if the caller provided a value
    if status:
        query = query.filter(models.Application.status == status)
    if company_id:
        query = query.filter(models.Application.company_id == company_id)

    applications = query.order_by(
        models.Application.applied_date.desc()  # newest first
    ).all()

    return [
        {
            "id":           a.id,
            "company_id":   a.company_id,
            "role":         a.role,
            "status":       a.status,
            "applied_date": a.applied_date,
        }
        for a in applications
    ]

# All:           GET /applications
# By status:     GET /applications?status=interview
# By company:    GET /applications?company_id=1
# Both:          GET /applications?status=offer&company_id=2
python — common filter patterns
# Exact match
.filter(Application.status == "interview")

# Not equal
.filter(Application.status != "rejected")

# In a list
.filter(Application.status.in_(["interview", "offer"]))

# Text search (case-insensitive LIKE)
.filter(Application.role.ilike("%engineer%"))
# % means "any characters" — like * in a file glob
# ilike is case-insensitive; like is case-sensitive

# Date range
from datetime import datetime
.filter(Application.applied_date >= datetime(2024, 1, 1))

# Count instead of fetch
db.query(models.Application).filter(...).count()

# First match only
db.query(models.Application).filter(...).first()  # None if not found

Joining Tables

Getting the company name alongside each application can be done two ways. The relationship approach uses the application.company attribute — clean but triggers an extra query per row (N+1 problem). The join approach fetches both tables in one query — slightly more code but more efficient for large lists.

python — via relationship (lazy load)
@app.get("/applications/full")
def list_applications_with_company(db: Session = Depends(get_db)):
    applications = db.query(models.Application).all()

    return [
        {
            "id":      a.id,
            "role":    a.role,
            "status":  a.status,
            "company": a.company.name,   # SQLAlchemy auto-loads the Company row
        }
        for a in applications
    ]

# Simple to write. But: for each application, SQLAlchemy runs a
# separate SELECT to load the company — that's N+1 queries total.
# Fine for small lists (under 100 rows). Use the join for larger ones.
python — explicit ORM join
from sqlalchemy.orm import joinedload

@app.get("/applications/full")
def list_applications_with_company(db: Session = Depends(get_db)):
    applications = (
        db.query(models.Application)
        .options(joinedload(models.Application.company))  # one query with JOIN
        .all()
    )
    return [
        {
            "id":      a.id,
            "role":    a.role,
            "status":  a.status,
            "company": a.company.name,   # same syntax, but loaded in one query
        }
        for a in applications
    ]

# joinedload() tells SQLAlchemy: "fetch companies in the same SQL query
# using a JOIN — don't make a separate query per row".
# SQL generated: SELECT ... FROM applications JOIN companies ON ...
N+1 explained: With 50 applications and no join, SQLAlchemy runs 1 query to get all applications, then 50 more queries (one per row) to load each company — 51 total. With joinedload, it runs 1 query that joins both tables. Use the relationship approach while learning; switch to joinedload when performance matters.

Updating Status

Updates fetch the row first, change the field, and commit. The pattern is: find it, change it, save it. Never skip the fetch — you need the object in SQLAlchemy's session for changes to be tracked.

python
@app.patch("/applications/{application_id}/status")
def update_status(
    application_id: int,
    new_status:     AppStatus,     # FastAPI validates this is a valid enum value
    db: Session = Depends(get_db),
):
    # Step 1: fetch the row
    application = db.query(models.Application).filter(
        models.Application.id == application_id
    ).first()

    if not application:
        raise HTTPException(status_code=404, detail="Application not found")

    # Step 2: change the field
    old_status         = application.status
    application.status = new_status

    # Step 3: commit
    db.commit()
    db.refresh(application)

    return {
        "id":         application.id,
        "role":       application.role,
        "old_status": old_status,
        "new_status": application.status,
    }

# Test: PATCH /applications/1/status?new_status=interview
python — optional: enforce valid transitions
# For simple apps, any status → any status is fine.
# For stricter apps, validate the transition is allowed:

VALID_TRANSITIONS = {
    AppStatus.applied:   {AppStatus.interview, AppStatus.rejected, AppStatus.withdrawn},
    AppStatus.interview: {AppStatus.offer, AppStatus.rejected, AppStatus.withdrawn},
    AppStatus.offer:     {AppStatus.withdrawn},   # can still withdraw an offer
    AppStatus.rejected:  set(),                   # terminal — no further transitions
    AppStatus.withdrawn: set(),                   # terminal
}

# Inside the route, before committing:
if new_status not in VALID_TRANSITIONS[application.status]:
    raise HTTPException(
        status_code=400,
        detail=f"Cannot move from {application.status} to {new_status}"
    )

# This is the same pattern as ProofDrop's article status flow:
# verified → grace_period → verified / mismatch
# The status machine lives in a dict, not scattered across routes.

SQLite → PostgreSQL

The entire migration from SQLite to PostgreSQL is one line in your .env file. All your models, routes, queries, and filters work identically on both databases. This is the main value of using an ORM — you write against a standard interface, not against a specific database.

.env — before and after
# BEFORE (dev — SQLite file)
DATABASE_URL=sqlite:///./jobs.db

# AFTER (prod — PostgreSQL server)
DATABASE_URL=postgresql://myuser:mypassword@localhost:5432/jobs

# That's it. No code changes needed.

# One extra package for PostgreSQL:
# pip install psycopg2-binary
# (psycopg2 is the PostgreSQL driver SQLAlchemy uses)

# For async PostgreSQL (faster, works with async FastAPI routes):
# pip install asyncpg
# DATABASE_URL=postgresql+asyncpg://user:pass@localhost/jobs
bash — Alembic for schema changes
# Install
pip install alembic

# One-time setup inside your project folder
alembic init alembic

# Edit alembic/env.py — point it at your models:
# from database import Base
# target_metadata = Base.metadata

# When you change a model (add a column, rename a field):
alembic revision --autogenerate -m "add notes column to applications"
# Alembic reads your models, compares to the current DB schema,
# and generates a migration file with the ALTER TABLE SQL.

# Apply the migration
alembic upgrade head

# See migration history
alembic history

What's Next

You've built the foundation that every real FastAPI project stands on — a typed schema, two related tables, filtered queries, and a status flow. These same patterns run CRMs, order management systems, project trackers, and booking apps. The only things that change are the model names and the business rules.

Add an HTML frontend: Wire the CRUD routes to a Jinja2 template using the same patterns from the CRUD guide. Add a Kanban board view grouped by status: db.query(Application).filter(Application.status == s).all() for each column.
Search by role or company name: Add a search: str = Query(None) parameter and apply .filter(Application.role.ilike(f"%{search}%")). This is the same pattern as CRM contact search.
Connect to AI chat: Pass all "interview" status applications to the AI chat guide's call_ai() function and ask: "I have interviews at these companies for these roles. What questions should I prepare?" — same httpx.post() call, just different data.
Add a third table: Add a Note model with a FK to Application — one application can have many notes. This is the same Companies → Applications relationship, one level deeper. It introduces many-to-one relationships and is the core pattern of a real CRM (contacts → activities, orders → line items).
Deploy with the database: Push to Render or Railway, add a PostgreSQL database as a plugin, set DATABASE_URL as an environment variable, and run alembic upgrade head as a deploy step. The app works exactly the same — one connection string change.
