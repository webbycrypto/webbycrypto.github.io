Docker for FastAPI Developers

Package your app into a container so it runs identically on every machine. Covers Dockerfile, .dockerignore, environment variables, docker compose for multi-service apps, and a production deployment workflow.

1

What is Docker?

Your app works on your laptop but breaks on the server because the server has a different Python version, different packages, or a different operating system. Docker fixes this by packaging your app and everything it needs into a single image that runs identically on any machine. An image is the packaged file, a container is a running copy of that image, and a Dockerfile is the recipe used to build the image.

bash
# On your laptop — works fine
$ python --version
Python 3.11.4
$ pip show fastapi | grep Version
Version: 0.111.0
$ uvicorn main:app --reload
INFO: Application startup complete.

# On the server — different Python, different packages, things break
$ python --version
Python 3.9.2
$ uvicorn main:app
ERROR: cannot import name 'Annotated' from 'typing'
  (this was added in Python 3.9 but the syntax you used needs 3.10+)

# With Docker — same result on every machine
# Build once on your laptop
docker build -t myapp .

# Run anywhere — same Python, same packages, same result
docker run -p 8000:8000 myapp
INFO: Application startup complete.
text
image          the packaged app -- built once, run anywhere.
               Stored as a file on your machine or in a registry.

container      a running copy of an image -- like a lightweight VM.
               You can run many containers from the same image.

Dockerfile     the recipe that tells Docker how to build the image.
               A plain text file with one instruction per line.

docker compose a tool for running multiple containers together.
               Defined in a docker-compose.yml file.

registry       a place to store and share images.
               Docker Hub is the default. GitHub Container Registry
               (ghcr.io) is popular for open source projects.

layer          each instruction in a Dockerfile creates a layer.
               Docker caches layers -- if nothing changed in a layer,
               it reuses the cached version. This makes rebuilds fast.

Install Docker

Docker Desktop is the easiest way to get started on Windows and Mac. It includes the Docker engine, the CLI, and a GUI to manage containers. On Linux you install the Docker engine directly. After installing, run the two verification commands to confirm it is working.

bash
# Windows and Mac -- download Docker Desktop from:
# https://www.docker.com/products/docker-desktop
# Run the installer, then start Docker Desktop from the Start menu / Applications.

# Linux (Ubuntu/Debian)
sudo apt update
sudo apt install docker.io docker-compose-plugin
sudo systemctl start docker
sudo systemctl enable docker          # start Docker automatically on boot
sudo usermod -aG docker $USER         # run docker without sudo (re-login after)

# Verify the install
docker --version                      # should print: Docker version 24.x.x
docker run hello-world                # pulls a test image and runs it

$ docker run hello-world

The Dockerfile

A Dockerfile is a plain text file that tells Docker how to build your app image. Each line is an instruction. Docker runs them in order and caches each step so rebuilds are fast. The file always lives in the root of your project folder next to main.py.

text
# Start from the official Python image -- slim removes extras to keep the image small
FROM python:3.11-slim

# Set the working directory inside the container -- all following commands run here
WORKDIR /app

# Copy requirements first so Docker can cache the pip install step
# If your code changes but requirements.txt doesn't, Docker reuses this layer
COPY requirements.txt .

# Install dependencies -- no-cache-dir keeps the image smaller
RUN pip install --no-cache-dir -r requirements.txt

# Copy the rest of your project files into the container
COPY . .

# Tell Docker this container will listen on port 8000
EXPOSE 8000

# The command that runs when the container starts
# 0.0.0.0 is required -- without it the app only listens inside the container
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
text
# requirements.txt -- pin versions so your image is reproducible
fastapi==0.111.0
uvicorn==0.29.0
python-dotenv==1.0.1
sqlalchemy==2.0.30
psycopg2-binary==2.9.9

# Generate this file from your current environment:
# pip freeze > requirements.txt
#
# Or pin only your direct dependencies and let pip resolve the rest.
# Pinning every transitive dependency makes the build slower but fully reproducible.

.dockerignore

Docker copies your project files into the image. Without a .dockerignore file it copies everything, including your virtual environment, secrets file, and git history. This makes the image much larger and can accidentally expose your .env file. The .dockerignore file works exactly like .gitignore — list what to exclude.

text
# Virtual environment -- Docker installs its own from requirements.txt
venv/
.venv/
env/

# Secrets -- never bake these into an image
.env
*.env

# Python bytecode -- not needed inside the container
__pycache__/
*.pyc
*.pyo

# Git history -- not needed inside the container
.git/
.gitignore

# Editor files
.vscode/
.idea/

# Local database files
*.db
*.sqlite3

# Test output
.pytest_cache/
htmlcov/
bash
# Without .dockerignore -- Docker copies venv (hundreds of MB) into the image
$ docker build -t myapp .
$ docker image ls myapp
REPOSITORY   TAG       IMAGE ID       SIZE
myapp        latest    a1b2c3d4e5f6   1.23GB   <-- ballooned by venv + .git

# After adding .dockerignore -- only your code and pip-installed deps
$ docker build -t myapp .
$ docker image ls myapp
REPOSITORY   TAG       IMAGE ID       SIZE
myapp        latest    b2c3d4e5f6a1   187MB    <-- much smaller

# Why each exclusion matters:
# venv/         Docker runs pip install inside the container -- its own venv
# .env          If pushed to a registry, anyone can read your SECRET_KEY
# __pycache__   Bytecode is OS-specific -- Linux container needs its own
# .git/         Can be hundreds of MB; not needed at runtime
# *.db          Local SQLite file -- the container uses its own database

Build and Run

Building creates the image from your Dockerfile. Running starts a container from that image. The -p flag maps a port on your machine to a port inside the container — without it the app is only reachable from inside Docker, not your browser.

bash
# Build the image -- tag it with a name so you can reference it later
# The dot at the end means "use the Dockerfile in the current folder"
docker build -t myapp .

# Run the container
# -p 8000:8000  --  map port 8000 on your machine to port 8000 in the container
# --rm          --  delete the container automatically when it stops
docker run -p 8000:8000 --rm myapp

# Run in detached mode (background) -- you get your terminal back
docker run -d -p 8000:8000 --name myapp-container myapp
bash
docker ps                          # list running containers
docker ps -a                       # list all containers including stopped ones
docker logs myapp-container        # see the container's stdout output
docker logs -f myapp-container     # follow logs in real time (like tail -f)
docker stop myapp-container        # stop a running container gracefully
docker rm myapp-container          # delete a stopped container
docker images                      # list all images on your machine
docker rmi myapp                   # delete an image
docker exec -it myapp-container sh # open a shell inside a running container

Environment Variables

Never put secrets inside a Docker image. If you build the .env file into the image and push it to Docker Hub, your secrets become public. Instead, pass environment variables at run time using --env-file or -e flags. Inside your Python code, os.getenv() works exactly the same as before.

bash
# Pass a single variable at run time
docker run -p 8000:8000 -e SECRET_KEY=abc123 myapp

# Pass all variables from a .env file -- the file stays on your machine
# It is never copied into the image
docker run -p 8000:8000 --env-file .env myapp

# In docker compose (preferred) -- see step 7
# env_file:
#   - .env
python
import os
from dotenv import load_dotenv

load_dotenv()  # loads .env when running locally -- ignored if vars are set by Docker

# os.getenv works the same whether the value came from .env or Docker -e
SECRET_KEY   = os.getenv("SECRET_KEY")
DATABASE_URL = os.getenv("DATABASE_URL")

# Fail fast at startup if a required variable is missing
if not SECRET_KEY:
    raise RuntimeError("SECRET_KEY is not set")

docker compose

Most apps need more than one service — a FastAPI app and a PostgreSQL database, for example. Running them with separate docker run commands gets complicated fast. Docker Compose lets you define all your services in a single YAML file and start everything with one command.

yaml
# docker-compose.yml -- define all services in one place

services:

  app:
    build: .                        # build the image from the Dockerfile in this folder
    ports:
      - "8000:8000"                 # host:container port mapping
    env_file:
      - .env                        # load environment variables from .env
    depends_on:
      - db                          # wait for the db service to start first
    volumes:
      - .:/app                      # mount current folder so code changes reflect immediately

  db:
    image: postgres:16-alpine       # use the official Postgres image -- no Dockerfile needed
    environment:
      POSTGRES_USER: myuser
      POSTGRES_PASSWORD: mypassword
      POSTGRES_DB: mydb
    volumes:
      - pgdata:/var/lib/postgresql/data  # persist database files between restarts

volumes:
  pgdata:                           # named volume -- Docker manages where it lives on disk
bash
docker compose up          # start all services -- shows logs in the terminal
docker compose up -d       # start in detached mode (background)
docker compose down        # stop and remove all containers
docker compose down -v     # also delete the named volumes (wipes the database)
docker compose logs -f     # follow logs from all services
docker compose logs app    # logs from the app service only
docker compose build       # rebuild images without starting containers
docker compose restart app # restart one service without stopping others

Production Deploy

On a production server you pull a pre-built image from a registry instead of building it there. Docker Hub is the default public registry. GitHub Container Registry is a good choice if your code is on GitHub. The workflow is: build the image locally or in CI, push it to the registry, then pull and run it on your server.

bash
# Log in to Docker Hub
docker login

# Tag the image with your Docker Hub username and a version
# format: username/image-name:tag
docker tag myapp yourusername/myapp:v1.0

# Push to Docker Hub -- image is now publicly accessible
docker push yourusername/myapp:v1.0

# On your server -- pull and run the image
docker pull yourusername/myapp:v1.0
docker run -d -p 8000:8000 --env-file .env --name myapp yourusername/myapp:v1.0
yaml
# .github/workflows/docker.yml
# Builds and pushes the image to Docker Hub on every push to main

name: Build and Push Docker Image

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/myapp:latest

# Add DOCKERHUB_USERNAME and DOCKERHUB_TOKEN in:
# GitHub repo > Settings > Secrets and variables > Actions
# Generate DOCKERHUB_TOKEN at hub.docker.com > Account Settings > Security

What's Next

You now have a containerised FastAPI app that builds, runs, and deploys consistently. From here, add a database container with docker compose, wire up your CI/CD pipeline, or look into Kubernetes for managing containers across multiple servers.

Multi-stage builds: Split your Dockerfile into a build stage and a run stage. The final image only contains what is needed to run, not the build tools. This can cut image size by 60% or more.
Docker + Celery: Add a worker service to your docker-compose.yml pointing at the same image but running celery -A tasks worker as the command. Redis runs as a third service. See the Background Tasks guide.
GitHub Container Registry: Use ghcr.io/username/myapp:latest instead of Docker Hub. Authentication uses your existing GitHub token — no separate Docker Hub account needed.
Kubernetes: Once you have multiple containers to manage across multiple servers, Kubernetes (k8s) is the standard tool. It handles load balancing, health checks, rolling deploys, and automatic restarts. Start with the deploy series guides first.
