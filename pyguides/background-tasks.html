Background Tasks with FastAPI

Run slow work after sending the response — from FastAPI's built-in BackgroundTasks for simple jobs to Celery + Redis for production job queues with retries, scheduling, and monitoring.

1

Why Background Tasks?

Every HTTP request has a deadline. The browser or client that made the request is waiting, and if your route takes too long — sending an email, resizing an image, calling a slow API, generating a PDF — the user stares at a spinner. Worse, most servers will time out the connection after 30–60 seconds regardless. Background tasks solve this by splitting the response from the work: you immediately tell the client "got it, done" and then do the slow part after the response is already sent. The user's browser is happy, the connection is free, and your slow code runs without any time pressure. This is one of the most common patterns in real production backends — almost every app that sends email, processes uploads, or talks to third-party services uses it.

The rule of thumb: if a task takes more than about 200ms and the user doesn't need the result immediately, it belongs in a background task. Sending a welcome email after signup is the classic example — the user just needs to know their account was created, not that the email was delivered.
2

FastAPI's Built-in BackgroundTasks

FastAPI ships with a simple BackgroundTasks system that requires zero extra packages. You add BackgroundTasks as a parameter to your route function — FastAPI injects it automatically, the same way it injects Depends() dependencies. You call add_task() to register a function to run after the response, then return your response normally. FastAPI sends the response to the client first, then runs your registered task in the same process. This is perfect for fast-finishing background work like sending one email, writing a log entry, or updating a cache. The key limitation is that the task runs in the same process and thread as your server — if it crashes, raises an error, or takes several minutes, it can affect other requests.

python
from fastapi import FastAPI, BackgroundTasks
import time

app = FastAPI()


def send_welcome_email(email: str):
    """This function runs AFTER the response is sent."""
    time.sleep(2)  # simulate slow email API call
    print(f"Welcome email sent to {email}")


@app.post("/signup")
def signup(
    email: str,
    background_tasks: BackgroundTasks  # FastAPI injects this automatically
):
    # Register the task — it does NOT run yet
    # First argument is the function, rest are its arguments
    background_tasks.add_task(send_welcome_email, email)

    # This response goes to the client immediately
    # The email task runs after this line, while the client is already done
    return {"message": "Account created. Check your email."}
bash
# Sign up — the response comes back instantly
# The 2-second sleep happens after, in the background
curl -X POST "http://localhost:8000/signup?email=alice@example.com"

# Expected response (immediate):
# { "message": "Account created. Check your email." }

# Check your terminal — 2 seconds later you'll see:
# Welcome email sent to alice@example.com

Multiple Tasks and Passing Dependencies

You can add as many background tasks as you like to one request — they run in the order you added them, one after another. You can also pass any extra arguments the function needs, including database sessions or config values. One important pattern: if your task needs a database session, do not pass the request's db session into it. FastAPI closes the session when the request ends, which happens before the background task runs — you would get an error trying to use a closed session. Instead, create a fresh session inside the task function itself. This catches many beginners off guard.

python
def send_welcome_email(email: str):
    print(f"Email sent to {email}")

def log_signup(email: str, plan: str):
    print(f"Logged: {email} signed up for {plan}")

def create_stripe_customer(email: str):
    print(f"Stripe customer created for {email}")


@app.post("/signup")
def signup(email: str, plan: str, background_tasks: BackgroundTasks):
    # Add three tasks — they run in this order after the response
    background_tasks.add_task(send_welcome_email, email)
    background_tasks.add_task(log_signup, email, plan)          # extra args passed here
    background_tasks.add_task(create_stripe_customer, email)

    return {"message": "Done"}
python
from sqlalchemy.orm import Session
from database import SessionLocal  # your SQLAlchemy session factory


# WRONG — do not pass the route's db session into a background task
def bad_task(user_id: int, db: Session):
    # db is already closed by the time this runs — will raise an error
    db.query(User).filter(User.id == user_id).first()


# RIGHT — create a fresh session inside the task
def good_task(user_id: int):
    db = SessionLocal()   # open a new session just for this task
    try:
        user = db.query(User).filter(User.id == user_id).first()
        user.welcome_sent = True
        db.commit()
    finally:
        db.close()        # always close — use try/finally so it closes even on error


@app.post("/signup")
def signup(user_id: int, background_tasks: BackgroundTasks):
    background_tasks.add_task(good_task, user_id)  # pass the ID, not the session
    return {"message": "Done"}

When Built-in BackgroundTasks Isn't Enough

FastAPI's built-in BackgroundTasks is great for quick fire-and-forget work, but it has real limits. It runs inside the same server process — if your task crashes the worker, it can bring down live traffic. There is no retry: if an email fails to send because the email provider was temporarily down, the task just disappears. There is no scheduling — you cannot say "run this in 10 minutes." There is no queue — if your server restarts mid-task, the work is lost. And there is no visibility — you have no way to check whether a task succeeded or failed after the fact. When any of these matter, you need a proper task queue. Celery is the standard Python answer: it runs tasks in a completely separate worker process, stores them in Redis or RabbitMQ, retries on failure, and gives you a monitoring dashboard.

Use FastAPI BackgroundTasks when: the task is fast (under a few seconds), failure is acceptable (no retry needed), you don't need to track the result, and you don't need scheduling.
Use Celery when: tasks are slow or unpredictable, you need retries on failure, you need to check task status from a frontend, you need scheduled jobs (cron-style), or your server restarts and tasks must survive.

Install Celery + Redis

Celery is the task queue library — it manages the queue of jobs, dispatches them to workers, handles retries, and stores results. Redis is the broker: it's the message bus that sits between your FastAPI app and the Celery worker. When your route calls a task, it sends a message to Redis. The Celery worker is a completely separate process — it polls Redis, picks up messages, and runs the task functions. Redis also stores task results so your app can check whether a task finished and what it returned. You need Redis running before Celery starts. On Windows, the easiest way is to run Redis in Docker. On Linux and macOS you can install it directly.

bash
# Install Celery with Redis support
pip install celery redis

# Install Flower — the Celery monitoring web UI (optional but recommended)
pip install flower
bash
# Windows — easiest: run Redis in Docker

# macOS (with Homebrew)
brew install redis
brew services start redis

# Linux (Ubuntu/Debian)
sudo apt install redis-server
sudo systemctl start redis

# Test that Redis is running

Celery App Setup

The Celery app object is the central configuration — it tells Celery where Redis is (the broker), where to store results (the backend), and various behavioural settings. You define it once in a dedicated file, usually called tasks.py or celery_app.py, and import it everywhere else. The broker_url tells Celery where to send task messages. The result_backend tells Celery where to store the return value of each task so you can retrieve it later. Setting result_expires means Redis cleans up old results automatically — without this, completed task results pile up in Redis forever. task_track_started means Celery records when a task starts, not just when it finishes, which is useful for progress tracking.

python
from celery import Celery
import os
from dotenv import load_dotenv

load_dotenv()

REDIS_URL = os.getenv("REDIS_URL", "redis://localhost:6379/0")
# redis://localhost:6379/0  →  host:port/database-number
# Redis has 16 databases (0–15) — /0 is the default

# Create the Celery app — first arg is the module name, used in logs
celery_app = Celery("myapp")

celery_app.conf.update(
    broker_url          = REDIS_URL,  # where tasks are sent
    result_backend      = REDIS_URL,  # where results are stored
    task_track_started  = True,       # record when a task starts running
    result_expires      = 3600,       # delete results from Redis after 1 hour
    task_serializer     = "json",     # encode tasks as JSON (not pickle — safer)
    result_serializer   = "json",
    accept_content      = ["json"],
)
bash
# .env
REDIS_URL=redis://localhost:6379/0

Defining Tasks

A Celery task is just a Python function decorated with @celery_app.task. That decorator registers the function with Celery so it can be serialised and sent through Redis to a worker. Inside the task, you write normal Python code — database calls, HTTP requests, file operations — with no concern about blocking the server. The bind=True option gives the task a self parameter, which is a reference to the task instance. You need self to call self.retry() on failure, or self.update_state() to report progress. Retries use exponential backoff by default when you use countdown — the task waits before trying again, which is sensible for transient failures like a briefly unavailable email server.

python
# tasks.py — add task definitions below the celery_app setup

import time

# @celery_app.task registers this function as a Celery task
@celery_app.task
def send_email(to: str, subject: str, body: str):
    # This runs in the Celery worker process, not in FastAPI
    time.sleep(2)  # simulate calling an email API
    print(f"Email sent to {to}: {subject}")
    return {"status": "sent", "to": to}
    # The return value is stored in Redis — retrievable by task ID


@celery_app.task
def resize_image(file_path: str, width: int, height: int):
    from PIL import Image
    img = Image.open(file_path)
    img = img.resize((width, height))
    img.save(file_path)
    return {"resized": file_path}
python
# bind=True gives the task a "self" reference so it can call self.retry()
@celery_app.task(bind=True, max_retries=3)
def send_email_with_retry(self, to: str, subject: str):
    try:
        # Attempt the email send
        result = call_email_api(to, subject)
        return result
    except Exception as exc:
        # On failure, wait 60s and try again (up to max_retries times)
        # countdown = seconds to wait before the retry
        raise self.retry(exc=exc, countdown=60)
        # After max_retries, the exception propagates and the task is marked FAILED
python
@celery_app.task(bind=True)
def process_large_file(self, file_path: str):
    rows = load_csv(file_path)
    total = len(rows)

    for i, row in enumerate(rows):
        process_row(row)

        # Update the task's state so the frontend can show a progress bar
        # self.update_state() writes to Redis — readable via AsyncResult
        self.update_state(
            state="PROGRESS",
            meta={"current": i + 1, "total": total}
        )

    return {"processed": total}

Calling Tasks from FastAPI Routes

To dispatch a Celery task from a FastAPI route, you call task_function.delay() instead of task_function() directly. The .delay() method serialises the arguments to JSON, sends them to Redis, and returns an AsyncResult object immediately — the task has not run yet, it is sitting in the queue waiting for a worker to pick it up. The AsyncResult object has an id attribute — this is a unique string identifier for that specific task run. You should return this ID to the client so they can poll for the result later. The .apply_async() method is the more powerful version of .delay() — it lets you add options like countdown (delay before running), eta (run at a specific time), and queue (which worker queue to use).

python
from fastapi import FastAPI
from tasks import send_email, process_large_file  # import from tasks.py

app = FastAPI()


@app.post("/signup")
def signup(email: str):
    # .delay() sends the task to Redis and returns immediately
    # The worker picks it up and runs it in the background
    task = send_email.delay(
        to=email,
        subject="Welcome!",
        body="Thanks for signing up."
    )

    # task.id is a UUID string — return it so the client can track progress
    return {
        "message": "Account created",
        "task_id": task.id   # e.g. "3f2e1a0b-..."
    }


@app.post("/upload")
def upload(file_path: str):
    # apply_async() is like .delay() but with extra options
    task = process_large_file.apply_async(
        args=[file_path],
        countdown=5  # wait 5 seconds before starting (useful for letting a file finish writing)
    )
    return {"task_id": task.id}
python
# .delay() — shorthand, positional or keyword args
send_email.delay("alice@example.com", "Hi", "body")
send_email.delay(to="alice@example.com", subject="Hi", body="body")

# .apply_async() — full control
send_email.apply_async(
    args=["alice@example.com"],     # positional args as a list
    kwargs={"subject": "Hi"},      # keyword args as a dict
    countdown=30,                   # start in 30 seconds
    # eta=datetime(2025,1,1,9,0),   # start at a specific datetime
    # queue="high_priority",        # send to a specific worker queue
    # retry=True, retry_policy={"max_retries": 5}
)

Checking Task Status

Once you have the task ID, you can check the task's state at any time using AsyncResult. This is how you build a progress endpoint that a frontend can poll. The task goes through states in order: PENDING means the task is in the queue waiting for a worker. STARTED means a worker picked it up and it is running (only shown if task_track_started is True in your config). SUCCESS means it finished successfully and the result is stored. FAILURE means an exception was raised. PROGRESS is a custom state you can set yourself using self.update_state() inside the task — it is not built-in but widely used for progress bars. The client polls your /tasks/{id} endpoint every few seconds and updates the UI based on the state.

python
from celery.result import AsyncResult
from tasks import celery_app


@app.get("/tasks/{task_id}")
def get_task_status(task_id: str):
    # AsyncResult looks up the task by ID in Redis
    result = AsyncResult(task_id, app=celery_app)

    # result.state is a string: PENDING, STARTED, PROGRESS, SUCCESS, FAILURE
    if result.state == "PENDING":
        return {"state": "PENDING", "message": "Task is waiting in the queue"}

    elif result.state == "PROGRESS":
        # result.info is the dict passed to self.update_state(meta=...)
        return {
            "state": "PROGRESS",
            "current": result.info.get("current", 0),
            "total":   result.info.get("total",   1)
        }

    elif result.state == "SUCCESS":
        # result.result is the return value of the task function
        return {"state": "SUCCESS", "result": result.result}

    elif result.state == "FAILURE":
        # result.info holds the exception that caused the failure
        return {"state": "FAILURE", "error": str(result.info)}

    else:
        return {"state": result.state}
text
PENDING   — Task is in the queue, not yet picked up by a worker
            (also returned for unknown task IDs — there's no way to tell the difference)

STARTED   — Worker picked it up and is running it
            (only visible if task_track_started=True in your Celery config)

PROGRESS  — Custom state set by self.update_state() inside the task
            result.info = the dict you passed to meta={}

SUCCESS   — Task finished without raising an exception
            result.result = the return value of the task function

FAILURE   — Task raised an unhandled exception
            result.info = the exception object

RETRY     — Task failed and is waiting for a retry (visible between retries)

REVOKED   — Task was cancelled before it ran

Monitoring with Flower

Flower is a real-time web dashboard for Celery — it shows every task that has run, its state, how long it took, which worker handled it, and whether it failed. You run it as a separate process alongside your FastAPI app and Celery worker. In development all three processes run in separate terminals. In production you would run all three as systemd services. Flower reads from the same Redis broker as Celery, so it has a live view of the queue and all workers. It also lets you manually revoke (cancel) pending tasks, inspect task arguments, and see worker CPU and memory usage. It is an optional tool but extremely useful when debugging why tasks are slow or failing.

bash
# Terminal 1 — FastAPI server
uvicorn main:app --reload

# Terminal 2 — Celery worker
# -A tasks → look for the celery_app object in tasks.py
# --loglevel=info → show task start/finish in the terminal
celery -A tasks worker --loglevel=info

# Terminal 3 — Flower dashboard
# Opens at http://localhost:5555
celery -A tasks flower

# On Windows, Celery worker needs an extra flag:
celery -A tasks worker --loglevel=info --pool=solo
bash
# /etc/systemd/system/celery-worker.service
[Unit]
Description=Celery Worker

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/myapp
ExecStart=/home/ubuntu/myapp/venv/bin/celery -A tasks worker --loglevel=info

[Install]

# Enable and start
sudo systemctl enable celery-worker

sudo systemctl status celery-worker
