Git Workflow for Developers

Version control from the ground up. Covers init, staging, commits, branching, merging, resolving conflicts, GitHub push/pull, and a clean feature-branch workflow used in real teams.

1

What is Git?

Git tracks every change you make to your code files over time. It lets you go back to any previous version, work on separate features at the same time without breaking each other, and collaborate with a team by merging everyone's changes together. Every project you work on professionally uses Git, and most use GitHub as the place to store and share the repository.

Init and Config

You run git init once in a folder to start tracking it. Git needs to know your name and email so it can label every commit you make. You set these once globally with git config --global and they apply to all your repositories.

bash
git init                                          # create a new .git folder in the current directory

git config --global user.name "Your Name"         # set your name on all commits (do this once)
git config --global user.email "you@example.com"  # set your email on all commits
git config --global init.defaultBranch main       # make new repos start on 'main' not 'master'

git status                                        # check what Git sees in this folder
bash
git config --list         # print every setting Git knows about (global + local)

git config user.name      # check just one value — prints what is stored for that key
git config user.email     # same pattern for any config key

Stage and Commit

Git does not automatically save every file change. You choose which changed files to include in a commit with git add, then save that snapshot with git commit. The -m flag lets you write the commit message inline. A good commit message describes what changed and why in one short sentence.

bash
git status                                   # see which files have changed or are untracked

git add filename.py                          # stage one specific file
git add .                                    # stage every changed file in the current folder

git commit -m "add user login endpoint"      # save the staged snapshot with a message

git log --oneline                            # show recent commits as one line each

.gitignore

Some files should never go into Git: secret keys, compiled bytecode, virtual environments, and OS metadata files. The .gitignore file lists patterns for files Git should ignore completely. If you accidentally committed a file before adding it to .gitignore, you need to remove it from tracking with git rm --cached.

gitignore
# Virtual environment — never commit this folder
venv/
.venv/

# Python bytecode and cache
__pycache__/
*.pyc
*.pyo
*.pyd

# Environment variables — contains secrets, NEVER commit
.env
.env.*

# Local SQLite database files
*.db
*.sqlite3

# macOS metadata
.DS_Store

# JetBrains IDE files
.idea/

# VS Code workspace settings (optional — some teams commit this)
.vscode/
bash
# First — add the file to .gitignore so it stays ignored from now on
# Then remove it from Git's tracking (does NOT delete the file on disk):

git rm --cached .env                   # stop tracking .env without deleting it
git rm --cached -r __pycache__/        # use -r to remove an entire folder recursively

git commit -m "remove .env from tracking"   # commit the removal so teammates get it too

# If you skip adding to .gitignore first, Git will just re-add it next time

Branches

A branch is a separate copy of the code where you can make changes without affecting the main branch. The main branch always contains working code. You create a feature branch for each new piece of work, then merge it back when it is done.

bash
git branch                          # list all local branches; current branch is marked with *

git branch feature/login            # create a new branch (does not switch to it yet)
git checkout feature/login          # switch to that branch

git checkout -b feature/login       # shortcut: create AND switch in one command

git branch -d feature/login         # delete the branch after it has been merged
reference

git merge <name>Merge the named branch into your current branch

Merging

Merging brings the commits from one branch into another. You switch to the branch you want to merge into (usually main), then run git merge with the branch name. If there are no conflicting changes, Git performs a fast-forward merge and the process is instant.

bash
git checkout main                             # switch to the branch you are merging INTO

git merge feature/login                       # bring commits from feature/login into main

git branch -d feature/login                   # clean up — delete the branch now it is merged

git log --oneline --graph                     # visualise the branch and merge in the commit graph
text
# Fast-forward merge (simplest case)
# main has had NO new commits since you branched off:

  main:     A --- B
                   \
  feature:          C --- D

# Git just moves the main pointer forward to D — no extra commit:

  main:     A --- B --- C --- D

# Merge commit (both branches diverged)
# main has had new commits while you were working on feature:

  main:     A --- B --- E
                   \
  feature:          C --- D

# Git creates a new merge commit M that joins both histories:

  main:     A --- B --- E --- M
                   \         /
  feature:          C --- D

# The merge commit has two parents and shows up in git log --graph

Resolving Conflicts

A conflict happens when two branches edited the same line in the same file. Git cannot decide which version to keep, so it marks both versions in the file and waits for you to choose. You open the file, remove the conflict markers, edit the line to the correct final version, stage the file, and commit.

text
# Git inserts conflict markers directly into the file:

def get_timeout():
<<<<<<< HEAD
    return 30          # <-- your version (current branch)
=======
    return 60          # <-- their version (incoming branch)
>>>>>>> feature/login

# Everything between <<<<<<< HEAD and ======= is your current branch
# Everything between ======= and >>>>>>> is the incoming branch
# You must delete all three marker lines and keep the correct version
bash
git status                          # shows "both modified: auth.py" for each conflicting file

# Open the file in your editor, find the <<<<<<< markers
# Delete the marker lines, keep only the correct final version of the code
# Save the file

git add auth.py                     # stage the resolved file to mark conflict as done

git commit -m "resolve merge conflict in auth.py"
# commit message should always say what was resolved and in which file

GitHub Push and Pull

Your local Git repository only exists on your machine. GitHub is where you store the same repo online so you can share it with teammates and access it from anywhere. git push sends your local commits to GitHub. git pull downloads new commits from GitHub to your local machine.

bash
# On GitHub: create a new empty repository, then copy the URL

git remote add origin https://github.com/yourname/myproject.git
# 'origin' is the conventional name for your main remote

git push -u origin main
# -u sets the upstream so future 'git push' and 'git pull' need no arguments
# after this first push, just run: git push
bash
git pull                             # fetch + merge latest commits from your team on GitHub

# ... make your changes ...

git add .                            # stage everything you changed
git commit -m "feat: add rate limit to login"   # commit with a clear message
git push                             # send your commits to GitHub

Feature Branch Workflow

Real teams follow a consistent workflow so nobody's changes interfere with each other. The rule is simple: never commit directly to main. Create a branch for each feature or fix, push it to GitHub, open a pull request, get it reviewed, then merge it. This keeps main always deployable.

bash
# 1. Always start from the latest main
git checkout main
git pull

# 2. Create a dedicated branch for your feature or fix
git checkout -b feature/user-login

# 3. Make your changes, then commit them
git add .
git commit -m "feat: add user login endpoint"

# 4. Push the branch to GitHub (not main — your feature branch)
git push -u origin feature/user-login

# 5. Open a Pull Request on GitHub (done in the browser)
#    Go to github.com/yourname/myproject and click "Compare & pull request"
#    Add a description, request a reviewer, then submit

# 6. After approval, merge the PR on GitHub (green "Merge pull request" button)

# 7. Pull the now-updated main back to your local machine
git checkout main
git pull

# 8. Delete the local feature branch — it has been merged and is no longer needed
git branch -d feature/user-login
