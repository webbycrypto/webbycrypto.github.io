Testing FastAPI Apps

Write tests that actually find bugs — from simple route tests to database tests with fixtures, dependency mocking, and coverage reports.

1

Why Tests Matter

A test is code that calls your code and checks whether the result is what you expected. Without tests, every time you change a function you have to manually verify that nothing else broke. With tests, you run one command and in a few seconds you know whether everything still works. This matters especially for APIs, which can have dozens of routes, each with different inputs and different error cases. FastAPI makes testing easy: the TestClient wraps your app and lets you make real HTTP requests against it inside a normal Python function, with no running server needed.

What makes a good test: it tests one specific behaviour, it is fast (under a second), it does not depend on external services (email, real database, third-party APIs), and it tells you exactly what broke when it fails. A test that passes 99% of the time and fails randomly is worse than no test.
2

Setup: pytest + TestClient

pytest is the standard Python test runner. It automatically finds any file named test_*.py, looks for functions named test_*, and runs them. If a function raises an AssertionError, the test fails. FastAPI's TestClient wraps your app and gives you methods like client.get() and client.post() that make real HTTP calls against the app without starting a server. You only need to install pytest and httpx. TestClient handles the rest. Test files live in a tests/ folder alongside your application code.

bash
# Install the test dependencies
pip install pytest httpx

# Project structure
myapp/
├── main.py           # your FastAPI app
├── tests/
│   ├── __init__.py   # empty file — makes tests/ a Python package
│   ├── conftest.py   # shared fixtures (step 6)
│   ├── test_items.py # tests for item routes
│   └── test_auth.py  # tests for auth routes

# Run all tests
pytest

# Run a specific file
pytest tests/test_items.py

# Run a specific test function
pytest tests/test_items.py::test_create_item

# Show print() output during tests
pytest -s

# Verbose — shows each test name
pytest -v
python
# tests/test_items.py
from fastapi.testclient import TestClient
from main import app  # import your FastAPI app object

# TestClient wraps the app — no server needed
client = TestClient(app)


# Every function starting with test_ is automatically run by pytest
def test_health():
    # Make a GET request — exactly like requests.get() but against the app
    response = client.get("/health")

    # assert raises AssertionError if the condition is False — pytest catches this
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}

Testing GET Routes

GET route tests are the simplest. You call client.get() with a URL, check the status code, and check the response body. The response object has a status_code integer, a json() method that returns the parsed response as a Python dictionary or list, and a text attribute with the raw response string. A good test covers the happy path and the error paths. Testing what happens when you pass an invalid ID or a missing parameter is just as important as testing success, because error cases are often where bugs hide.

python
def test_get_all_items():
    response = client.get("/items")
    assert response.status_code == 200
    # Empty list is valid — no items yet
    assert isinstance(response.json(), list)


def test_get_item_by_id():
    # First create an item so there is something to GET
    create_resp = client.post("/items?name=Notebook")
    item_id = create_resp.json()["id"]

    # Now test the GET
    response = client.get(f"/items/{item_id}")
    assert response.status_code == 200

    data = response.json()
    assert data["id"]   == item_id
    assert data["name"] == "Notebook"  # check the value we sent


def test_get_with_query_param():
    # Pass query params as a dict — TestClient encodes them correctly
    response = client.get("/items", params={"search": "note", "limit": 10})
    assert response.status_code == 200
python
def test_get_nonexistent_item():
    # ID 99999 does not exist — should return 404
    response = client.get("/items/99999")
    assert response.status_code == 404
    assert "detail" in response.json()  # FastAPI puts error message in "detail"


def test_get_invalid_id_type():
    # "banana" is not an int — FastAPI should return 422 Unprocessable Entity
    response = client.get("/items/banana")
    assert response.status_code == 422


def test_response_keys():
    # Check the exact shape of the response — useful when the contract must be stable
    client.post("/items?name=Pen")
    response = client.get("/items")
    items = response.json()
    if items:
        first = items[0]
        assert "id"   in first
        assert "name" in first

Testing POST Routes with a JSON Body

For POST routes that accept JSON, use client.post() with a json= argument. TestClient converts the dictionary to JSON and sets the Content-Type header automatically. For routes that use Form() parameters instead of JSON, use data= instead. This sends the request as URL-encoded form data, which is what HTML forms send. For file uploads, use files= with a dictionary that maps the field name to a tuple containing the filename, a file object, and the content type. Always test both the successful case and validation failures like missing fields or wrong data types.

python
def test_create_item():
    # json= serialises the dict and sets Content-Type: application/json
    response = client.post("/items", json={"name": "Notebook", "price": 9.99})

    assert response.status_code == 201  # or 200, depending on your route
    data = response.json()
    assert data["name"]  == "Notebook"
    assert data["price"] == 9.99
    assert "id" in data     # server assigned an ID


def test_create_item_missing_field():
    # "name" is required — omitting it should return 422
    response = client.post("/items", json={"price": 9.99})
    assert response.status_code == 422


def test_create_item_wrong_type():
    # price should be a number — sending a string should return 422
    response = client.post("/items", json={"name": "Pen", "price": "expensive"})
    assert response.status_code == 422
python
def test_signup_form():
    # data= sends as application/x-www-form-urlencoded (Form() params)
    response = client.post("/signup", data={
        "email":    "alice@example.com",
        "password": "securepass123"
    })
    assert response.status_code == 200
python
import io

def test_file_upload():
    # Create a fake in-memory file — io.BytesIO() wraps bytes as a file object
    fake_image = io.BytesIO(b"fake image content")

    # files= sends as multipart/form-data
    # ("upload.jpg", fake_image, "image/jpeg") = (filename, file-obj, content-type)
    response = client.post(
        "/upload",
        files={"file": ("upload.jpg", fake_image, "image/jpeg")}
    )
    assert response.status_code == 200
    assert "saved_as" in response.json()

Testing Protected Routes with Auth Headers

Routes that require a JWT or API key check the Authorization header. In tests you need to either log in first and use a real token, or skip auth entirely using dependency_overrides, which is covered in step 7. The simplest approach for integration tests is a helper function that creates a test user, logs in, and returns a headers dictionary with the token. You then pass that dictionary to the headers= argument on client.get() or client.post(). TestClient adds those headers to the request automatically.

python
def test_protected_route():
    # Step 1: create a user and get a token
    client.post("/auth/signup", json={
        "email": "test@example.com",
        "password": "password123"
    })
    login_resp = client.post("/auth/login", json={
        "email": "test@example.com",
        "password": "password123"
    })
    token = login_resp.json()["access_token"]

    # Step 2: use the token on the protected route
    response = client.get(
        "/profile",
        headers={"Authorization": f"Bearer {token}"}
    )
    assert response.status_code == 200


def test_protected_route_no_token():
    # No auth header — should return 401 Unauthorized
    response = client.get("/profile")
    assert response.status_code == 401


def test_protected_route_bad_token():
    # Invalid token — should return 401
    response = client.get("/profile", headers={"Authorization": "Bearer notavalidtoken"})
    assert response.status_code == 401
python
# A helper that creates a user and returns headers with a valid token
# Call this at the top of tests that need an authenticated user
def get_auth_headers(email="test@example.com", password="password123"):
    # Signup (ignore error if user already exists)
    client.post("/auth/signup", json={"email": email, "password": password})

    # Login and extract token
    resp = client.post("/auth/login", json={"email": email, "password": password})
    token = resp.json()["access_token"]

    # Return headers dict — pass directly to any client call
    return {"Authorization": f"Bearer {token}"}


def test_create_item_authenticated():
    headers = get_auth_headers()
    response = client.post("/items", json={"name": "Pen"}, headers=headers)
    assert response.status_code == 201

Fixtures and conftest.py

A fixture is a function that sets up something a test needs and cleans it up afterwards. The @pytest.fixture decorator marks a function as a fixture. Any test function that lists the fixture's name as a parameter automatically receives its return value. The conftest.py file is a special file pytest finds automatically in your tests/ folder. Fixtures defined there are available to all test files without any imports. The yield keyword in a fixture separates setup from teardown: code before yield runs before the test and code after yield runs after, even if the test fails.

python
# tests/conftest.py — fixtures here are available to all test files
import pytest
from fastapi.testclient import TestClient
from main import app


# scope="module" → one client per test file (not recreated for every test)
# scope="function" → fresh client for every single test (default)
@pytest.fixture(scope="module")
def client():
    # Everything before yield is setup
    with TestClient(app) as c:
        yield c  # the test receives this value as the "client" parameter
    # Everything after yield is teardown — runs after the test finishes


@pytest.fixture
def sample_item(client):
    # Create an item and return it — any test that needs an existing item uses this
    resp = client.post("/items", json={"name": "Test Item"})
    item = resp.json()
    yield item
    # Teardown: delete the item after the test
    client.delete(f"/items/{item['id']}")
python
# tests/test_items.py — no import needed for conftest.py fixtures

# List the fixture name as a parameter — pytest injects the value
def test_get_item(client, sample_item):
    # client   → TestClient from conftest.py
    # sample_item → the created item dict from conftest.py
    item_id = sample_item["id"]

    response = client.get(f"/items/{item_id}")
    assert response.status_code == 200
    assert response.json()["name"] == "Test Item"


def test_update_item(client, sample_item):
    item_id = sample_item["id"]
    response = client.put(f"/items/{item_id}", json={"name": "Updated"})
    assert response.json()["name"] == "Updated"

Mocking Dependencies

FastAPI's Depends() system can be overridden in tests. The app.dependency_overrides dictionary maps a real dependency function to a replacement function. When the app runs, it calls your replacement instead of the real one. This is how you skip authentication by returning a fake user, avoid hitting a real database by using an in-memory session, or avoid calling external services by using a mock. Tests that use overrides are fast and self-contained because they do not need real credentials or internet access. Always clear the overrides after each test so they do not leak into other tests.

python
import pytest
from main import app
from auth import get_current_user  # the real auth dependency


# A fake user that bypasses all auth logic
def fake_user():
    return {"id": 1, "email": "test@example.com", "role": "user"}


@pytest.fixture
def authed_client():
    # Override get_current_user with fake_user for every route in this test
    app.dependency_overrides[get_current_user] = fake_user

    with TestClient(app) as c:
        yield c

    # IMPORTANT: clear overrides after — or they bleed into other tests
    app.dependency_overrides.clear()


def test_protected_route(authed_client):
    # This route normally requires auth — but the override makes it always pass
    response = authed_client.get("/profile")
    assert response.status_code == 200
python
from services import get_email_service  # the real email dependency


class FakeEmailService:
    """Captures sent emails without actually sending anything."""
    def __init__(self):
        self.sent = []  # list of dicts we can inspect in tests

    def send(self, to: str, subject: str):
        self.sent.append({"to": to, "subject": subject})
        # Does nothing — no real email sent

fake_email = FakeEmailService()


@pytest.fixture
def client_with_fake_email():
    app.dependency_overrides[get_email_service] = lambda: fake_email
    with TestClient(app) as c:
        yield c, fake_email   # yield both so the test can inspect sent emails
    app.dependency_overrides.clear()
    fake_email.sent.clear() # reset for next test


def test_signup_sends_email(client_with_fake_email):
    client, email_svc = client_with_fake_email
    client.post("/signup", json={"email": "alice@example.com"})

    # Assert that exactly one email was sent to the right address
    assert len(email_svc.sent) == 1
    assert email_svc.sent[0]["to"] == "alice@example.com"

Testing with a Real (SQLite) Database

If your routes read and write a database, your tests need a database too. The best approach is a separate SQLite database that is created fresh for each test and deleted afterwards. You override the get_db dependency to return a session connected to the test database instead of the real one. SQLite is perfect for this because it needs no server setup and can even run entirely in memory. The key rule is to create a fresh database for every test function, not just every test run. If one test creates a record, you do not want that record to show up in the next test's results.

python
# tests/conftest.py
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from fastapi.testclient import TestClient
from main import app
from database import Base, get_db  # your ORM base and session dependency

# In-memory SQLite — a fresh database with every test session
TEST_DATABASE_URL = "sqlite:///./test.db"

engine = create_engine(TEST_DATABASE_URL, connect_args={"check_same_thread": False})
TestingSession = sessionmaker(autocommit=False, autoflush=False, bind=engine)


@pytest.fixture(scope="function")  # fresh DB state for every test
def db_client():
    # Create all tables at the start of each test
    Base.metadata.create_all(bind=engine)

    def override_get_db():
        db = TestingSession()
        try:
            yield db
        finally:
            db.close()

    # Replace the real DB dependency with the test one
    app.dependency_overrides[get_db] = override_get_db

    with TestClient(app) as client:
        yield client

    # Teardown: drop all tables so the next test starts clean
    Base.metadata.drop_all(bind=engine)
    app.dependency_overrides.clear()
python
# tests/test_db_routes.py

def test_create_and_retrieve(db_client):
    # Each test gets a clean database — no data from other tests
    response = db_client.post("/items", json={"name": "Notebook"})
    assert response.status_code == 201
    item_id = response.json()["id"]

    # Retrieve it — should be in the database
    get_resp = db_client.get(f"/items/{item_id}")
    assert get_resp.status_code == 200
    assert get_resp.json()["name"] == "Notebook"


def test_list_is_empty_at_start(db_client):
    # Because scope="function", the database is clean for this test too
    # Even if test_create_and_retrieve ran before, its data is gone
    response = db_client.get("/items")
    assert response.json() == []

Running Tests and Checking Coverage

Coverage tells you which lines of your code actually ran during the tests. A line that was never executed could contain a bug you would never catch. The pytest-cov plugin measures this. Run pytest with --cov=app and it shows a table with the percentage of lines covered in each file. The missing lines column shows you exactly which line numbers were never reached by any test. One hundred percent coverage does not guarantee your app has no bugs, because you still need meaningful assertions. Below 60% coverage usually means large parts of your logic are completely untested, which is a real risk in production.

bash
# Install coverage plugin
pip install pytest-cov

# Run tests with coverage report in the terminal
pytest --cov=app

# Show which line numbers were missed
pytest --cov=app --cov-report=term-missing

# Generate an HTML report — open htmlcov/index.html in a browser
# Each file shows green (covered) and red (missed) lines
pytest --cov=app --cov-report=html

# Fail the test run if coverage drops below 80%
pytest --cov=app --cov-fail-under=80

# Run only tests matching a keyword
pytest -k "item"  # runs test_create_item, test_get_item, etc.

# Run tests in parallel (pip install pytest-xdist)
pytest -n auto   # uses all CPU cores
ini
# pytest.ini — put this in your project root
# Saves you from typing the same flags every time
[pytest]
testpaths = tests          # where pytest looks for test files
addopts =
    --cov=app              # measure coverage for the app/ package
    --cov-report=term-missing  # show missed line numbers in terminal
    -v                     # verbose output — show each test name

# Now just run: pytest
# and all the flags are applied automatically
