Capstone 1: B2B Lead Enrichment Bridge

A third-party webhook delivers a lead to your FastAPI endpoint. You return 202 Accepted immediately, offload enrichment to a BackgroundTask, call external APIs to fill in company data, force an LLM to output a structured sales script via Pydantic, and save everything to PostgreSQL — wrapped in retry logic that handles rate limits gracefully.

1

Architecture Overview

Before writing any code, it helps to understand why this system is designed the way it is. Webhooks have a timing problem. When a third-party service sends a POST request to your endpoint, it waits for a reply. If your server takes more than a few seconds to respond, the sender assumes something went wrong and may retry or log an error.

Enriching a lead properly takes time. You need to call an external API to look up the company, then call an AI to generate a sales script. Each of those can take several seconds. You cannot do all that work before responding without risking a timeout.

The solution is the 202 Accepted pattern. HTTP 202 means "I received your request and accepted it, but the work is not finished yet." Your endpoint validates the incoming data, saves a minimal record, and immediately returns 202. The sender gets a fast reply in under 100ms. Meanwhile, a BackgroundTask does the real work behind the scenes at its own pace.

This pattern applies any time your server receives a request that triggers slow work, such as sending emails, processing images, or calling multiple external services. Waiting for everything before responding leads to timeouts and duplicate records in your database.

Data flow in this project:
1. Third-party POST /webhook with lead JSON → 202 Accepted (under 100ms)
2. BackgroundTask starts → calls enrichment API with email domain
3. BackgroundTask calls LLM → structured Pydantic output (sales script + priority score)
4. BackgroundTask saves completed Lead record to PostgreSQL
5. GET /leads returns all enriched leads (protected by API key)

Project Setup + Database Models

This project uses two database tables. The leads table stores every incoming webhook. It holds both the raw data that arrived and the enriched data added later by the BackgroundTask. A status field starts as "pending" and changes to "enriched" when the job completes, so you can always find leads that are still processing or that failed.

The api_keys table stores bcrypt-hashed API keys that protect the webhook endpoint and the leads listing. Storing keys as hashes means an attacker who sees your database still cannot use the keys to call your API.

The folder structure for this project separates concerns cleanly. A services/ directory holds the enrichment and AI logic. Route handlers stay thin. They validate input, start a BackgroundTask, and return a response. The actual work lives in service functions that the BackgroundTask calls. This separation makes testing easier because you can test each service function without running a full HTTP server.

python
from sqlalchemy import Column, Integer, String, Text, DateTime, Float
from sqlalchemy.ext.declarative import declarative_base
from datetime import datetime

Base = declarative_base()


class Lead(Base):
    __tablename__ = "leads"

    id           = Column(Integer, primary_key=True, index=True)
    email        = Column(String, index=True)        # lead's email address from webhook
    name         = Column(String, nullable=True)        # lead's name if provided
    company      = Column(String, nullable=True)        # filled in by enrichment API
    industry     = Column(String, nullable=True)        # filled in by enrichment API
    employee_count = Column(Integer, nullable=True)    # filled in by enrichment API
    sales_script = Column(Text, nullable=True)          # generated by LLM
    priority     = Column(Float, nullable=True)         # 1-10 priority score from LLM
    status       = Column(String, default="pending")    # "pending" → "enriched" | "failed"
    raw_payload  = Column(Text, nullable=True)          # original webhook JSON, stored as string
    created_at   = Column(DateTime, default=datetime.utcnow)
    enriched_at  = Column(DateTime, nullable=True)      # set when BackgroundTask completes


class APIKey(Base):
    __tablename__ = "api_keys"

    id         = Column(Integer, primary_key=True)
    label      = Column(String)          # human-readable name, e.g. "Production CRM"
    key_hash   = Column(String)          # bcrypt hash of the actual key — never store plain
    created_at = Column(DateTime, default=datetime.utcnow)

The Webhook Endpoint — 202 Accepted

The webhook endpoint has one job: accept the incoming data and return a response as fast as possible. It validates the request body against a Pydantic schema, creates a minimal database record with status "pending", and registers a BackgroundTask. All of that should complete in under 50 milliseconds.

The response status code matters. HTTP 200 means "the request is complete and here is the result." HTTP 202 means "I received your request and I have started working on it, but it is not done yet." Using 202 is the correct choice here. It tells the sender everything is fine and they can stop waiting. Using 200 would be misleading because the enrichment has not happened yet.

You create the Lead database record immediately in the route handler before returning. This guarantees you have a record even if the BackgroundTask fails or the server crashes. You can always query for leads with status "pending" and retry them later. If you waited until the BackgroundTask finished to save the record, a crash would lose the lead entirely.

python
from pydantic import BaseModel, EmailStr
from typing import Optional


class WebhookPayload(BaseModel):
    """
    Schema for the incoming webhook body.
    EmailStr validates that the email field is a valid email address format.
    Optional fields are allowed to be missing — the enrichment API will fill them in.
    """
    email: EmailStr                      # required — used to look up the company domain
    name:  Optional[str] = None          # optional — may not be provided by the sender
    source: Optional[str] = None         # optional — which form / campaign this came from


class LeadResponse(BaseModel):
    """Schema for the GET /leads response — what the API returns per lead."""
    id:            int
    email:         str
    name:          Optional[str]
    company:       Optional[str]
    industry:      Optional[str]
    employee_count: Optional[int]
    sales_script:  Optional[str]
    priority:      Optional[float]
    status:        str

    class Config:
        from_attributes = True           # allows Pydantic to read SQLAlchemy model fields

from fastapi import FastAPI, BackgroundTasks, Depends, Response
from sqlalchemy.orm import Session
import json

from database import get_db, engine
from models import Base, Lead
from schemas import WebhookPayload, LeadResponse
from services.pipeline import enrich_lead      # the BackgroundTask function
from middleware.api_key import verify_api_key  # the key-checking dependency

# Create all tables on startup if they don't exist
Base.metadata.create_all(bind=engine)

app = FastAPI(title="Lead Enrichment Bridge")


@app.post("/webhook", status_code=202, dependencies=[Depends(verify_api_key)])
async def receive_webhook(
    payload: WebhookPayload,
    background_tasks: BackgroundTasks,
    db: Session = Depends(get_db)
):
    # 1. Create a minimal Lead record immediately — status "pending"
    # This guarantees we have a record even if the BackgroundTask never runs
    lead = Lead(
        email=payload.email,
        name=payload.name,
        status="pending",
        raw_payload=json.dumps(payload.model_dump())  # store original for debugging
    )
    db.add(lead)
    db.commit()
    db.refresh(lead)  # reload from DB to get the auto-generated id

    # 2. Register the enrichment task — it runs AFTER this function returns
    # Pass lead.id (not the lead object) — the BackgroundTask opens its own DB session
    background_tasks.add_task(enrich_lead, lead.id)

    # 3. Return 202 immediately — enrichment hasn't started yet
    # The sender gets a fast response; the work happens behind the scenes
    return {"accepted": True, "lead_id": lead.id}


@app.get("/leads", response_model=list[LeadResponse], dependencies=[Depends(verify_api_key)])
async def list_leads(db: Session = Depends(get_db)):
    # Return all leads, newest first
    return db.query(Lead).order_by(Lead.created_at.desc()).all()

The BackgroundTask Pipeline

The pipeline function is the orchestrator. It takes a lead ID, opens its own database session, and runs all three steps in order: fetch company data, call the AI, and save the result. Each step can fail on its own. If the enrichment API is down, you want to mark the lead as failed rather than leave it stuck as "pending" forever. A try/except/finally block around the whole pipeline ensures the status is always updated, even when something goes wrong.

The most important rule for BackgroundTask functions: never accept a database session as a parameter. The session used in the route handler closes the moment the response is sent. If you pass that closed session to the BackgroundTask, you will get a cryptic error when you try to use it. Always open a fresh session inside the BackgroundTask and close it yourself in a finally block.

python
from datetime import datetime
from database import SessionLocal  # NOT get_db — we manage our own session here
from models import Lead
from services.enrichment import fetch_company_data
from services.llm import generate_sales_script


def enrich_lead(lead_id: int):
    """
    Called as a BackgroundTask — runs after the 202 response is sent.
    Opens its own DB session, runs enrichment, saves result, closes session.
    """
    # Always create a fresh session — never reuse the request-scoped one
    db = SessionLocal()
    try:
        # Fetch the lead record we created in the route handler
        lead = db.query(Lead).filter(Lead.id == lead_id).first()
        if not lead:
            return  # shouldn't happen, but guard anyway

        # Step 1: Extract the domain from the email (e.g. "stripe.com" from "sarah@stripe.com")
        domain = lead.email.split("@")[1]

        # Step 2: Call the enrichment API — returns a dict with company info
        # This function handles retries internally (see Step 9)
        company_data = fetch_company_data(domain)

        # Step 3: Update the lead with enrichment data
        lead.company       = company_data.get("name")
        lead.industry      = company_data.get("industry")
        lead.employee_count = company_data.get("employee_count")

        # Step 4: Call the LLM — returns a structured object with sales_script + priority
        script_data = generate_sales_script(lead.name, company_data)

        # Step 5: Update the lead with LLM output
        lead.sales_script = script_data.sales_script
        lead.priority     = script_data.priority

        # Step 6: Mark as complete
        lead.status      = "enriched"
        lead.enriched_at = datetime.utcnow()

        db.commit()

    except Exception as e:
        # Enrichment failed — mark the lead so we know to retry it
        # Don't let the exception bubble up — BackgroundTask errors are silent otherwise
        print(f"Enrichment failed for lead {lead_id}: {e}")
        try:
            lead = db.query(Lead).filter(Lead.id == lead_id).first()
            if lead:
                lead.status = "failed"
                db.commit()
        except:
            pass

    finally:
        db.close()  # always close — don't rely on garbage collection

External API Enrichment with httpx

The enrichment service calls an external company data API using the email domain. Several real services provide this, such as Clearbit, Hunter.io, Apollo.io, or the free Brandfetch API. The core pattern is the same regardless of which you choose. You make an authenticated HTTP GET request, parse the JSON response, and return a clean dictionary to the pipeline.

One important point: the BackgroundTask function here is a regular synchronous function, not an async def. This means you use httpx.Client() instead of httpx.AsyncClient(). FastAPI runs synchronous BackgroundTask functions in a thread pool, so synchronous httpx works correctly. Mixing sync and async incorrectly is a common source of subtle bugs, so being deliberate about which one you are using matters.

python
import httpx
import os


def fetch_company_data(domain: str) -> dict:
    """
    Calls an enrichment API to get company info for a given domain.
    Returns a dict with: name, industry, employee_count, description.
    Retries are handled by tenacity in Step 9 — this function just makes one attempt.
    """
    api_key = os.getenv("ENRICHMENT_API_KEY", "")

    # httpx.Client() — synchronous, correct for use inside a BackgroundTask
    # timeout=10.0 — raise an exception if the API takes longer than 10 seconds
    with httpx.Client(timeout=10.0) as client:
        response = client.get(
            f"https://api.brandfetch.io/v2/brands/{domain}",
            headers={"Authorization": f"Bearer {api_key}"}
        )
        response.raise_for_status()  # raises httpx.HTTPStatusError on 4xx/5xx
        data = response.json()

    # Normalise the response into a clean dict regardless of API response structure
    return {
        "name":           data.get("name", domain),
        "industry":      data.get("industries", [{}])[0].get("name", "Unknown"),
        "employee_count": data.get("companiesCount", None),
        "description":   data.get("description", ""),
    }

Structured LLM Output with Pydantic

Getting free-form text from an AI is easy. Getting back structured data you can store in a database is harder. If you ask the AI to "write a sales script and give a priority score", it might return a paragraph, or JSON, or ignore your instructions entirely. You cannot reliably extract a number from unstructured text in code.

The modern solution is to tell the AI to respond in JSON using response_format={"type": "json_object"}. You describe exactly what fields you want in the system prompt and the AI constrains its output to match. You then parse that JSON into a Pydantic model. If the JSON does not match the expected shape, Pydantic raises a validation error that you can catch. This is far more reliable than trying to parse free-form text with code.

python
import json
import os
from openai import OpenAI
from pydantic import BaseModel, Field


class SalesScriptOutput(BaseModel):
    """
    The exact JSON structure we expect the LLM to return.
    Field descriptions become part of the prompt — write them clearly.
    """
    sales_script: str = Field(description="A 2-3 sentence personalised opening for a cold outreach email to this lead.")
    priority:     float = Field(ge=1.0, le=10.0, description="Priority score from 1-10. Higher = better fit for our product.")
    reasoning:    str = Field(description="One sentence explaining why you gave this priority score.")


client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


def generate_sales_script(name: str, company_data: dict) -> SalesScriptOutput:
    """
    Calls GPT-4o with response_format=json_object.
    Returns a validated SalesScriptOutput Pydantic model.
    Retries handled by tenacity in Step 9.
    """
    # Describe the exact JSON fields you want in the system prompt
    system_prompt = """You are a B2B sales assistant. Given information about a lead and their company,
    you output a JSON object with exactly these fields:
    - sales_script (string): A 2-3 sentence personalised opening for a cold outreach email
    - priority (float): Priority score 1-10 based on how well they fit our product
    - reasoning (string): One sentence explaining the priority score

    Output ONLY the JSON object, no other text."""

    user_message = f"""Lead name: {name or 'Unknown'}
Company: {company_data.get('name', 'Unknown')}
Industry: {company_data.get('industry', 'Unknown')}
Employees: {company_data.get('employee_count', 'Unknown')}
Description: {company_data.get('description', '')}"""

    response = client.chat.completions.create(
        model="gpt-4o-mini",
        response_format={"type": "json_object"},  # forces JSON output — no stray text
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_message},
        ],
        max_tokens=300,
        temperature=0.7,
    )

    # Parse the JSON string from the response content
    raw_json = response.choices[0].message.content
    data = json.loads(raw_json)

    # Validate the parsed dict against the Pydantic schema
    # This raises ValidationError if the LLM returned unexpected fields or types
    return SalesScriptOutput(**data)

Saving to PostgreSQL — End to End

At this point the pipeline is complete. The BackgroundTask has enriched company data from the external API and a structured sales script from the AI. The final step is writing everything to the Lead record in PostgreSQL and changing the status to "enriched". Commit all fields at once as the last step. You do not want to save a partially enriched record.

To test the full pipeline without an internet connection, use the mock enrichment function from Step 5 and a mock AI response. The mock AI function returns a hardcoded output so you can test the complete database write flow with no API keys required. Once the pipeline works with mocks, swap in the real implementations one at a time.

API Key Middleware

The webhook endpoint and the leads listing must be protected. Only authorised senders should be able to post to your webhook, and only authorised clients should be able to read enriched leads. The standard way for servers to authenticate each other is with an API key sent in a request header. You store these keys in the database as bcrypt hashes, never as plain text. When a request arrives, you hash the incoming key and compare it to the stored hashes. If any match, the request is allowed through.

In FastAPI, this is implemented as a dependency function that reads the X-API-Key header. If the header is missing or the key does not match any stored hash, the dependency raises an HTTPException with status 403 and FastAPI automatically stops the request and returns the error. You attach this dependency to routes using dependencies=[Depends(verify_api_key)].

python
from fastapi import Depends, HTTPException, Header
from sqlalchemy.orm import Session
import bcrypt

from database import get_db
from models import APIKey


def verify_api_key(
    x_api_key: str = Header(...),      # reads X-API-Key header; raises 422 if missing
    db: Session = Depends(get_db)
):
    """
    FastAPI dependency — checks X-API-Key header against bcrypt hashes in DB.
    Raises 403 if key is missing or doesn't match any stored hash.
    """
    # Load all stored key hashes from the database
    stored_keys = db.query(APIKey).all()

    # Check the incoming key against each stored hash
    # bcrypt.checkpw() returns True if the plain key matches the stored hash
    key_bytes = x_api_key.encode("utf-8")
    for stored in stored_keys:
        if bcrypt.checkpw(key_bytes, stored.key_hash.encode("utf-8")):
            return  # key is valid — let the request through

    # No matching key found — reject the request
    raise HTTPException(status_code=403, detail="Invalid or missing API key")

Retry Logic with tenacity

Every time your BackgroundTask calls an external service, there is a chance it fails. The most common failure is a 429 rate limit error, which means the API received too many requests and is telling you to slow down. Retrying immediately will fail again for the same reason. The correct approach is exponential backoff: wait a short time before the first retry, a longer time before the second, and longer still before the third, then give up.

The tenacity library makes this a one-line decorator. Adding @retry(wait=wait_exponential(multiplier=1, min=1, max=30), stop=stop_after_attempt(3)) means the function will retry up to 3 times, waiting 1 second before the first retry, 2 seconds before the second, and 4 seconds before the third. You apply this decorator to the enrichment and AI functions. The pipeline function that calls them does not need to know about retries at all. If all three attempts fail, tenacity raises the last exception, which the pipeline's except block catches.

python
import httpx
import os
from tenacity import retry, wait_exponential, stop_after_attempt, retry_if_exception_type


# Retry on any httpx error (connection error, timeout, 429, 500, etc.)
# Wait: 1s → 2s → 4s (exponential), capped at 30s. Give up after 3 attempts.
@retry(
    wait=wait_exponential(multiplier=1, min=1, max=30),
    stop=stop_after_attempt(3),
    retry=retry_if_exception_type((httpx.HTTPError, httpx.TimeoutException))
)
def fetch_company_data(domain: str) -> dict:
    """
    Same logic as before — tenacity handles retries transparently.
    If all 3 attempts fail, tenacity re-raises the last exception.
    The pipeline's except block catches it and marks the lead as "failed".
    """
    api_key = os.getenv("ENRICHMENT_API_KEY", "")
    with httpx.Client(timeout=10.0) as client:
        response = client.get(
            f"https://api.brandfetch.io/v2/brands/{domain}",
            headers={"Authorization": f"Bearer {api_key}"}
        )
        response.raise_for_status()
        data = response.json()
    return {
        "name":           data.get("name", domain),

import json, os
from openai import OpenAI, RateLimitError, APIError
from pydantic import BaseModel, Field
from tenacity import retry, wait_exponential, stop_after_attempt, retry_if_exception_type

client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


class SalesScriptOutput(BaseModel):
    sales_script: str   = Field(description="2-3 sentence personalised cold email opening.")
    priority:     float = Field(ge=1.0, le=10.0, description="Fit score 1-10.")
    reasoning:    str   = Field(description="One sentence explaining the priority score.")


# Retry on OpenAI rate limit (429) and server errors (500+)
# 3 attempts with 2s → 4s → 8s backoff
@retry(
    wait=wait_exponential(multiplier=2, min=2, max=60),
    stop=stop_after_attempt(3),
    retry=retry_if_exception_type((RateLimitError, APIError))
)
def generate_sales_script(name: str, company_data: dict) -> SalesScriptOutput:
    system_prompt = """You are a B2B sales assistant. Given lead info, output JSON with:
    - sales_script (string): 2-3 sentence personalised cold email opening
    - priority (float 1-10): fit score
    - reasoning (string): one sentence explaining the score
    Output ONLY the JSON object."""

    user_message = f"""Lead: {name or 'Unknown'} | Company: {company_data.get('name')} | Industry: {company_data.get('industry')} | Employees: {company_data.get('employee_count')}"""

    response = client.chat.completions.create(
        model="gpt-4o-mini",
        response_format={"type": "json_object"},
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_message},
        ],
        max_tokens=300,
    )
    data = json.loads(response.choices[0].message.content)
    return SalesScriptOutput(**data)

Testing the Pipeline

Testing a BackgroundTask pipeline requires a specific strategy. You do not want tests to make real API calls. Tests should be fast, predictable, and free to run. The solution is to use app.dependency_overrides to swap real dependencies for mocks, and unittest.mock.patch to replace the service functions themselves. Your test sends a POST to /webhook, checks that the response is 202, then calls the pipeline function directly with mock data to verify the database was written correctly.
