Django REST Framework

Build a JSON API with Django — serializers, class-based views, ViewSets, token authentication, and permissions. Connect it to a JavaScript frontend or mobile app.

1

DRF vs Django Templates

Regular Django builds pages by rendering HTML on the server and sending the full page to the browser on each request. Django REST Framework (DRF) uses the same Django core, including models, the ORM, the admin panel, and migrations, but your views return JSON instead of HTML. Instead of templates you use serializers, which convert model objects into plain Python dicts. Any frontend, whether it is React, Vue, a mobile app, or another service, can then read that JSON over HTTP. DRF is how most production Django projects are built when there is a separate frontend or a mobile app involved.

When to use DRF: your frontend is React, Vue, or a mobile app. Multiple clients need the same data. You want the Django admin panel for free. Your team works on frontend and backend separately.

When to use Django templates: small single-developer project, no mobile app, SEO is critical (server-rendered HTML is better indexed), or you want simplicity without a JSON API layer.
2

Install and Setup

DRF is a normal Django app. You install it with pip and add it to INSTALLED_APPS just like any other package, and it needs no separate server or process. The REST_FRAMEWORK settings dictionary controls global defaults for your whole API. The two most common settings are DEFAULT_PERMISSION_CLASSES, which sets who can access the API by default, and DEFAULT_AUTHENTICATION_CLASSES, which sets how the API identifies the current user. Setting these globally means you do not need to repeat them on every single view, but you can always override them on a specific view when needed.

bash
# Install DRF
pip install djangorestframework

# Create a new Django project (if you don't have one)
django-admin startproject myapi .

# Create an app for your models + API
python manage.py startapp books

# Run migrations and start the server
python manage.py migrate
python manage.py runserver
python
# settings.py
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "rest_framework",               # add DRF
    "rest_framework.authtoken",      # add if using token auth (step 6)

    # Who can call the API by default
    "DEFAULT_PERMISSION_CLASSES": [

}

Serializers — Converting Models to JSON

A serializer does two things: it converts a Django model instance into a Python dict that can be sent as JSON, and it validates incoming JSON data and converts it back into a model instance. Think of it as DRF's equivalent of a Django form, but built for APIs. The ModelSerializer is the most common type. You give it a model class and a list of fields, and it automatically builds all the validation rules from the model's own field definitions. You only need to explicitly declare a field when you want to add or change something that is not already in the model, like a computed value or a nested relationship.

python
# books/models.py
from django.db import models
from django.contrib.auth.models import User


class Book(models.Model):
    title       = models.CharField(max_length=200)
    author      = models.CharField(max_length=100)
    published   = models.DateField()
    description = models.TextField(blank=True)
    created_by  = models.ForeignKey(User, on_delete=models.CASCADE, related_name="books")
    created_at  = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.title
python
# books/serializers.py
from rest_framework import serializers
from .models import Book


class BookSerializer(serializers.ModelSerializer):
    # Extra fields not in the model — computed or read-only
    # read_only=True means this field appears in GET responses but not POST/PUT
    created_by_username = serializers.CharField(
        source="created_by.username",  # follow the ForeignKey and get .username
        read_only=True
    )

    class Meta:
        model  = Book                         # which model to serialise
        fields = [                            # which fields to include in the JSON
            "id", "title", "author", "published",
            "description", "created_by_username", "created_at"
        ]
        read_only_fields = ["id", "created_at"]  # auto-set, never from user input
python
# Nested serializer — embed related object data inline instead of just an ID
from django.contrib.auth.models import User

class UserSerializer(serializers.ModelSerializer):
    class Meta:
        model  = User
        fields = ["id", "username", "email"]


class BookSerializer(serializers.ModelSerializer):
    # Nest the full user object inside each book
    # Without this, created_by would just be an integer (the user's PK)
    created_by = UserSerializer(read_only=True)

    class Meta:
        model  = Book
        fields = ["id", "title", "author", "published", "created_by"]

APIView — Class-Based Views

DRF's APIView is the base class you use when writing views by hand. You define methods named get(), post(), put(), and delete(), one for each HTTP method you want to support. DRF handles parsing the request body for you and gives you request.data instead of request.POST. The Response object automatically converts your dict to JSON. A view class usually needs two URL patterns: one for the collection, like /books/, which handles listing and creating, and one for a single item, like /books/1/, which handles reading, updating, and deleting.

python
# books/views.py
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from .models import Book
from .serializers import BookSerializer


# Handles: GET /books/  and  POST /books/
class BookListCreate(APIView):

    def get(self, request):
        # Fetch all books, serialise to a list of dicts
        books = Book.objects.all()
        serializer = BookSerializer(books, many=True)  # many=True for querysets
        return Response(serializer.data)                   # 200 OK by default

    def post(self, request):
        # request.data contains the parsed JSON body
        serializer = BookSerializer(data=request.data)

        if serializer.is_valid():
            # save() creates the DB row — pass extra fields not in the request
            serializer.save(created_by=request.user)
            return Response(serializer.data, status=status.HTTP_201_CREATED)

        # serializer.errors is a dict of field → list of error messages
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)


# Handles: GET /books/1/  PUT /books/1/  DELETE /books/1/
class BookDetail(APIView):

    def get_object(self, pk):
        try:
            return Book.objects.get(pk=pk)
        except Book.DoesNotExist:
            raise Http404         # DRF converts this to a 404 JSON response

    def get(self, request, pk):
        book = self.get_object(pk)
        return Response(BookSerializer(book).data)

    def put(self, request, pk):
        book = self.get_object(pk)
        # partial=True allows updating just some fields (like PATCH)
        serializer = BookSerializer(book, data=request.data, partial=True)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

    def delete(self, request, pk):
        book = self.get_object(pk)
        book.delete()
        return Response(status=status.HTTP_204_NO_CONTENT)  # 204 = deleted, no body
python
# books/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("books/",     views.BookListCreate.as_view()),  # list + create
    path("books/<int:pk>/", views.BookDetail.as_view()),   # retrieve + update + delete
]

    path("admin/", admin.site.urls),
    path("api/",   include("books.urls")),   # all book routes at /api/books/

ViewSets and Routers — Less Code, Same Result

Writing get(), post(), put(), and delete() by hand for every resource gets repetitive fast. A ViewSet combines all those actions into one class, and a Router automatically generates all the URL patterns from it. ModelViewSet is the highest-level option: you declare a queryset and a serializer_class, and you get all six standard REST actions for free. In practice, most DRF projects use ViewSets and Routers for standard CRUD, and fall back to APIView for custom endpoints like login or analytics that do not map neatly to a model.

python
from rest_framework import viewsets, permissions
from .models import Book
from .serializers import BookSerializer


class BookViewSet(viewsets.ModelViewSet):
    # queryset  → which objects this ViewSet operates on
    queryset            = Book.objects.all().order_by("-created_at")

    # serializer_class → used for all read and write operations
    serializer_class    = BookSerializer

    # permission_classes → who can call which actions
    permission_classes  = [permissions.IsAuthenticatedOrReadOnly]

    # Override perform_create to set fields automatically
    # This runs when a new book is created (POST /api/books/)
    def perform_create(self, serializer):
        # created_by is set from the authenticated user — not from the request body
        serializer.save(created_by=self.request.user)
python
# books/urls.py — Router replaces all manual URL patterns
from rest_framework.routers import DefaultRouter
from .views import BookViewSet

router = DefaultRouter()
# register("books", BookViewSet) generates:
#   GET  /api/books/         → list
#   POST /api/books/         → create
#   GET  /api/books/{id}/    → retrieve
#   PUT  /api/books/{id}/    → update
#   PATCH /api/books/{id}/   → partial_update
#   DELETE /api/books/{id}/  → destroy
router.register("books", BookViewSet)

urlpatterns = router.urls  # all six patterns from one line
python
from rest_framework.decorators import action

class BookViewSet(viewsets.ModelViewSet):
    queryset         = Book.objects.all()
    serializer_class = BookSerializer

    # @action adds a custom route outside the standard six
    # detail=True → /books/{id}/featured/  (for a specific book)
    # detail=False → /books/featured/       (not tied to an ID)
    @action(detail=False, methods=["get"])
    def featured(self, request):
        # Custom logic — return only highly-rated books
        featured_books = self.queryset.filter(rating__gte=4)
        serializer = self.get_serializer(featured_books, many=True)
        return Response(serializer.data)
    # Accessible at GET /api/books/featured/

Token Authentication

Token authentication is the standard way to protect a DRF API for non-browser clients like mobile apps or React frontends. When a user logs in, the server creates a Token object linked to their account and returns the token string. The client stores this string, usually in localStorage or a mobile keychain, and sends it as an Authorization header on every request after that. DRF reads this header, looks up the token in the database, and sets request.user automatically. DRF tokens do not expire by default, which keeps things simple. If you need expiring tokens, add the djangorestframework-simplejwt package, but a static token is fine for most projects.

python
# 1. Add 'rest_framework.authtoken' to INSTALLED_APPS (already shown in step 2)
# 2. Run migrations to create the token table
#    python manage.py migrate

# 3. Add a login view that returns a token
from rest_framework.authtoken.models import Token
from rest_framework.views import APIView
from rest_framework.response import Response
from django.contrib.auth import authenticate
from rest_framework import status
from rest_framework.permissions import AllowAny


class LoginView(APIView):
    permission_classes = [AllowAny]  # no auth required to log in

    def post(self, request):
        username = request.data.get("username")
        password = request.data.get("password")

        user = authenticate(username=username, password=password)
        if not user:
            return Response(
                {"error": "Invalid credentials"},
                status=status.HTTP_401_UNAUTHORIZED
            )

        # get_or_create returns (token, created_bool)
        # If the user already has a token, it returns the existing one
        token, _ = Token.objects.get_or_create(user=user)
        return Response({"token": token.key})
bash
# Step 1: log in and get a token
curl -X POST http://localhost:8000/api/login/ \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "password": "pass123"}'

# Response:
# { "token": "9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b" }

# Step 2: use the token on protected routes
# Format: "Token " + the token string (note: "Token", not "Bearer")
curl http://localhost:8000/api/books/ \
  -H "Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"

# Create a superuser for testing in the Django admin
python manage.py createsuperuser

Permissions — Controlling Access

DRF's permission system controls what logged-in and anonymous users are allowed to do. IsAuthenticated rejects any request without a valid token. IsAuthenticatedOrReadOnly lets anonymous users read with GET, but requires a token to create, update, or delete. IsAdminUser requires Django's is_staff flag to be True. You set defaults in REST_FRAMEWORK settings and override them per view when needed. For row-level rules like "users can only edit their own posts," you write a custom permission class that checks the object's owner in one place and reuse it across your views.

python
from rest_framework import permissions

# Apply globally in settings.py:
REST_FRAMEWORK = {
    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticatedOrReadOnly"
    ]
}

# Override per view or ViewSet:
class AdminOnlyView(APIView):
    permission_classes = [permissions.IsAdminUser]  # requires is_staff=True

class PublicView(APIView):
    permission_classes = [permissions.AllowAny]     # no auth required

class PrivateView(APIView):
    permission_classes = [permissions.IsAuthenticated]  # token required

# Combine multiple permissions — ALL must pass
class StrictView(APIView):
    permission_classes = [permissions.IsAuthenticated, permissions.IsAdminUser]
python
# books/permissions.py
from rest_framework import permissions


class IsOwnerOrReadOnly(permissions.BasePermission):
    """
    Allow read access to anyone.
    Allow write access only to the object's owner.
    """

    def has_object_permission(self, request, view, obj):
        # SAFE_METHODS = ("GET", "HEAD", "OPTIONS") — read-only
        if request.method in permissions.SAFE_METHODS:
            return True

        # Write access — only the user who created this book
        return obj.created_by == request.user


# Use it in a ViewSet:
class BookViewSet(viewsets.ModelViewSet):
    queryset         = Book.objects.all()
    serializer_class = BookSerializer
    permission_classes = [
        permissions.IsAuthenticatedOrReadOnly,  # must be logged in to write
        IsOwnerOrReadOnly                       # must own the book to edit/delete
    ]

The Browsable API

DRF comes with a browsable API that is enabled by default. When you open an API URL in a browser, DRF detects you are a human and renders a full interactive HTML page instead of raw JSON. The page shows the response data with syntax highlighting and includes a form for sending POST and PUT requests right from the browser, so you do not need curl or Postman during development. In production you usually disable it so users always receive plain JSON. You can toggle it by changing DEFAULT_RENDERER_CLASSES in your REST_FRAMEWORK settings.

python
# settings.py
import os

REST_FRAMEWORK = {
    # Development: show the browsable HTML API in browser, JSON for clients
    "DEFAULT_RENDERER_CLASSES": [
        "rest_framework.renderers.JSONRenderer",       # always available
        "rest_framework.renderers.BrowsableAPIRenderer",  # HTML in browser
    ],
}

# Production: JSON only — remove the browsable renderer
if os.getenv("ENVIRONMENT") == "production":
    REST_FRAMEWORK["DEFAULT_RENDERER_CLASSES"] = [
        "rest_framework.renderers.JSONRenderer"
    ]

# Now visit http://localhost:8000/api/books/ in your browser
# You'll see a fully interactive UI for your API
# Add the login URL to enable the "Log in" button in the browsable API:

# myapi/urls.py
urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/",   include("books.urls")),
    path("api-auth/", include("rest_framework.urls")),  # adds login/logout to browsable API
]

Connecting a JavaScript Frontend

A JavaScript frontend talks to your DRF API using the browser's fetch() function. The basic flow is: send a POST request to log in, save the token you get back, then attach it as an Authorization header on every request after that. You also need to add CORS headers to Django so the browser allows requests from a different origin. For example, if your frontend runs on localhost:3000 and your API runs on localhost:8000, the browser blocks requests between them unless CORS is configured. Install django-cors-headers and add your frontend URL to CORS_ALLOWED_ORIGINS.

python
# Install the CORS middleware
# pip install django-cors-headers

# settings.py
INSTALLED_APPS = [
    "corsheaders",  # add before your own apps
    "rest_framework",
    "books",
    ...
]

MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",  # must be FIRST in the list
    "django.middleware.common.CommonMiddleware",
    ...
]

# Allow requests from your frontend's origin
CORS_ALLOWED_ORIGINS = [
    "http://localhost:3000",    # React dev server
    "http://localhost:5173",    # Vite dev server
    "https://myapp.com",       # production frontend
]
javascript
const API = "http://localhost:8000/api";

// Step 1: log in and save the token
async function login(username, password) {
  const resp = await fetch(`${API}/login/`, {
    method:  "POST",
    headers: { "Content-Type": "application/json" },
    body:    JSON.stringify({ username, password })
  });
  const data = await resp.json();
  localStorage.setItem("token", data.token);  // store for later requests
}

// Step 2: helper that attaches the token to every request
function authHeaders() {
  const token = localStorage.getItem("token");
  return {
    "Authorization": `Token ${token}`,  // DRF uses "Token", not "Bearer"
    "Content-Type":  "application/json"
  };
}

// GET all books — works without a token (IsAuthenticatedOrReadOnly)
async function getBooks() {
  const resp = await fetch(`${API}/books/`);
  return resp.json();
}

// POST a new book — requires a token
async function createBook(title, author, published) {
  const resp = await fetch(`${API}/books/`, {
    method:  "POST",
    headers: authHeaders(),
    body:    JSON.stringify({ title, author, published })
  });
  if (!resp.ok) throw new Error("Failed to create book");
  return resp.json();
}
