Capstone 2: Company Knowledge Base RAG API

Upload internal documents and chat with them intelligently. This project teaches the full Retrieval-Augmented Generation pipeline: chunking text, generating embeddings, storing them in PostgreSQL with pgvector, running cosine similarity search at query time, injecting retrieved context into an LLM prompt, and streaming the answer token-by-token to the client.

1

How RAG Works

AI language models have a knowledge cutoff and a limit on how much text you can send them at once. They do not know about your company's internal documents, and even if you tried to paste all that content into one prompt, you would quickly exceed the limit. Retrieval-Augmented Generation (RAG) solves both problems. It turns your documents into a searchable database of meaning, then fetches only the relevant pieces at query time and sends those to the AI.

The key concept to understand is "embedding." An embedding is what you get when you take a piece of text and feed it through a neural network that converts it into a list of numbers. That list is called a vector. Texts with similar meanings produce vectors that are numerically close to each other. Texts with unrelated meanings produce vectors that are numerically far apart. This is why you can search your documents by meaning rather than by exact keywords.

The RAG pipeline has two phases. During the ingestion phase, done once per document, you split the document into chunks, turn each chunk into a vector, and store both the text and the vector in the database. During the query phase, done for each user question, you turn the question into a vector, find the chunks whose vectors are closest to it, and inject those chunks into the AI's prompt as context. The AI then answers using only the provided context, which keeps the response grounded in your documents.

Data flow in this project:
POST /documents → chunk text → embed each chunk → store in pgvector
POST /chat → embed question → cosine similarity search → top 5 chunks → LLM → StreamingResponse

Database Setup + pgvector

This project uses PostgreSQL with the pgvector extension. pgvector adds a VECTOR column type to PostgreSQL and lets you run distance operations like cosine similarity directly in SQL queries. You enable it once per database by running CREATE EXTENSION IF NOT EXISTS vector;. After that, SQLAlchemy can use the Vector(dimensions) type from the pgvector.sqlalchemy package to define vector columns in your models.

The number of dimensions must match the embedding model you choose. OpenAI's text-embedding-3-small produces 1536-dimensional vectors. If you use a local model like all-MiniLM-L6-v2, it produces 384 dimensions. You cannot mix dimensions in the same column, so pick one model and define the column size to match. This guide uses text-embedding-3-small and 1536 dimensions.

There are two database models. Document tracks each uploaded file, including its name, upload time, and owner. DocumentChunk stores the individual text fragments created during chunking. Each chunk has a foreign key linking it back to its parent Document and a column storing its embedding vector. When a Document is deleted, all its chunks are deleted automatically by the cascade rule on the relationship.

python
from sqlalchemy import Column, Integer, String, Text, DateTime, ForeignKey
from sqlalchemy.orm import relationship
from sqlalchemy.ext.declarative import declarative_base
from pgvector.sqlalchemy import Vector   # pip install pgvector
from datetime import datetime

Base = declarative_base()


class Document(Base):
    __tablename__ = "documents"

    id         = Column(Integer, primary_key=True)
    name       = Column(String)          # original filename from the upload
    owner_id   = Column(Integer)         # user who uploaded (from API key lookup)
    created_at = Column(DateTime, default=datetime.utcnow)

    # All chunks for this document — deleted automatically when document is deleted
    chunks     = relationship("DocumentChunk", back_populates="document", cascade="all, delete-orphan")


class DocumentChunk(Base):
    __tablename__ = "document_chunks"

    id          = Column(Integer, primary_key=True)
    document_id = Column(Integer, ForeignKey("documents.id"))  # which document this came from
    chunk_index = Column(Integer)        # position within the document (0, 1, 2, ...)
    text        = Column(Text)           # the raw text content of this chunk

    # The embedding vector — 1536 dimensions for text-embedding-3-small
    # This is the column pgvector adds — it stores a list of 1536 floats
    embedding   = Column(Vector(1536))

    document    = relationship("Document", back_populates="chunks")

    """
    Creates tables and enables pgvector extension.
    Call this once on startup — safe to call on an existing DB.

    # Enable the pgvector extension — required before creating VECTOR columns
    with engine.connect() as conn:
        conn.execute(text("CREATE EXTENSION IF NOT EXISTS vector"))
        conn.commit()
    # Now create tables (VECTOR column type is available after the extension is enabled)
    Base.metadata.create_all(bind=engine)


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

File Upload + Text Extraction

The document upload endpoint accepts text and PDF files. For plain text files, extraction is simple: read the bytes and decode them to a string. For PDF files, you need a library to read the PDF format and extract the text from each page. pypdf is a pure-Python library that does this without any system-level dependencies. It reads pages one at a time and joins their text together. PDFs created from Word documents or LaTeX extract cleanly. Scanned PDFs, where the text is actually an image, will produce empty or garbled output because there are no real characters to extract.

After extraction, the route passes the text to the chunking function and then to the embedding and storage pipeline. The whole process runs synchronously and can take a few seconds for large documents. This is a reasonable trade-off because uploads are infrequent and users expect a short wait. For very large documents or many concurrent users, you could move the chunking and embedding into a BackgroundTask, as covered in Capstone 1.

python
from fastapi import FastAPI, UploadFile, File, Depends, HTTPException
from sqlalchemy.orm import Session

from database import get_db, init_db
from models import Document, DocumentChunk
from middleware.api_key import verify_api_key, get_user_id_from_key
from services.extractor import extract_text
from services.chunker import chunk_text
from services.embedder import embed_texts

app = FastAPI(title="Knowledge Base RAG API")

@app.on_event("startup")
def startup():
    init_db()  # enables pgvector extension + creates tables


@app.post("/documents", dependencies=[Depends(verify_api_key)])
async def upload_document(
    file: UploadFile = File(...),
    db: Session = Depends(get_db)
):
    # Validate file type — only accept .txt and .pdf
    allowed = ["text/plain", "application/pdf"]
    if file.content_type not in allowed:
        raise HTTPException(status_code=400, detail="Only .txt and .pdf files are accepted.")

    # Read the file bytes and extract text
    file_bytes = await file.read()
    text = extract_text(file_bytes, file.content_type)

    if not text.strip():
        raise HTTPException(status_code=422, detail="Could not extract text from this file.")

    # Create a Document record
    doc = Document(name=file.filename, owner_id=1)  # owner_id from API key in production
    db.add(doc)
    db.flush()  # flush to get doc.id without committing yet

    # Chunk the extracted text into overlapping fragments
    chunks = chunk_text(text)

    # Embed all chunks in one API call (more efficient than one call per chunk)
    vectors = embed_texts(chunks)

    # Save each chunk + its vector as a DocumentChunk row
    for i, (chunk, vector) in enumerate(zip(chunks, vectors)):
        db.add(DocumentChunk(
            document_id=doc.id,
            chunk_index=i,
            text=chunk,
            embedding=vector  # pgvector stores this list of floats as a VECTOR
        ))

    db.commit()
    return {"document_id": doc.id, "chunks_created": len(chunks)}
python
import io
from pypdf import PdfReader   # pip install pypdf


def extract_text(file_bytes: bytes, content_type: str) -> str:
    """
    Extracts plain text from a file's bytes, based on content type.
    Returns a single string of all the text content.
    """
    if content_type == "text/plain":
        # Plain text — just decode the bytes to a string
        # errors="replace" handles files with unusual encodings gracefully
        return file_bytes.decode("utf-8", errors="replace")

    elif content_type == "application/pdf":
        # PDF — use pypdf to read pages and extract text from each one
        reader = PdfReader(io.BytesIO(file_bytes))  # wrap bytes in a file-like object
        pages = []
        for page in reader.pages:
            page_text = page.extract_text()
            if page_text:
                pages.append(page_text)
        # Join all pages with a newline between them
        return "\n".join(pages)

    return ""  # unsupported type — caller checks for empty string

Text Chunking

Chunking is the process of splitting a document into smaller pieces before turning them into vectors. You cannot embed an entire 50-page document as one vector. The embedding model has a token limit, and a single vector for an entire document would be too broad to retrieve specific passages accurately. A chunk should be large enough to contain one focused idea and small enough to be specific, roughly a paragraph or two.

The most important parameter is overlap. If you split a document into perfectly non-overlapping chunks, you will sometimes cut through sentences or ideas at the boundaries. A question about content that spans two chunks will only retrieve half the relevant context. Overlap solves this by repeating some characters at the start of each new chunk. This ensures that boundary content appears fully in at least one chunk. A typical overlap is 10 to 15 percent of the chunk size.

This guide uses a simple character-based splitter, which works well for structured text documents. More advanced approaches like sentence-aware splitting or paragraph-aware splitting produce better results but are more complex to build. Master the simple approach first and improve it later as a natural upgrade.

python
from typing import List


def chunk_text(
    text: str,
    chunk_size: int = 400,    # characters per chunk — tune based on your documents
    overlap: int = 50         # characters shared between consecutive chunks
) -> List[str]:
    """
    Splits text into overlapping chunks.
    Returns a list of strings, each of length approximately chunk_size.
    """
    # Normalise whitespace — collapse multiple spaces/newlines to single spaces
    text = " ".join(text.split())

    chunks = []
    start = 0

    while start < len(text):
        end = start + chunk_size

        # Try to break at a word boundary — find the last space before the end
        # This avoids cutting a word in the middle of a chunk
        if end < len(text):
            last_space = text.rfind(" ", start, end)
            if last_space > start:   # found a space within the chunk range
                end = last_space

        chunk = text[start:end].strip()
        if chunk:               # skip empty chunks (can happen at end of text)
            chunks.append(chunk)

        # Next chunk starts (chunk_size - overlap) characters after current start
        # The overlap means the next chunk shares 'overlap' chars with the current one
        start += chunk_size - overlap

    return chunks

Generating Embeddings

Generating an embedding means sending text to the OpenAI embeddings API and getting back a list of numbers. This is different from the chat completions API. There is no prompt, no system message, and no temperature setting. You send text in and get a vector out. The vector always has the same number of dimensions regardless of how long the input is. A single word and a three-paragraph excerpt both produce a 1536-dimensional vector.

The most important efficiency tip is to batch your embedding calls. Instead of sending one API request per chunk, which could mean over 100 calls for a single document, send all chunks in one call as a list. The OpenAI embeddings endpoint accepts a list of strings and returns a list of vectors in the same order. This is dramatically faster and cheaper than embedding one chunk at a time. The model handles batches of up to 2048 inputs per call, which is well beyond what most documents need.

python
import os
from typing import List
from openai import OpenAI
from tenacity import retry, wait_exponential, stop_after_attempt

client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

EMBEDDING_MODEL = "text-embedding-3-small"  # produces 1536-dimensional vectors
EMBEDDING_DIMS  = 1536                       # must match the Vector(1536) in models.py


@retry(wait=wait_exponential(multiplier=1, min=1, max=30), stop=stop_after_attempt(3))
def embed_texts(texts: List[str]) -> List[List[float]]:
    """
    Embeds a list of strings in a single API call.
    Returns a list of vectors in the same order as the input.
    Uses tenacity to retry on rate limit errors.
    """
    if not texts:
        return []

    # Send all texts in one call — far more efficient than one call per text
    response = client.embeddings.create(
        model=EMBEDDING_MODEL,
        input=texts,            # list of strings — returns a list of vectors
    )

    # Response.data is a list of Embedding objects, each with .embedding (list of floats)
    # Sort by index to ensure order matches input (API guarantees this but be safe)
    return [item.embedding for item in sorted(response.data, key=lambda x: x.index)]


def embed_query(text: str) -> List[float]:
    """Convenience wrapper for embedding a single query string."""
    return embed_texts([text])[0]
python
import random
from typing import List

EMBEDDING_DIMS = 1536


def embed_texts(texts: List[str]) -> List[List[float]]:
    """
    Mock embedder — returns random vectors of the correct dimension.
    Use this while building the pipeline to avoid OpenAI API costs.
    WARNING: similarity search will produce random results with mock vectors.
    Replace with the real embedder once the pipeline structure is correct.
    """
    return [
        [random.uniform(-1, 1) for _ in range(EMBEDDING_DIMS)]
        for _ in texts
    ]


def embed_query(text: str) -> List[float]:
    return embed_texts([text])[0]

Storing Vectors in PostgreSQL

Storing vectors is straightforward. You assign the list of floats directly to the embedding column of a DocumentChunk model, and SQLAlchemy with pgvector handles the rest. Under the hood, pgvector stores vectors as compact binary arrays and supports index types for fast similarity search. For most applications, an HNSW index dramatically speeds up search on large datasets.

For your first build, you do not need an index. A linear scan over a few thousand chunks is fast enough. Once you have tens of thousands of chunks, you would add an HNSW index with a single SQL statement. The index is transparent to your application code. You query the same way with or without it. This guide includes the index creation command for completeness, but you can skip it during development and add it before deploying.

python
# This is the saving portion of the upload route from Step 3 — shown in isolation for clarity

# After chunking and embedding:
chunks  = chunk_text(extracted_text)   # List[str]
vectors = embed_texts(chunks)          # List[List[float]] — same length as chunks

# Save each chunk + its vector — zip pairs each chunk with its corresponding vector
for i, (chunk_text_content, vector) in enumerate(zip(chunks, vectors)):
    chunk = DocumentChunk(
        document_id=doc.id,           # which document this came from
        chunk_index=i,                 # position within the document
        text=chunk_text_content,       # the raw text — returned to the LLM as context
        embedding=vector               # the 1536-float list — used for similarity search
    )
    db.add(chunk)

db.commit()  # commit all chunks at once — faster than committing per chunk

# To verify what was stored:
stored = db.query(DocumentChunk).filter(DocumentChunk.document_id == doc.id).all()
for c in stored[:3]:
    print(f"Chunk {c.chunk_index}: {c.text[:60]}... | vector dims: {len(c.embedding)}")
sql
-- Create an HNSW index for fast approximate nearest-neighbor search
-- Run this AFTER populating the table with data
-- cosine_ops = use cosine distance for similarity (matches our search query)
CREATE INDEX ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- m = 16: number of bidirectional connections per node (higher = better recall, more memory)
-- ef_construction = 64: search width during index build (higher = better accuracy, slower build)

-- To check the index was created:
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'document_chunks';

-- No code changes needed — queries using <-> automatically use the index

Cosine Similarity Search

At query time, you convert the user's question into a vector using the same embedding model used during ingestion. You must use exactly the same model. Embedding models do not produce compatible vector spaces with each other, so comparing a vector from one model against vectors from a different model produces meaningless results.

Once you have the query vector, you use pgvector's <-> operator to measure cosine distance between the query vector and every chunk vector in the database. Cosine distance measures how similar the meaning of two pieces of text is. A distance of 0 means identical meaning. A distance of 1 means completely unrelated. You order the results by distance and take the top 5 closest chunks. These are the chunks you inject into the AI's prompt as context.

python
from typing import List
from sqlalchemy.orm import Session
from pgvector.sqlalchemy import Vector

from models import DocumentChunk
from services.embedder import embed_query


def retrieve_relevant_chunks(
    question: str,
    db: Session,
    top_k: int = 5    # how many chunks to retrieve — 5 is a good starting point
) -> List[DocumentChunk]:
    """
    Converts the question to a vector, then finds the top_k most similar chunks
    using cosine distance. Returns the chunk objects (which contain .text).
    """
    # Step 1: Embed the question — same model as used during ingestion
    query_vector = embed_query(question)  # returns a list of 1536 floats

    # Step 2: Query PostgreSQL using the <-> cosine distance operator
    # .order_by(DocumentChunk.embedding.cosine_distance(query_vector)) means:
    # "sort chunks by how close their vector is to the query vector"
    # .limit(top_k) returns only the top_k closest chunks
    results = (
        db.query(DocumentChunk)
        .order_by(DocumentChunk.embedding.cosine_distance(query_vector))
        .limit(top_k)
        .all()
    )

    return results  # List of DocumentChunk objects — use .text for the content
sql
-- This is what SQLAlchemy generates under the hood.
-- The <-> operator is pgvector's cosine distance.
-- '[0.1, 0.2, ...]'::vector casts the Python list to a pgvector VECTOR type.

SELECT id, document_id, chunk_index, text,
       embedding <-> '[0.1, 0.2, 0.3, ...]'::vector AS distance
FROM document_chunks
ORDER BY distance ASC
LIMIT 5;

-- distance of 0.0 = identical meaning
-- distance of 1.0 = completely unrelated
-- Typical good matches have distance < 0.3

The Chat Endpoint

The chat endpoint ties everything together. It receives the user's question, retrieves the relevant chunks, builds a prompt that includes those chunks as context, calls the AI, and returns the answer. The most important part is the system prompt. You tell the AI that it must answer using only the provided context and must not use any general knowledge. This is called "grounding" the AI. It prevents the AI from making up facts that are not in your documents.

The format you use to inject context also matters. Each chunk is numbered and labelled with its source document name. This lets the AI attribute its answers clearly, for example by saying "According to the HR Policy document, ..." It also gives you a numbered reference if you want to show users which document a fact came from.

python
from pydantic import BaseModel
import os
from openai import OpenAI

from services.retriever import retrieve_relevant_chunks

openai_client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


class ChatRequest(BaseModel):
    question: str    # the user's question


@app.post("/chat", dependencies=[Depends(verify_api_key)])
async def chat(
    body: ChatRequest,
    db: Session = Depends(get_db)
):
    # Step 1: Retrieve the top 5 most relevant chunks
    chunks = retrieve_relevant_chunks(body.question, db, top_k=5)

    if not chunks:
        return {"answer": "No documents have been uploaded yet. Please upload documents first."}

    # Step 2: Build the context string from retrieved chunk texts
    context_parts = []
    for i, chunk in enumerate(chunks, 1):
        # Include document name so the LLM can cite sources
        doc_name = chunk.document.name if chunk.document else "Unknown"
        context_parts.append(f"[{i}] From '{doc_name}':\n{chunk.text}")

    context = "\n\n".join(context_parts)

    # Step 3: Build the system prompt — "grounding" the LLM to only use the context
    system_prompt = f"""You are a helpful assistant for this company's knowledge base.
Answer the user's question using ONLY the context provided below.
If the answer is not in the context, say "I don't have information about that in the uploaded documents."
Do not use any knowledge outside the provided context.

CONTEXT:
{context}"""

    # Step 4: Call the LLM and return the full response
    response = openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": body.question},
        ],
        max_tokens=500,
        temperature=0.1,  # low temperature = more factual, less creative
    )

    answer = response.choices[0].message.content
    return {"answer": answer, "sources_used": len(chunks)}

StreamingResponse

The full-response approach in Step 8 waits for the AI to generate the entire answer before sending anything to the client. For short answers that is fine, but for longer responses the user may stare at a blank screen for five to ten seconds. Streaming fixes this by sending each word to the client as soon as the AI generates it, the same way ChatGPT works.

In FastAPI, streaming uses a StreamingResponse with an async generator. An async generator is a function defined with async def that uses yield instead of return. Each time it yields a piece of text, FastAPI sends that piece to the client immediately without waiting for the rest to finish. You enable streaming on the OpenAI API by passing stream=True to the completions call. This changes the response into an iterator of small text fragments that arrive one at a time.

The client that calls your streaming endpoint receives a plain text response that arrives in fragments. In a browser, you would use the Fetch API with response.body.getReader() to read the stream. In curl, you would see text appearing word by word. The client needs to know it is receiving a stream, not a complete response, and handle the partial data as it arrives.

python
from fastapi import FastAPI, Depends
from fastapi.responses import StreamingResponse
from sqlalchemy.orm import Session
import os
from openai import OpenAI

from services.retriever import retrieve_relevant_chunks

openai_client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


@app.post("/chat/stream", dependencies=[Depends(verify_api_key)])
async def chat_stream(
    body: ChatRequest,
    db: Session = Depends(get_db)
):
    chunks = retrieve_relevant_chunks(body.question, db, top_k=5)

    if not chunks:
        async def empty():
            yield "No documents uploaded yet."
        return StreamingResponse(empty(), media_type="text/plain")

    context = "\n\n".join(
        f"[{i}] From '{c.document.name}':\n{c.text}"
        for i, c in enumerate(chunks, 1)
    )

    system_prompt = f"""You are a helpful knowledge base assistant.
Answer using ONLY the context below. If the answer isn't there, say so.

CONTEXT:
{context}"""

    async def generate():
        """
        Async generator — yields text chunks as the LLM produces them.
        FastAPI's StreamingResponse calls this generator and sends each
        yielded string to the client immediately.
        """
        # stream=True makes the OpenAI call return an iterator of delta chunks
        stream = openai_client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user",   "content": body.question},
            ],
            max_tokens=500,
            temperature=0.1,
            stream=True,   # THIS is what enables streaming
        )

        # Iterate over delta chunks as the LLM generates them
        for chunk in stream:
            delta = chunk.choices[0].delta
            if delta.content:              # some deltas are empty (start/end markers)
                yield delta.content         # send this token fragment to the client NOW

    # StreamingResponse takes the async generator and streams each yielded string
    # media_type="text/plain" — client receives a stream of plain text
    return StreamingResponse(generate(), media_type="text/plain")

// Browser JS — read the stream and append tokens to the page as they arrive
async function chatStream(question) {
  const response = await fetch("/chat/stream", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-API-Key": "YOUR_API_KEY"
    },
    body: JSON.stringify({ question })
  });

  const reader = response.body.getReader();    // get the stream reader
  const decoder = new TextDecoder();           // convert bytes to string
  const output = document.getElementById("answer");

  output.textContent = "";  // clear previous answer

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;                             // stream ended
    output.textContent += decoder.decode(value); // append new tokens as they arrive
  }
}

Auth + Testing

The same X-API-Key middleware from Capstone 1 protects all endpoints here. The middleware reads the header, hashes it with bcrypt, and checks it against the database. You can reuse the create_api_key.py script from Capstone 1 exactly as-is because the APIKey model is identical.

Testing the RAG pipeline requires mocking both the embedder and the AI. You do not want tests to make real API calls. Real calls are slow, cost money, and produce different results each time. Mock the embedder to return fixed vectors, mock the AI response, and verify that documents are stored with the correct number of chunks and that the chat route returns an answer. You cannot easily test whether an answer is semantically correct in a unit test. That kind of check is done manually with real data.
