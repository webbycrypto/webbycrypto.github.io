Capstone 2: Company Knowledge Base RAG API

Upload internal documents and chat with them intelligently. This project teaches the full Retrieval-Augmented Generation pipeline: chunking text, generating embeddings, storing them in PostgreSQL with pgvector, running cosine similarity search at query time, injecting retrieved context into an LLM prompt, and streaming the answer token-by-token to the client.

1

How RAG Works

Large language models have a knowledge cutoff and a context window limit. They don't know about your company's internal documents — your HR policies, your product manuals, your support runbooks — and even if you tried to paste all that content into a single prompt, you'd quickly exceed the token limit. Retrieval-Augmented Generation (RAG) solves both problems by turning your documents into a searchable database of meaning, then fetching only the relevant pieces at query time to inject into the LLM's context.

The word "embedding" is the key concept to understand. An embedding is what you get when you take a piece of text — a sentence, a paragraph, a document chunk — and feed it through a neural network that converts it into a list of hundreds or thousands of numbers. This list of numbers is called a vector, and it encodes the semantic meaning of the text. Texts with similar meanings produce vectors that are numerically close to each other. Texts with unrelated meanings produce vectors that are numerically distant. This is why you can search a corpus by meaning rather than by keywords — instead of looking for exact word matches, you find semantically similar text.

The RAG pipeline has two phases. The ingestion phase (done once per document): split the document into chunks → embed each chunk → store the chunk text and its vector in the database. The query phase (done per user question): embed the question → find the top-k chunks whose vectors are closest to the question vector → inject those chunks as context into the LLM prompt → the LLM answers using only the provided context. Because you only inject the most relevant chunks, you stay well within the token limit and the LLM's answer is grounded in your documents.

Data flow in this project:
POST /documents → chunk text → embed each chunk → store in pgvector
POST /chat → embed question → cosine similarity search → top 5 chunks → LLM → StreamingResponse

Database Setup + pgvector

This project uses PostgreSQL with the pgvector extension. pgvector adds a native VECTOR column type to PostgreSQL and implements distance operations including cosine similarity, Euclidean distance, and inner product. You install it once per PostgreSQL database by running CREATE EXTENSION IF NOT EXISTS vector;. After that, SQLAlchemy can use the Vector(dimensions) type from the pgvector.sqlalchemy package to define vector columns in your models.

The dimension count must match the embedding model you use. OpenAI's text-embedding-3-small produces 1536-dimensional vectors. OpenAI's text-embedding-3-large produces 3072. If you use a local model like all-MiniLM-L6-v2 from sentence-transformers, it produces 384-dimensional vectors. You cannot mix dimensions in the same column — pick a model and define the column size accordingly. This guide uses text-embedding-3-small and 1536 dimensions.

There are two models. Document tracks each uploaded file — its name, when it was uploaded, and who owns it. DocumentChunk stores the individual text fragments created by chunking, with a foreign key to the parent Document and the embedding vector. When a document is deleted, its chunks are deleted automatically by the cascade rule on the relationship.

python
from sqlalchemy import Column, Integer, String, Text, DateTime, ForeignKey
from sqlalchemy.orm import relationship
from sqlalchemy.ext.declarative import declarative_base
from pgvector.sqlalchemy import Vector   # pip install pgvector
from datetime import datetime

Base = declarative_base()


class Document(Base):
    __tablename__ = "documents"

    id         = Column(Integer, primary_key=True)
    name       = Column(String)          # original filename from the upload
    owner_id   = Column(Integer)         # user who uploaded (from API key lookup)
    created_at = Column(DateTime, default=datetime.utcnow)

    # All chunks for this document — deleted automatically when document is deleted
    chunks     = relationship("DocumentChunk", back_populates="document", cascade="all, delete-orphan")


class DocumentChunk(Base):
    __tablename__ = "document_chunks"

    id          = Column(Integer, primary_key=True)
    document_id = Column(Integer, ForeignKey("documents.id"))  # which document this came from
    chunk_index = Column(Integer)        # position within the document (0, 1, 2, ...)
    text        = Column(Text)           # the raw text content of this chunk

    # The embedding vector — 1536 dimensions for text-embedding-3-small
    # This is the column pgvector adds — it stores a list of 1536 floats
    embedding   = Column(Vector(1536))

    document    = relationship("Document", back_populates="chunks")

    """
    Creates tables and enables pgvector extension.
    Call this once on startup — safe to call on an existing DB.
    """
    from models import Base
    # Enable the pgvector extension — required before creating VECTOR columns
    with engine.connect() as conn:
        conn.execute(text("CREATE EXTENSION IF NOT EXISTS vector"))
        conn.commit()
    # Now create tables (VECTOR column type is available after the extension is enabled)
    Base.metadata.create_all(bind=engine)


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

File Upload + Text Extraction

The document upload endpoint accepts text and PDF files. For plain text files (.txt), extraction is trivial: read the bytes and decode to a string. For PDF files, you need a library that can parse the PDF binary format and extract the text from each page. pypdf is a pure-Python library that does this without any system-level dependencies — it reads pages one at a time and joins their text content. The quality of text extraction from PDFs varies: PDFs with real text (generated from Word, LaTeX, etc.) extract cleanly. Scanned image PDFs produce garbage or nothing, because the text is an image, not actual characters.

After extraction, the route passes the text to the chunking function, then to the embedding and storage pipeline. The whole process can take a few seconds for large documents, but it runs synchronously here — it's a reasonable trade-off because document upload is not a frequent operation and users expect it to take a moment. If you have very large documents or very many concurrent users, you'd move the chunking and embedding into a BackgroundTask (which you now know how to do from Capstone 1).

python
from fastapi import FastAPI, UploadFile, File, Depends, HTTPException
from sqlalchemy.orm import Session

from database import get_db, init_db
from models import Document, DocumentChunk
from middleware.api_key import verify_api_key, get_user_id_from_key
from services.extractor import extract_text
from services.chunker import chunk_text
from services.embedder import embed_texts

app = FastAPI(title="Knowledge Base RAG API")

@app.on_event("startup")
def startup():
    init_db()  # enables pgvector extension + creates tables


@app.post("/documents", dependencies=[Depends(verify_api_key)])
async def upload_document(
    file: UploadFile = File(...),
    db: Session = Depends(get_db)
):
    # Validate file type — only accept .txt and .pdf
    allowed = ["text/plain", "application/pdf"]
    if file.content_type not in allowed:
        raise HTTPException(status_code=400, detail="Only .txt and .pdf files are accepted.")

    # Read the file bytes and extract text
    file_bytes = await file.read()
    text = extract_text(file_bytes, file.content_type)

    if not text.strip():
        raise HTTPException(status_code=422, detail="Could not extract text from this file.")

    # Create a Document record
    doc = Document(name=file.filename, owner_id=1)  # owner_id from API key in production
    db.add(doc)
    db.flush()  # flush to get doc.id without committing yet

    # Chunk the extracted text into overlapping fragments
    chunks = chunk_text(text)

    # Embed all chunks in one API call (more efficient than one call per chunk)
    vectors = embed_texts(chunks)

    # Save each chunk + its vector as a DocumentChunk row
    for i, (chunk, vector) in enumerate(zip(chunks, vectors)):
        db.add(DocumentChunk(
            document_id=doc.id,
            chunk_index=i,
            text=chunk,
            embedding=vector  # pgvector stores this list of floats as a VECTOR
        ))

    db.commit()
    return {"document_id": doc.id, "chunks_created": len(chunks)}
python
import io
from pypdf import PdfReader   # pip install pypdf


def extract_text(file_bytes: bytes, content_type: str) -> str:
    """
    Extracts plain text from a file's bytes, based on content type.
    Returns a single string of all the text content.
    """
    if content_type == "text/plain":
        # Plain text — just decode the bytes to a string
        # errors="replace" handles files with unusual encodings gracefully
        return file_bytes.decode("utf-8", errors="replace")

    elif content_type == "application/pdf":
        # PDF — use pypdf to read pages and extract text from each one
        reader = PdfReader(io.BytesIO(file_bytes))  # wrap bytes in a file-like object
        pages = []
        for page in reader.pages:
            page_text = page.extract_text()
            if page_text:
                pages.append(page_text)
        # Join all pages with a newline between them
        return "\n".join(pages)

    return ""  # unsupported type — caller checks for empty string

Text Chunking

Chunking is the process of splitting a document into smaller pieces before embedding. You can't embed an entire 50-page document as a single vector — the embedding model has a token limit (typically 8192 tokens for OpenAI's models), and even within that limit, a single vector for an entire document would be too coarse to retrieve specific passages accurately. A chunk should be small enough to contain one focused idea — a paragraph or two — but large enough to provide meaningful context to the LLM when retrieved.

The most important parameter is overlap. If you split a document into perfectly non-overlapping chunks, you'll inevitably cut through sentences or ideas at the boundaries. A question about content that spans a chunk boundary will retrieve a chunk containing only half the relevant context. Overlap solves this by duplicating some characters at the beginning of each chunk, ensuring that boundary content appears in at least one chunk fully. A typical overlap is 10–15% of the chunk size — so for 400-character chunks, a 50-character overlap is reasonable.

This guide uses a simple character-based splitter, which works well for structured text documents. More sophisticated approaches — sentence-aware splitting, paragraph-aware splitting, semantic chunking — produce better retrieval quality but are significantly more complex to implement. Master the simple approach first; improving it is a natural v2 upgrade.

python
from typing import List


def chunk_text(
    text: str,
    chunk_size: int = 400,    # characters per chunk — tune based on your documents
    overlap: int = 50         # characters shared between consecutive chunks
) -> List[str]:
    """
    Splits text into overlapping chunks.
    Returns a list of strings, each of length approximately chunk_size.
    """
    # Normalise whitespace — collapse multiple spaces/newlines to single spaces
    text = " ".join(text.split())

    chunks = []
    start = 0

    while start < len(text):
        end = start + chunk_size

        # Try to break at a word boundary — find the last space before the end
        # This avoids cutting a word in the middle of a chunk
        if end < len(text):
            last_space = text.rfind(" ", start, end)
            if last_space > start:   # found a space within the chunk range
                end = last_space

        chunk = text[start:end].strip()
        if chunk:               # skip empty chunks (can happen at end of text)
            chunks.append(chunk)

        # Next chunk starts (chunk_size - overlap) characters after current start
        # The overlap means the next chunk shares 'overlap' chars with the current one
        start += chunk_size - overlap

    return chunks

Generating Embeddings

Generating embeddings means calling the OpenAI embeddings API with your text and getting back a list of floats. The key difference from the chat completions API you've used before is that this returns numbers, not words. There's no prompt, no system message, no temperature — just text in, vector out. The vector always has the same number of dimensions regardless of how long or short the input text is. A single word and a three-paragraph excerpt both produce a 1536-dimensional vector.

The most important efficiency tip: batch your embedding calls. Instead of sending one API request per chunk (which could mean 100+ API calls for a single document), send all chunks in a single call using the list format. The OpenAI embeddings endpoint accepts a list of strings and returns a list of vectors in the same order. This reduces API call overhead dramatically and is significantly faster and cheaper than embedding chunks one at a time. The model handles batches up to 2048 inputs per call — well beyond what most documents need.

python
import os
from typing import List
from openai import OpenAI
from tenacity import retry, wait_exponential, stop_after_attempt

client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

EMBEDDING_MODEL = "text-embedding-3-small"  # produces 1536-dimensional vectors
EMBEDDING_DIMS  = 1536                       # must match the Vector(1536) in models.py


@retry(wait=wait_exponential(multiplier=1, min=1, max=30), stop=stop_after_attempt(3))
def embed_texts(texts: List[str]) -> List[List[float]]:
    """
    Embeds a list of strings in a single API call.
    Returns a list of vectors in the same order as the input.
    Uses tenacity to retry on rate limit errors.
    """
    if not texts:
        return []

    # Send all texts in one call — far more efficient than one call per text
    response = client.embeddings.create(
        model=EMBEDDING_MODEL,
        input=texts,            # list of strings — returns a list of vectors
    )

    # Response.data is a list of Embedding objects, each with .embedding (list of floats)
    # Sort by index to ensure order matches input (API guarantees this but be safe)
    return [item.embedding for item in sorted(response.data, key=lambda x: x.index)]


def embed_query(text: str) -> List[float]:
    """Convenience wrapper for embedding a single query string."""
    return embed_texts([text])[0]
python
import random
from typing import List

EMBEDDING_DIMS = 1536


def embed_texts(texts: List[str]) -> List[List[float]]:
    """
    Mock embedder — returns random vectors of the correct dimension.
    Use this while building the pipeline to avoid OpenAI API costs.
    WARNING: similarity search will produce random results with mock vectors.
    Replace with the real embedder once the pipeline structure is correct.
    """
    return [
        [random.uniform(-1, 1) for _ in range(EMBEDDING_DIMS)]
        for _ in texts
    ]


def embed_query(text: str) -> List[float]:
    return embed_texts([text])[0]

Storing Vectors in PostgreSQL

Storing the vectors is straightforward — you assign the list of floats directly to the embedding column of a DocumentChunk model, and SQLAlchemy + pgvector handles the rest. What's worth understanding is what pgvector actually stores and how it indexes it. Under the hood, pgvector stores vectors as compact binary arrays and provides several index types for fast similarity search. For most applications, an IVFFlat index or HNSW index dramatically speeds up search on large datasets.

For your first build, you don't need an index — a brute-force linear scan over a few thousand chunks is fast enough. At tens of thousands of chunks, you'd add an HNSW index. The index is created with a single SQL statement after populating the table, and it's transparent to the application code — you query the same way with or without it. This guide includes the index creation command for completeness, but you can skip it while developing and add it before deploying.

python
# This is the saving portion of the upload route from Step 3 — shown in isolation for clarity

# After chunking and embedding:
chunks  = chunk_text(extracted_text)   # List[str]
vectors = embed_texts(chunks)          # List[List[float]] — same length as chunks

# Save each chunk + its vector — zip pairs each chunk with its corresponding vector
for i, (chunk_text_content, vector) in enumerate(zip(chunks, vectors)):
    chunk = DocumentChunk(
        document_id=doc.id,           # which document this came from
        chunk_index=i,                 # position within the document
        text=chunk_text_content,       # the raw text — returned to the LLM as context
        embedding=vector               # the 1536-float list — used for similarity search
    )
    db.add(chunk)

db.commit()  # commit all chunks at once — faster than committing per chunk

# To verify what was stored:
stored = db.query(DocumentChunk).filter(DocumentChunk.document_id == doc.id).all()
for c in stored[:3]:
    print(f"Chunk {c.chunk_index}: {c.text[:60]}... | vector dims: {len(c.embedding)}")
sql
-- Create an HNSW index for fast approximate nearest-neighbor search
-- Run this AFTER populating the table with data
-- cosine_ops = use cosine distance for similarity (matches our search query)
CREATE INDEX ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- m = 16: number of bidirectional connections per node (higher = better recall, more memory)
-- ef_construction = 64: search width during index build (higher = better accuracy, slower build)

-- To check the index was created:
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'document_chunks';

-- No code changes needed — queries using <-> automatically use the index

Cosine Similarity Search

At query time, you convert the user's question into a vector using the same embedding model used during ingestion. This is critical — you must use exactly the same model, because embedding models don't produce compatible vector spaces. A vector from text-embedding-3-small is numerically meaningless if compared against vectors from a different model.

Once you have the query vector, you use pgvector's <-> operator to measure cosine distance between the query vector and every chunk vector in the database. Cosine distance measures the angle between two vectors in high-dimensional space — a distance of 0 means the vectors point in exactly the same direction (identical meaning), and a distance of 1 means they're maximally different. You order by distance ascending and take the top 5 results: the 5 chunks whose meaning is closest to the user's question. These are the chunks you'll inject into the LLM's context.

python
from typing import List
from sqlalchemy.orm import Session
from pgvector.sqlalchemy import Vector

from models import DocumentChunk
from services.embedder import embed_query


def retrieve_relevant_chunks(
    question: str,
    db: Session,
    top_k: int = 5    # how many chunks to retrieve — 5 is a good starting point
) -> List[DocumentChunk]:
    """
    Converts the question to a vector, then finds the top_k most similar chunks
    using cosine distance. Returns the chunk objects (which contain .text).
    """
    # Step 1: Embed the question — same model as used during ingestion
    query_vector = embed_query(question)  # returns a list of 1536 floats

    # Step 2: Query PostgreSQL using the <-> cosine distance operator
    # .order_by(DocumentChunk.embedding.cosine_distance(query_vector)) means:
    # "sort chunks by how close their vector is to the query vector"
    # .limit(top_k) returns only the top_k closest chunks
    results = (
        db.query(DocumentChunk)
        .order_by(DocumentChunk.embedding.cosine_distance(query_vector))
        .limit(top_k)
        .all()
    )

    return results  # List of DocumentChunk objects — use .text for the content
sql
-- This is what SQLAlchemy generates under the hood.
-- The <-> operator is pgvector's cosine distance.
-- '[0.1, 0.2, ...]'::vector casts the Python list to a pgvector VECTOR type.

SELECT id, document_id, chunk_index, text,
       embedding <-> '[0.1, 0.2, 0.3, ...]'::vector AS distance
FROM document_chunks
ORDER BY distance ASC
LIMIT 5;

-- distance of 0.0 = identical meaning
-- distance of 1.0 = completely unrelated
-- Typical good matches have distance < 0.3

The Chat Endpoint

The chat endpoint ties everything together. It receives the user's question, retrieves the relevant chunks, constructs a prompt that includes those chunks as context, calls the LLM, and returns the answer. The prompt structure is the most important part to get right. You tell the LLM in the system prompt that it must answer using only the provided context — it should not use any general knowledge. This is called "grounding" the LLM, and it's what makes RAG reliable for enterprise use: the LLM can't hallucinate facts that aren't in the documents, because you've explicitly told it not to use anything else.

The context injection format matters too. Each chunk is numbered and presented clearly, so if you decide to add citation (telling the user which document a fact came from), you have a numbered reference to work with. A good format includes the document name alongside each chunk, so the LLM can attribute its answer: "According to the HR Policy document, ..."

python
from pydantic import BaseModel
import os
from openai import OpenAI

from services.retriever import retrieve_relevant_chunks

openai_client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


class ChatRequest(BaseModel):
    question: str    # the user's question


@app.post("/chat", dependencies=[Depends(verify_api_key)])
async def chat(
    body: ChatRequest,
    db: Session = Depends(get_db)
):
    # Step 1: Retrieve the top 5 most relevant chunks
    chunks = retrieve_relevant_chunks(body.question, db, top_k=5)

    if not chunks:
        return {"answer": "No documents have been uploaded yet. Please upload documents first."}

    # Step 2: Build the context string from retrieved chunk texts
    context_parts = []
    for i, chunk in enumerate(chunks, 1):
        # Include document name so the LLM can cite sources
        doc_name = chunk.document.name if chunk.document else "Unknown"
        context_parts.append(f"[{i}] From '{doc_name}':\n{chunk.text}")

    context = "\n\n".join(context_parts)

    # Step 3: Build the system prompt — "grounding" the LLM to only use the context
    system_prompt = f"""You are a helpful assistant for this company's knowledge base.
Answer the user's question using ONLY the context provided below.
If the answer is not in the context, say "I don't have information about that in the uploaded documents."
Do not use any knowledge outside the provided context.

CONTEXT:
{context}"""

    # Step 4: Call the LLM and return the full response
    response = openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": body.question},
        ],
        max_tokens=500,
        temperature=0.1,  # low temperature = more factual, less creative
    )

    answer = response.choices[0].message.content
    return {"answer": answer, "sources_used": len(chunks)}

StreamingResponse

The full-response approach in Step 8 waits for the LLM to generate the entire answer before sending anything to the client. For short answers that's fine, but for longer responses it can mean the user stares at a blank screen for 5–10 seconds before any text appears. Streaming fixes this by sending each token to the client as soon as the LLM generates it — the same way ChatGPT's interface works, where you see words appearing in real time.

In FastAPI, streaming uses a StreamingResponse with an async generator. An async generator is a function defined with async def that uses yield instead of return. Each time the loop calls yield, FastAPI sends that chunk of data to the client immediately over the HTTP connection, without waiting for the rest of the generator to finish. You enable streaming from the OpenAI API by passing stream=True to the completions call — this returns an iterator of delta objects, each containing a small piece of the response text.

The client that calls your streaming endpoint receives a plain text HTTP response that arrives in fragments. In a browser frontend, you'd use the Fetch API with response.body.getReader() to read the stream. In curl, you'd see text appearing token by token. The client needs to understand it's receiving a stream — not a complete response — and handle the partial data accordingly.

python
from fastapi import FastAPI, Depends
from fastapi.responses import StreamingResponse
from sqlalchemy.orm import Session
import os
from openai import OpenAI

from services.retriever import retrieve_relevant_chunks

openai_client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


@app.post("/chat/stream", dependencies=[Depends(verify_api_key)])
async def chat_stream(
    body: ChatRequest,
    db: Session = Depends(get_db)
):
    chunks = retrieve_relevant_chunks(body.question, db, top_k=5)

    if not chunks:
        async def empty():
            yield "No documents uploaded yet."
        return StreamingResponse(empty(), media_type="text/plain")

    context = "\n\n".join(
        f"[{i}] From '{c.document.name}':\n{c.text}"
        for i, c in enumerate(chunks, 1)
    )

    system_prompt = f"""You are a helpful knowledge base assistant.
Answer using ONLY the context below. If the answer isn't there, say so.

CONTEXT:
{context}"""

    async def generate():
        """
        Async generator — yields text chunks as the LLM produces them.
        FastAPI's StreamingResponse calls this generator and sends each
        yielded string to the client immediately.
        """
        # stream=True makes the OpenAI call return an iterator of delta chunks
        stream = openai_client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user",   "content": body.question},
            ],
            max_tokens=500,
            temperature=0.1,
            stream=True,   # THIS is what enables streaming
        )

        # Iterate over delta chunks as the LLM generates them
        for chunk in stream:
            delta = chunk.choices[0].delta
            if delta.content:              # some deltas are empty (start/end markers)
                yield delta.content         # send this token fragment to the client NOW

    # StreamingResponse takes the async generator and streams each yielded string
    # media_type="text/plain" — client receives a stream of plain text
    return StreamingResponse(generate(), media_type="text/plain")

// Browser JS — read the stream and append tokens to the page as they arrive
async function chatStream(question) {
  const response = await fetch("/chat/stream", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-API-Key": "YOUR_API_KEY"
    },
    body: JSON.stringify({ question })
  });

  const reader = response.body.getReader();    // get the stream reader
  const decoder = new TextDecoder();           // convert bytes to string
  const output = document.getElementById("answer");

  output.textContent = "";  // clear previous answer

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;                             // stream ended
    output.textContent += decoder.decode(value); // append new tokens as they arrive
  }
}

Auth + Testing

The same X-API-Key middleware pattern from Capstone 1 protects all endpoints here. The middleware reads the header, hashes it with bcrypt, and checks it against the database. You can reuse the create_api_key.py script from Capstone 1 exactly as-is — the APIKey model is identical.

Testing the RAG pipeline requires mocking both the embedder and the LLM. You don't want tests to make real API calls — they'd be slow, cost money, and produce non-deterministic results. Mock the embedder to return fixed vectors, mock the LLM response, and verify that: documents are stored with the correct number of chunks, similarity search returns chunks in order, and the chat route constructs the prompt correctly and returns a response. You can't easily test that the answers are semantically correct in a unit test — that's validated manually with real data.
