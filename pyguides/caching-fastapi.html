Caching with FastAPI and Redis

Stop running the same database query a thousand times. Covers in-memory TTL caching, Redis setup, caching database results, expiry times, cache invalidation, and a reusable cache decorator.

1

What is Caching?

Every time a user loads a page, your app queries the database, does calculations, or calls external services. If 1000 users load the same page at once, that is 1000 identical database queries. Caching stores the result of a slow operation so the next request gets it from memory instantly without hitting the database again. The tradeoff is that cached data can go out of date, so every cached value has a time limit called a TTL, after which it expires and the next request fetches fresh data.

python
from fastapi import FastAPI
from database import get_products  # your db query function

app = FastAPI()

# PROBLEM: every single request hits the database.
# 1000 users load /products at the same time = 1000 identical queries.
# The result is the same for all of them, so almost all that work is wasted.

@app.get("/products")
async def list_products():
    products = get_products()  # slow — hits the database every time
    return products
python
from fastapi import FastAPI
from database import get_products
import some_cache  # in-memory dict or Redis — details in next steps

app = FastAPI()

# SOLUTION: check the cache first.
# Cache HIT  → return instantly, no database involved at all.
# Cache MISS → query the database, store the result, then return.
# 1000 users = 1 database query + 999 instant cache reads.

@app.get("/products")
async def list_products():
    cached = some_cache.get("products:all")
    if cached:
        return cached  # cache hit — returned in microseconds

    products = get_products()              # cache miss — query the db
    some_cache.set("products:all", products, ttl=300)  # store for 5 minutes
    return products

In-Memory Cache (No Redis)

The simplest cache is a Python dictionary with timestamps. It stores values with an expiry time and checks whether the value is still fresh before returning it. This approach works for a single-server app and needs no extra software to install. It has two downsides: the cache disappears when the server restarts, and it is not shared if you run multiple server processes.

python
import time

# A plain dict: { key: {"value": ..., "expires_at": timestamp} }
_cache: dict = {}

def cache_get(key: str, ttl: int):
    """Return cached value if it exists and has not expired, else None."""
    entry = _cache.get(key)
    if entry is None:
        return None                  # key not in cache at all
    if time.time() > entry["expires_at"]:
        del _cache[key]              # value is stale — remove it
        return None
    return entry["value"]          # still fresh — return it

def cache_set(key: str, value, ttl: int):
    """Store value in cache with an expiry time (ttl in seconds)."""
    _cache[key] = {
        "value": value,
        "expires_at": time.time() + ttl,  # absolute timestamp when it expires
    }
python
from fastapi import FastAPI
from cache import cache_get, cache_set  # the functions from the other tab

app = FastAPI()

# Fake database function — replace with your real SQLAlchemy / psycopg2 call
def fetch_products_from_db():
    return [{"id": 1, "name": "Widget"}, {"id": 2, "name": "Gadget"}]

CACHE_TTL = 300  # 5 minutes

@app.get("/products")
async def list_products():
    cached = cache_get("products:all", CACHE_TTL)
    if cached is not None:
        return cached               # hit — no database involved

    products = fetch_products_from_db()   # miss — query the database
    cache_set("products:all", products, CACHE_TTL)  # store the result
    return products

Install Redis

Redis is an in-memory data store that is fast, shared across all server processes, and persists between restarts. It is the standard choice for caching in production. The easiest way to run it locally is with Docker. On Mac and Linux you can also install it directly.

bash
# Option 1: Docker (works on Windows, Mac, Linux — recommended)
docker run -d -p 6379:6379 --name redis redis:alpine

# Option 2: Homebrew (Mac only)
brew install redis
brew services start redis

# Option 3: apt (Ubuntu / Debian)
sudo apt update && sudo apt install redis-server -y
sudo systemctl start redis

# Install the Python client
pip install redis

# Verify Redis is running — should print PONG
redis-cli ping

Connect to Redis in FastAPI

The redis Python library connects to Redis. Create a client once at module level so it is reused across all requests instead of creating a new connection every time. The from_url() method reads the connection string from your environment so you can switch between local and production Redis without changing code.

python
# cache.py
import os
import redis
from dotenv import load_dotenv

load_dotenv()

# Create ONE client at module level — reused for the lifetime of the process.
# decode_responses=True means get() returns a str instead of bytes,
# so you can pass the result straight to json.loads() without decoding.
redis_client = redis.from_url(
    os.getenv("REDIS_URL", "redis://localhost:6379/0"),
    decode_responses=True,  # always set this — saves you a .decode("utf-8") everywhere
)

# Import this client in your routes:
# from cache import redis_client
python
# main.py
from fastapi import FastAPI
from cache import redis_client

app = FastAPI()

# Check the Redis connection when the server starts.
# If Redis is down, the app refuses to start instead of silently failing
# at runtime when the first request tries to use it.
@app.on_event("startup")
async def check_redis():
    try:
        redis_client.ping()         # raises ConnectionError if Redis is not running
        print("Redis connection OK")
    except Exception as e:
        # Raise so uvicorn exits with a clear message — much better than
        # a confusing ConnectionError on the first request in production.
        raise RuntimeError(f"Cannot connect to Redis: {e}")

Cache a Database Query

The pattern is always the same: check if the key exists in Redis, return it immediately if it does, query the database if it does not, store the result in Redis with a TTL, then return it. The key must be unique per query, so include the query parameters in the key name.

python
import json
from fastapi import FastAPI, HTTPException
from cache import redis_client
from database import get_user_by_id  # your real db function

app = FastAPI()

@app.get("/users/{user_id}")
async def get_user(user_id: int):
    cache_key = f"user:{user_id}"  # key includes the id — different users = different keys

    # Step 1: check Redis for a cached copy
    cached = redis_client.get(cache_key)
    if cached:
        return json.loads(cached)   # cache hit — deserialise and return immediately

    # Step 2: cache miss — go to the database
    user = get_user_by_id(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="User not found")

    # Step 3: store in Redis.
    # setex(key, seconds, value) — sets the value AND an expiry in one call.
    # 300 seconds = 5 minutes. After that, Redis deletes the key automatically.
    redis_client.setex(cache_key, 300, json.dumps(user))

    return user  # Step 4: return the fresh data
python
import json
from typing import Callable, Any
from cache import redis_client

def get_or_cache(key: str, ttl: int, fn: Callable[[], Any]) -> Any:
    """
    Check Redis for key. If present, return it.
    If missing, call fn() to get the value, cache it, and return it.

    Usage:
        data = get_or_cache("user:42", ttl=300, fn=lambda: fetch_user(42))
    """
    cached = redis_client.get(key)
    if cached:
        return json.loads(cached)   # hit — return without calling fn at all

    value = fn()                    # miss — call the fallback (db query, API call, etc.)
    redis_client.setex(key, ttl, json.dumps(value))  # store with expiry
    return value

# Using the helper in a route — much less boilerplate than the manual pattern
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return get_or_cache(
        key=f"user:{user_id}",
        ttl=300,
        fn=lambda: get_user_by_id(user_id),
    )

TTL — Setting Expiry Times

The TTL is how many seconds a cached value stays valid. Set it too short and you do not get much benefit. Set it too long and users see stale data. The right value depends on how often the underlying data changes and how bad it would be to show old data.

python
import json
from cache import redis_client

# setex(key, seconds, value) — the standard way to cache with an expiry.
# Redis deletes the key automatically when the TTL runs out.

# User profile — changes occasionally, short TTL is fine
redis_client.setex(f"user:{user_id}", 300, json.dumps(user_data))      # 5 minutes

# Product list — changes rarely, longer TTL reduces db load significantly
redis_client.setex("products:all", 600, json.dumps(products))           # 10 minutes

# Homepage aggregated stats — expensive query, changes slowly
redis_client.setex("homepage:stats", 3600, json.dumps(stats))          # 1 hour

# App configuration — basically never changes, cache for a full day
redis_client.setex("config:feature_flags", 86400, json.dumps(config))   # 24 hours

# Check how long a key has left before expiry
ttl_remaining = redis_client.ttl(f"user:{user_id}")
# Returns seconds remaining, -1 if no expiry, -2 if key does not exist

Cache Invalidation

When data changes in the database, the cache still holds the old version. Invalidation means deleting the cached key so the next request fetches fresh data. The simplest rule is: in every route that writes to the database, delete the cache keys for the data you just changed.

python
from fastapi import FastAPI, HTTPException
from cache import redis_client
from database import update_user_in_db, get_user_by_id
from pydantic import BaseModel

app = FastAPI()

class UserUpdate(BaseModel):
    name: str
    email: str

@app.put("/users/{user_id}")
async def update_user(user_id: int, body: UserUpdate):
    # Step 1: write the new data to the database first
    updated = update_user_in_db(user_id, body.dict())
    if not updated:
        raise HTTPException(status_code=404, detail="User not found")

    # Step 2: delete the cached version so the next GET fetches fresh data.
    # redis_client.delete() is safe even if the key does not exist — no error.
    redis_client.delete(f"user:{user_id}")

    return {"ok": True, "user_id": user_id}
python
from cache import redis_client

# Delete multiple specific keys in one call — more efficient than calling delete() in a loop
redis_client.delete(f"user:{user_id}", "users:all", "homepage:stats")

# ---- Pattern-based deletion ----
# redis_client.keys("user:*") scans the entire key space for matching keys.
# Fine for development or small datasets, but DO NOT use on large production
# databases — it blocks the Redis server while scanning and can cause timeouts.
# Use SCAN-based iteration or a dedicated key registry for production pattern deletes.

keys_to_delete = redis_client.keys("user:*")   # find all user keys
if keys_to_delete:
    redis_client.delete(*keys_to_delete)           # unpack list and delete all at once

# Production-safe pattern scan using SCAN (non-blocking, cursor-based)
cursor = 0
while True:
    cursor, keys = redis_client.scan(cursor, match="user:*", count=100)
    if keys:
        redis_client.delete(*keys)
    if cursor == 0:  # cursor returns to 0 when the full scan is complete
        break

Cache Decorator

Repeating the check/store logic in every route gets tedious. A decorator wraps any route function and handles the cache automatically. You add one line above your function and the decorator does the rest.

python
# cache.py
import json
import functools
from typing import Callable
from cache import redis_client

def cached(ttl: int = 300):
    """
    Decorator factory — add @cached(ttl=N) above any async route function.
    Builds a cache key from the function name + its arguments so different
    callers (e.g. /users/1 vs /users/2) get separate cache entries.
    """
    def decorator(fn: Callable):
        @functools.wraps(fn)
        async def wrapper(*args, **kwargs):
            # Build a unique key from the function name and all its arguments
            key_parts = [fn.__name__] + [str(a) for a in args] + [
                f"{k}={v}" for k, v in sorted(kwargs.items())
            ]
            cache_key = ":".join(key_parts)  # e.g. "get_user:42" or "list_products:"

            # Check Redis — return immediately on a hit
            cached_value = redis_client.get(cache_key)
            if cached_value:
                return json.loads(cached_value)

            # Cache miss — call the real route function
            result = await fn(*args, **kwargs)

            # Store in Redis with the configured TTL
            redis_client.setex(cache_key, ttl, json.dumps(result))

            return result
        return wrapper
    return decorator
python
from fastapi import FastAPI
from cache import cached  # import the decorator
from database import get_user_by_id, get_all_products

app = FastAPI()

# One line replaces all the manual get/set/serialise boilerplate.
# The decorated function looks exactly like a normal route.

@app.get("/users/{user_id}")
@cached(ttl=300)  # cache for 5 minutes — key will be "get_user:<user_id>"
async def get_user(user_id: int):
    return get_user_by_id(user_id)  # only called on a cache miss


@app.get("/products")
@cached(ttl=600)  # cache for 10 minutes — key will be "list_products:"
async def list_products():
    return get_all_products()       # only called on a cache miss

# Compare to the manual version which needed ~8 lines per route.
# The decorator handles: key generation, get, json.loads, setex, json.dumps.

What's Next

You now have a full caching layer from simple in-memory dicts to Redis with TTL and invalidation. The cache decorator makes it easy to add to any route without repeating code.

Redis as a Celery broker
Redis also powers Celery task queues. If you want to offload slow work (sending emails, generating reports, processing uploads) to background workers, Redis serves as the message broker that connects your FastAPI app to your Celery workers. See the Background Tasks guide for how to run Celery alongside your FastAPI app.
Cache warming
By default, the cache starts empty and fills up as users make requests. For high-traffic data you can pre-populate the cache at startup instead of waiting for the first request to warm it. Add a startup event handler that runs your most expensive queries and stores the results in Redis before the server accepts traffic.
Rate limiting with Redis
Redis is also used to implement rate limiting with a sliding window counter. Each request increments a key like ratelimit:<ip> with a short TTL. When the counter exceeds your limit, you return a 429 response. The key expires automatically at the end of the window, resetting the counter without any cleanup code. The public-api-fastapi guide covers a simple version you can drop straight into your app.
