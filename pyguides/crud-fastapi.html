CRUD with FastAPI + HTML Frontend

Learn Create, Read, Update, and Delete with FastAPI — from a simple in-memory store to a working no-JavaScript HTML frontend. Covers the patterns you'll use for real CRMs, AI integrations, and APIs.

1

What is CRUD?

CRUD stands for Create, Read, Update, and Delete. These are the four operations every app does with data. A CRM creates contacts, reads them into a list, updates their details, and deletes them when removed. FastAPI maps each operation directly to an HTTP method, which is the instruction a browser or frontend sends to your server.

OperationHTTP MethodWhat it meansExample URL
CreatePOSTSend new data to save/items
ReadGETFetch data, change nothing/items or /items/1
UpdatePUTSend updated data for an existing record/items/1
DeleteDELETERemove a record permanently/items/1
REST naming rule: the URL is a plural noun (/items, /tasks, /contacts). The HTTP method is the verb. Never put the action in the URL — /createItem is wrong; POST /items is correct.

Setup & Install

A virtual environment keeps this project's packages separate from everything else on your machine. Always activate it before installing or running anything, and you will see (venv) in your terminal prompt when it is active. FastAPI is the framework and Uvicorn is the server that runs it. python-dotenv lets you load secret keys from a .env file instead of writing them directly in your code. Once the server is running, FastAPI gives you a free interactive docs page at /docs where you can test every route without writing any frontend code.

bash
# Create your project folder
mkdir FastDev
cd FastDev

# Create and activate a virtual environment
python -m venv venv
venv\Scripts\activate        # Windows
source venv/bin/activate     # macOS / Linux

# Install the packages
pip install fastapi uvicorn jinja2 python-multipart python-dotenv

# Run the server (--reload restarts automatically when you save a file)
uvicorn main:app --reload

# Open your browser to test routes interactively
# http://localhost:8000/docs

The Complete Boilerplate

Two versions are shown here. The API-only tab is the minimal CRUD backend, and you should use it when your frontend is separate, such as a React app or mobile app. The with HTML frontend tab is the full version used in steps 13 to 16. It serves an HTML page, reads form submissions, and redirects after every change. Both share the same CRUD logic. The only difference is how they receive input and what they return.

python
from fastapi import FastAPI, HTTPException

# Create the app — everything hangs off this object
app = FastAPI()

# In-memory store — replace with a real database later
# Resets every time the server restarts
db = {}
next_id = 1


# ── CREATE ──────────────────────────────────────────────────
# POST /items  →  save a new item, return it with its new ID
@app.post("/items")
def create_item(name: str, description: str = None):
    global next_id
    db[next_id] = {"id": next_id, "name": name, "description": description}
    next_id += 1
    return db[next_id - 1]


# ── READ ALL ─────────────────────────────────────────────────
# GET /items  →  return every item as a list
@app.get("/items")
def get_all_items():
    return list(db.values())


# ── READ ONE ─────────────────────────────────────────────────
# GET /items/3  →  return the item with id=3, or 404 if missing
@app.get("/items/{item_id}")
def get_item(item_id: int):
    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")
    return db[item_id]


# ── UPDATE ───────────────────────────────────────────────────
# PUT /items/3  →  update fields on item 3, return updated item
@app.put("/items/{item_id}")
def update_item(item_id: int, name: str = None, description: str = None):
    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")
    if name is not None:
        db[item_id]["name"] = name
    if description is not None:
        db[item_id]["description"] = description
    return db[item_id]


# ── DELETE ───────────────────────────────────────────────────
# DELETE /items/3  →  remove item 3, return a confirmation message
@app.delete("/items/{item_id}")
def delete_item(item_id: int):
    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")
    del db[item_id]
    return {"message": f"Item {item_id} deleted"}
python
from fastapi import FastAPI, HTTPException, Form, Request
from fastapi.responses import HTMLResponse, RedirectResponse
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

app = FastAPI()

# Serve files from the static/ folder at the /static URL path
app.mount("/static", StaticFiles(directory="static"), name="static")

# Tell FastAPI where your HTML template files live
templates = Jinja2Templates(directory="templates")

db = {}
next_id = 1


# ── SERVE PAGE ───────────────────────────────────────────────
# GET /  →  render index.html, pass all items into the template
@app.get("/", response_class=HTMLResponse)
def index(request: Request):
    return templates.TemplateResponse("index.html", {
        "request": request,              # always required by Jinja2
        "items": list(db.values())       # available in HTML as {{ items }}
    })


# ── CREATE ───────────────────────────────────────────────────
# POST /items/create  →  read form fields, save, redirect back to /
@app.post("/items/create")
def create_item(
    name: str        = Form(...),   # Form(...) = required HTML field
    description: str = Form(None)  # Form(None) = optional — blank field sends ""
):
    global next_id
    db[next_id] = {"id": next_id, "name": name, "description": description}
    next_id += 1
    return RedirectResponse("/", status_code=303)  # 303 = redirect after POST


# ── UPDATE ───────────────────────────────────────────────────
# POST /items/update  →  HTML forms can't send PUT, so we use POST
# item_id comes from a hidden <input type="hidden"> in the form
@app.post("/items/update")
def update_item(
    item_id: int     = Form(...),   # which item — from hidden input
    name: str        = Form(None),  # blank field sends "" — skip update if empty
    description: str = Form(None)   # blank field sends "" — skip update if empty
):
    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")
    # "if name:" catches both None and "" (empty string from a blank input)
    # Use "if name is not None:" only for API routes where "" means "clear the field"
    if name:
        db[item_id]["name"] = name
    if description:
        db[item_id]["description"] = description
    return RedirectResponse("/", status_code=303)


# ── DELETE ───────────────────────────────────────────────────
# POST /items/delete  →  HTML forms can't send DELETE, so we use POST
@app.post("/items/delete")
def delete_item(item_id: int = Form(...)):
    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")
    del db[item_id]
    return RedirectResponse("/", status_code=303)

CREATE — POST /items

POST is the HTTP method for sending new data to the server to be saved. FastAPI reads the parameters like name and description directly from the URL query string, so calling POST /items?name=Notebook sets name to "Notebook" inside the function. The global keyword tells Python to use the next_id counter that was defined outside the function. Without it, Python would create a brand new local variable instead, and the counter would reset to 1 every time. Each item is stored in the db dictionary with its ID as the key, and the saved item is returned so the caller can see its new ID.

python
@app.post("/items")          # responds to: POST /items
def create_item(name: str, description: str = None):
    # name: str  →  required, must be a string
    # description: str = None  →  optional, defaults to None if not provided

    global next_id  # tells Python: use the counter defined outside this function

    db[next_id] = {
        "id":          next_id,      # store the ID inside the item so it's easy to return
        "name":        name,         # value comes from the query string
        "description": description   # will be None if not provided
    }

    next_id += 1               # move the counter forward for next time
    return db[next_id - 1]     # return the item we just saved
bash
# Using curl — or just use the /docs page in your browser
curl -X POST "http://localhost:8000/items?name=Notebook&description=A5%20size"

# Expected response:
# { "id": 1, "name": "Notebook", "description": "A5 size" }

# Create another — description is optional
curl -X POST "http://localhost:8000/items?name=Pen"

# Expected response:
# { "id": 2, "name": "Pen", "description": null }

READ — GET /items and GET /items/{id}

There are two read operations: fetch all records, and fetch one by ID. GET is the default HTTP method, and it is what a browser uses when you type a URL and press enter. The {item_id} in the path is a variable slot in the URL, so visiting /items/3 sets item_id to 3 inside the function. The : int after the parameter name tells FastAPI to convert the text "3" from the URL into the number 3, and it will reject anything that cannot be converted (like /items/banana) with a 422 error. HTTPException with status_code=404 sends a standard "not found" response that all browsers and API clients understand.

python
@app.get("/items")           # responds to: GET /items
def get_all_items():
    # db.values() returns all the stored dicts
    # list() wraps them so FastAPI can return them as a JSON array
    return list(db.values())
python
@app.get("/items/{item_id}")  # {item_id} is a variable slot in the URL
def get_item(item_id: int):  # : int tells FastAPI to convert it from a string

    if item_id not in db:
        # 404 = "not found" — a standard HTTP status code
        raise HTTPException(status_code=404, detail="Item not found")

    return db[item_id]
bash
# Get all items
curl http://localhost:8000/items

# Get a specific item
curl http://localhost:8000/items/1

# Try a missing ID — should return a 404 error
curl http://localhost:8000/items/99

# Try an invalid ID — should return a 422 validation error
curl http://localhost:8000/items/banana

UPDATE — PUT /items/{id}

PUT is the HTTP method for sending updated data for an existing record. The URL always includes the ID so the server knows which record to change. Each field parameter defaults to None, which means the caller can update just one field at a time without providing the others. The if is not None check makes sure only the fields that were actually sent get overwritten. This pattern is called a partial update and appears in almost every real API.

python
@app.put("/items/{item_id}")   # responds to: PUT /items/3
def update_item(item_id: int, name: str = None, description: str = None):
    # item_id  →  comes from the URL path  e.g. /items/3
    # name     →  comes from the query string  e.g. ?name=Binder
    # Both default to None so the caller can update just one field at a time

    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")

    # Only update a field if a new value was actually provided
    if name is not None:
        db[item_id]["name"] = name

    if description is not None:
        db[item_id]["description"] = description

    # Return the updated item so the caller can confirm the change
    return db[item_id]
bash
# Update just the name of item 1
curl -X PUT "http://localhost:8000/items/1?name=Hardcover+Notebook"

# Update just the description
curl -X PUT "http://localhost:8000/items/1?description=A4+ruled"

# Update both at once
curl -X PUT "http://localhost:8000/items/1?name=Notebook&description=A4+ruled"

DELETE — DELETE /items/{id}

DELETE is the HTTP method for removing a record permanently. Like PUT, the URL always includes the ID, and no extra data is needed beyond that. After deleting, returning a confirmation message is a common convention so the caller knows the operation succeeded. The del keyword removes a key from a Python dictionary entirely, which is why the existence check comes first. If you skip the check and try to delete a key that does not exist, Python raises a KeyError.

python
@app.delete("/items/{item_id}")  # responds to: DELETE /items/3
def delete_item(item_id: int):

    if item_id not in db:
        raise HTTPException(status_code=404, detail="Item not found")

    del db[item_id]  # remove the entry from the dictionary entirely

    # Return a confirmation — the f-string inserts item_id into the message
    return {"message": f"Item {item_id} deleted"}
bash
# Delete item 1
curl -X DELETE http://localhost:8000/items/1

# Expected response:
# { "message": "Item 1 deleted" }

# Try to get it again — should now return 404
curl http://localhost:8000/items/1

Type Hints — What They Are and When to Use Them

A type hint is the colon annotation you write after a parameter name, like item_id: int or name: str. Plain Python ignores them, but FastAPI reads them to do three things automatically: convert the incoming value to the right type, reject bad values with a clear error before they reach your function, and show the correct input fields in the /docs page. You do not need Pydantic models for simple apps, as type hints on function parameters are enough. Add a model only when you have many fields and want to group them under one name.

python
# str   →  any text: "hello", "john@email.com", "2024-01-01"
# int   →  whole numbers: 1, 42, -5
# float →  decimal numbers: 3.14, 19.99
# bool  →  True or False (accepts: true, false, 1, 0 from query strings)

# Required parameter — must be provided or FastAPI returns 422
def example(name: str):
    ...

# Optional parameter — defaults to None if not provided
def example(name: str = None):
    ...

# Optional with a real default value
def example(done: bool = False, priority: int = 1):
    ...
python
# Inline type hints — fine for 2-4 fields, simple apps
def create_contact(name: str, email: str, phone: str = None):
    ...

# Pydantic model — better when you have many fields
# pip install pydantic  (included with fastapi)
from pydantic import BaseModel

class Contact(BaseModel):
    name:    str
    email:   str
    phone:   str   = None
    company: str   = None
    tags:    list  = []
    active:  bool  = True

def create_contact(contact: Contact):  # one clean parameter instead of six
    ...

Routers — Keeping Code Organised

Once your app has more than one resource, like items and users or contacts and deals, putting everything in one main.py file gets hard to read quickly. Routers let you split each resource into its own file. APIRouter works exactly like app and uses the same decorators, but it belongs to a file rather than the whole app. In main.py, include_router() mounts it, and the prefix argument means FastAPI adds /items to every route automatically so you do not have to type it each time.

python
from fastapi import APIRouter, HTTPException

# APIRouter works exactly like app — same decorators, same syntax
router = APIRouter()

db = {}
next_id = 1

# Notice: just "/", not "/items/" — the prefix is added in main.py
@router.post("/")
def create_item(name: str):
    global next_id
    db[next_id] = {"id": next_id, "name": name}
    next_id += 1
    return db[next_id - 1]

@router.get("/")
def get_all_items():
    return list(db.values())

# ... rest of CRUD routes follow the same pattern
python
from fastapi import FastAPI
from routes.items import router as items_router
# from routes.users import router as users_router  ← add more as you grow

app = FastAPI()

# prefix="/items" means all routes in items_router are at /items/...
# tags=["items"] groups them together in the /docs page
app.include_router(items_router, prefix="/items", tags=["items"])
# app.include_router(users_router, prefix="/users", tags=["users"])

Environment Variables — Storing Secrets Safely

Any time your app connects to an external service like an AI API, a database, or a payment provider, you will have an API key or password. Never write these directly in your Python file, because if you push that file to GitHub your key becomes public. The standard approach is a .env file, which is a plain text file of KEY=VALUE pairs that lives only on your machine and is never committed to version control. python-dotenv reads this file when your app starts and makes the values available via os.getenv(). Add .env to your .gitignore file before your first commit.

bash
# .env — never commit this file
OPENAI_API_KEY=sk-abc123yourkeyhere
DATABASE_URL=postgresql://user:pass@localhost/mydb
SECRET_KEY=some-long-random-string
python
from dotenv import load_dotenv
import os

# Reads your .env file and loads the values into the environment
# Call this once at the top of main.py before reading any variables
load_dotenv()

# os.getenv() reads the value — returns None if the key doesn't exist
OPENAI_API_KEY = os.getenv("OPENAI_API_KEY")
DATABASE_URL   = os.getenv("DATABASE_URL")

# Fail fast at startup if a required key is missing
if not OPENAI_API_KEY:
    raise RuntimeError("OPENAI_API_KEY not set in .env")

CORS — Connecting a Frontend or External Service

CORS stands for Cross-Origin Resource Sharing. Browsers block requests from one domain to another by default as a security measure. If your HTML frontend is at localhost:5500 and your FastAPI server is at localhost:8000, the browser will block every API call unless the server explicitly allows it. Adding the CORS middleware tells FastAPI to include the right headers in its responses so browsers permit the connection. allow_origins=["*"] permits any domain and is fine for development and public APIs. In production, replace the star with your specific frontend domain for tighter security.

python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

# Add this before any routes are defined
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],      # allow any domain — fine for dev and public APIs
    allow_methods=["*"],      # allow GET, POST, PUT, DELETE, etc.
    allow_headers=["*"],      # allow any headers including Authorization
)

# In production, tighten allow_origins to your actual frontend domain:
# allow_origins=["https://myapp.com", "https://www.myapp.com"]

Adding an HTML Frontend — What Changes in main.py

Connecting an HTML frontend to FastAPI requires four new imports and two structural changes. Jinja2Templates tells FastAPI where your HTML files live and fills in the double-curly-brace placeholders with Python data before the page is sent to the browser. StaticFiles mounts a folder so the browser can load CSS and images. Form replaces query-string parameters, so instead of reading ?name=x from the URL, FastAPI reads the value from the form body. RedirectResponse sends the browser to a new URL after a form submission, which prevents the form from being resubmitted if the user refreshes the page. Request is a required new parameter on the page-serving route because Jinja2 needs it to build the response correctly.

python
# API-only version — no HTML
from fastapi import FastAPI, HTTPException

# ─────────────────────────────────────────────────────────────

# With HTML frontend — four new imports added
from fastapi import FastAPI, HTTPException, Form, Request
from fastapi.responses import HTMLResponse, RedirectResponse
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

# Form          →  reads a value from an HTML <form> submission
# Request       →  the incoming HTTP request; Jinja2 requires it
# HTMLResponse  →  tells FastAPI the response is HTML, not JSON
# RedirectResponse → sends the browser to a new URL after a form POST
# StaticFiles   →  serves CSS/images from a folder
# Jinja2Templates → renders .html files with {{ }} placeholders filled in

app = FastAPI()

# Mount the static/ folder — browser loads /static/style.css from here
# The name= string is how Jinja2 references it: url_for('static', path='style.css')
app.mount("/static", StaticFiles(directory="static"), name="static")

# Tell FastAPI where your HTML template files live
templates = Jinja2Templates(directory="templates")
python
# This route renders and serves the HTML page
# response_class=HTMLResponse tells FastAPI to set the correct Content-Type header
@app.get("/", response_class=HTMLResponse)
def index(request: Request):
    # templates.TemplateResponse(filename, context_dict)
    # filename  → which file inside your templates/ folder to render
    # context   → a dict of variables available inside the HTML as {{ key }}
    return templates.TemplateResponse("index.html", {
        "request": request,         # always required — Jinja2 needs it internally
        "items": list(db.values())  # available in HTML as {{ items }} or {% for item in items %}
    })

# This route is called automatically after every form submission
# because each create/update/delete route ends with:
#     return RedirectResponse("/", status_code=303)
# The browser follows the redirect, hits GET /, and gets fresh HTML
python
# ── QUERY STRING (API-only) ──────────────────────────────────
# Parameters come from the URL: POST /items?name=Notebook
@app.post("/items")
def create_item(name: str, description: str = None):
    ...

# ── FORM DATA (HTML frontend) ────────────────────────────────
# Parameters come from the form body: <input name="name">
# The route URL changes too — /items/create instead of /items
# so it doesn't clash with GET /items (read all)
@app.post("/items/create")
def create_item(
    name: str        = Form(...),  # Form(...) = required — 422 error if missing
    description: str = Form(None) # Form(None) = optional — blank field sends ""
):
    ...
    return RedirectResponse("/", status_code=303)
# 303 = "See Other" — the standard redirect code after a POST form submission
# Without the redirect, pressing browser refresh would re-submit the form

The HTML Template — templates/index.html

Jinja2 is the templating engine FastAPI uses to fill in placeholders before sending HTML to the browser. The browser never sees the double curly braces, only the finished result. There are two kinds of Jinja2 syntax: double curly braces like {{ item.name }} output a value, and curly-percent blocks like {% for %} and {% if %} contain logic such as loops and conditionals. The name attribute on every HTML input must exactly match the parameter name in the Form() declaration, and a hidden input carries the item_id invisibly so Python knows which item to update or delete.

html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>FastDev</title>
  <!-- /static/ maps to your static/ folder, configured in main.py -->
  <link rel="stylesheet" href="/static/style.css">
</head>
<body>

  <header>
    <h1>FastDev</h1>
  </header>

  <main>

    <!-- ── CREATE FORM ────────────────────────────────────────────
         method="post"           → HTTP POST request
         action="/items/create"  → the FastAPI route: @app.post("/items/create")
         name="name"             → links to Python param: name: str = Form(...)
         name="description"      → links to: description: str = Form(None)
    -->
    <section>
      <h2>Add an Item</h2>
      <form method="post" action="/items/create">
        <label>Name</label>
        <input type="text" name="name" placeholder="Item name" required>
        <!-- required enforced by browser before submitting -->

        <label>Description</label>
        <input type="text" name="description" placeholder="Optional">
        <!-- left blank → Python receives None for description -->

        <button type="submit">Add Item</button>
      </form>
    </section>

    <!-- ── READ ALL ───────────────────────────────────────────────
         No form needed. Python passed items via:
             "items": list(db.values())
         Jinja2 class="hl-template">{% for %} loops over that list below.
    -->
    <section>
      <h2>All Items</h2>

      <!-- class="hl-template">{% if items %} checks whether the list is non-empty -->
      class="hl-template">{% if items %}
        <div class="item-list">

          <!-- class="hl-template">{% for item in items %} loops — one card per dict in the list -->
          class="hl-template">{% for item in items %}
          <div class="item-card">

            <div class="item-info">
              <!-- class="hl-template">{{ item.id }} outputs the "id" key from the dict -->
              <span class="item-id">#class="hl-template">{{ item.id }}</span>
              <strong>class="hl-template">{{ item.name }}</strong>

              <!-- class="hl-template">{% if item.description %} — only render if not None/empty -->
              class="hl-template">{% if item.description %}
                <p>class="hl-template">{{ item.description }}</p>
              class="hl-template">{% endif %}
            </div>

            <div class="item-actions">

              <!-- ── UPDATE FORM ───────────────────────────────────
                   HTML forms can't send PUT — so we POST to a
                   dedicated route: @app.post("/items/update")
                   The hidden input sends item_id without showing it.
                   value=" class="hl-template">{{ item.id }}" → Jinja2 fills in this item's ID
              -->
              <form method="post" action="/items/update">
                <input type="hidden" name="item_id" value=" class="hl-template">{{ item.id }}">
                <!-- "hidden" → invisible to user, still sent with the form -->

                <input type="text" name="name"
                       placeholder=" class="hl-template">{{ item.name }}">
                <!-- placeholder shows current value as a hint -->

                <input type="text" name="description"
                       placeholder=" class="hl-template">{{ item.description or 'description' }}">
                <!-- item.description or 'description' → Jinja2 fallback if None -->

                <button type="submit">Save</button>
              </form>

              <!-- ── DELETE FORM ───────────────────────────────────
                   HTML forms can't send DELETE — so we POST to:
                   @app.post("/items/delete")
                   One hidden input, one button — that's all that's needed.
              -->
              <form method="post" action="/items/delete">
                <input type="hidden" name="item_id" value=" class="hl-template">{{ item.id }}">
                <button type="submit">Delete</button>
              </form>

            </div>
          </div>
          class="hl-template">{% endfor %}
          <!-- class="hl-template">{% endfor %} closes the for loop -->

        </div>
      class="hl-template">{% else %}
        <p>No items yet — add one above.</p>
      class="hl-template">{% endif %}

    </section>
  </main>

</body>
</html>

How HTML Forms Talk to Python — The Full Mapping

Every connection between your HTML and your Python function goes through three things: the form's action attribute (which route to call), the form's method (GET or POST), and the name attribute on each input (which parameter to set). HTML forms only support GET and POST, so there is no method="put" or method="delete". This is why the HTML frontend uses POST for update and delete operations, with dedicated routes like /items/update and /items/delete instead of the REST-standard PUT and DELETE. The /docs page still exposes the original PUT and DELETE routes for API clients, so both interfaces can coexist in the same app.

text
HTML attribute / tag             Python / FastAPI equivalent
─────────────────────────────────────────────────────────────────
method="post"                  @app.post(...)
method="get"                   @app.get(...)
action="/items/create"         the URL string in @app.post("/items/create")
name="name"                    parameter name:  name: str = Form(...)
name="item_id"                 parameter name:  item_id: int = Form(...)
required  (HTML attribute)     enforced by browser before submitting
Form(...)                      required in Python — 422 error if missing
Form(None)                     optional — Python receives None if left blank
type="hidden"                  invisible to user, still sent in the form body
<button type="submit">         sends the form when clicked
RedirectResponse("/", 303)     sends browser to GET / after the POST finishes

HTML method="put" / "delete"   NOT SUPPORTED — use POST + dedicated route
PUT  /items/{id}               still works via /docs or curl/fetch — API clients
DELETE /items/{id}             still works via /docs or curl/fetch — API clients

# Without RedirectResponse — browser stays on the POST URL
@app.post("/items/create")
def create_item(name: str = Form(...)):
    db[next_id] = {"name": name}
    return {"ok": True}
# Problem: the browser URL is now /items/create
# Pressing refresh re-submits the form → duplicate item created

# ─────────────────────────────────────────────────────────────

# With RedirectResponse — browser moves to GET /
@app.post("/items/create")
def create_item(name: str = Form(...)):
    db[next_id] = {"name": name}
    return RedirectResponse("/", status_code=303)
# Browser follows the redirect → hits GET / → fresh page renders
# Pressing refresh now just reloads the page — no duplicate
# This is called the Post/Redirect/Get pattern (PRG)
# status_code=303 = "See Other" — the correct code for POST → GET redirects

CSS — static/style.css

The static/ folder holds files that FastAPI serves exactly as they are, with no Python processing. CSS, images, and client-side JavaScript all go here. The file is linked in index.html with href="/static/style.css", which maps to static/style.css on disk because of the app.mount() call in main.py. Nothing in this file needs to change when you add more Python routes, because it is completely independent of the backend logic.
