HTMX + FastAPI

Build dynamic, interactive UIs without writing JavaScript. HTMX lets HTML attributes trigger HTTP requests and swap content on the page — your FastAPI routes return HTML fragments instead of JSON, and HTMX puts them exactly where you want them.

1

What is HTMX?

Most of the JavaScript developers write is just plumbing: fetch some data, loop over it, build HTML, and insert it into the page. React and Vue exist to manage this work, but they bring a lot of complexity with them. You need a build step, a bundler, and hundreds of kilobytes of JavaScript before your app even starts.

HTMX takes a different approach and extends HTML itself. Instead of writing JavaScript to call fetch() and update the page, you add attributes like hx-get="/tasks" directly to HTML elements. HTMX reads those attributes, makes the HTTP request for you, and puts the server's response exactly where you told it to go. Your FastAPI route returns a small chunk of HTML called a fragment, and HTMX swaps it into the page. The result feels like a modern single-page app, but your server just renders templates the same way it always has.

HTML already has the idea built in: a link causes a GET request and a form causes a POST. HTMX just extends this so any element can trigger any HTTP request and the response can go anywhere on the page. The entire HTMX library is about 14KB, which is smaller than a single React component in many projects.

What HTMX is not: It's not for apps that need heavy client-side state — think spreadsheets, real-time collaborative editors, complex data visualisations. For apps that are primarily about displaying and updating server-side data — task managers, dashboards, admin panels, CRMs — HTMX is a perfect fit. If your app was happily using Jinja2 templates, HTMX makes it dramatically more interactive with minimal effort.
2

Project Setup

HTMX is a single JavaScript file. You load it from a CDN with one script tag and there is no npm, no bundler, and no build step needed. On the backend you need FastAPI, Uvicorn, and Jinja2. Jinja2 is the template engine that lets FastAPI render HTML files with Python variables inside them. The project structure has a templates/ folder for HTML files and a static/ folder for CSS and images.

In an HTMX app you have two kinds of templates. Full page templates render the entire HTML document including the head, body, navigation, and everything else. Fragment templates are tiny partial snippets, such as just a list of items or a single updated row. When HTMX makes a request, the server returns a fragment. When the browser navigates directly to a URL, the server returns a full page. You will create both kinds as you build your app.

python
from fastapi import FastAPI, Request
from fastapi.responses import HTMLResponse
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

app = FastAPI()

# Serve anything in static/ at the /static URL prefix
app.mount("/static", StaticFiles(directory="static"), name="static")

# Tell FastAPI where to find HTML template files
templates = Jinja2Templates(directory="templates")

# In-memory task list — we'll swap this for a database later
tasks = [
    {"id": 1, "title": "Buy groceries", "done": False},
    {"id": 2, "title": "Write tests", "done": False},
]


@app.get("/", response_class=HTMLResponse)
async def index(request: Request):
    # TemplateResponse renders the Jinja2 template and returns HTML
    # First arg: template filename. Second: dict of variables available in the template.
    # "request" is always required by Jinja2Templates in FastAPI.
    return templates.TemplateResponse("index.html", {"request": request, "tasks": tasks})

hx-get and hx-post

These two attributes are the foundation of HTMX. Adding hx-get="/some-url" to an element tells HTMX to make a GET request to that URL when the element is triggered. Adding hx-post="/some-url" does the same but sends a POST. There is no JavaScript to write, no fetch() to call, and no event listeners to set up.

The default trigger for most elements is a click. HTMX is smart about the defaults for specific element types: on an input the default is the change event, and on a form it is submit. So adding hx-post="/tasks" to a form will fire when the user submits it, include all the form fields automatically, and swap the server's response into the page without any JavaScript.

What happens to the response? By default, HTMX takes the HTML response and puts it inside the element that made the request, replacing its children (innerHTML). You almost always want to override this with hx-target and hx-swap, which you'll learn in the next step. But knowing the default helps you understand what's happening when things don't look right.
html
<!-- Clicking this button makes a GET request to /tasks -->
<!-- The response HTML replaces the button's own content by default -->
<button
  hx-get="/tasks"
>
  Load Tasks
</button>

<!-- Clicking this marks task 1 as done via DELETE -->
<!-- HTMX supports all HTTP verbs: hx-get, hx-post, hx-put, hx-patch, hx-delete -->
<button
  hx-delete="/tasks/1"
>
  Delete Task 1
</button>
html
<!-- hx-post on a form fires on submit -->
<!-- HTMX serialises all form inputs into the POST body automatically -->
<form
  hx-post="/tasks"
>
  <input type="text" name="title" placeholder="New task...">
  <button type="submit">Add</button>
</form>

<!-- The FastAPI route receives "title" as a form field -->
<!-- It returns HTML (not JSON) and HTMX swaps it in -->
python
from fastapi import FastAPI, Request, Form
from fastapi.responses import HTMLResponse
from fastapi.templating import Jinja2Templates

app = FastAPI()
templates = Jinja2Templates(directory="templates")
tasks = []
next_id = 1


@app.get("/tasks", response_class=HTMLResponse)
async def get_tasks(request: Request):
    # Returns just the task list fragment, not a full page
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )


@app.post("/tasks", response_class=HTMLResponse)
async def create_task(request: Request, title: str = Form(...)):
    global next_id
    # Form(...) tells FastAPI to read "title" from the POST body, not from JSON
    tasks.append({"id": next_id, "title": title, "done": False})
    next_id += 1
    # Return the updated task list HTML — HTMX swaps it into the page
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )

hx-target and hx-swap

By default, HTMX puts the response HTML inside the element that made the request. That is rarely what you want. If a button triggers a GET request, you do not want the task list to appear inside the button. The hx-target attribute tells HTMX where to put the response instead. You give it a CSS selector like #task-list and HTMX finds that element on the page and uses it as the destination.

The hx-swap attribute controls how the response gets placed into the target. The default is innerHTML, which replaces everything inside the target. Other useful values are outerHTML to replace the target element itself, beforeend to append new content after the last child, and delete to remove the target element entirely when the server responds with nothing. Choosing the right swap mode is what makes individual rows appear, disappear, or update cleanly.

html
<!-- The form that adds a new task -->
<form
  hx-post="/tasks"
  hx-target="#task-list"   <!-- put the response in the element with id="task-list" -->
  hx-swap="innerHTML"     <!-- replace everything inside that element -->
>
  <input type="text" name="title" placeholder="New task...">
  <button type="submit">Add</button>
</form>

<!-- This is the container HTMX targets -->
<!-- Its content will be replaced with the server's HTML response -->
<ul id="task-list">
  {% for task in tasks %}
    <li>{{ task.title }}</li>
  {% endfor %}
</ul>

<!-- Appending to a list: swap="beforeend" adds one <li> at a time -->
<form
  hx-post="/tasks/append"
  hx-target="#task-list"
  hx-swap="beforeend"     <!-- append the new <li> after existing items -->
>
  <input type="text" name="title">
  <button type="submit">Append</button>
</form>

<!-- Delete a row: the route returns empty body, swap="outerHTML" removes the <li> -->
<li id="task-1">
  Buy groceries
  <button
    hx-delete="/tasks/1"
    hx-target="#task-1"
    hx-swap="outerHTML"    <!-- replace the entire <li> with the response -->
                            <!-- if the response is empty, the <li> disappears -->
  >Delete</button>
</li>
html
<!-- templates/partials/task_list.html -->
<!-- This is a fragment — no <html>, <head>, or <body> tags -->
<!-- FastAPI returns this from /tasks, HTMX puts it inside #task-list -->
{% for task in tasks %}
  <li id="task-{{ task.id }}">
    <span>{{ task.title }}</span>
    <button
      hx-delete="/tasks/{{ task.id }}"
      hx-target="#task-{{ task.id }}"
      hx-swap="outerHTML"
    >
      ✕
    </button>
  </li>
{% else %}
  <li class="empty">No tasks yet.</li>
{% endfor %}

hx-trigger

Every HTMX request needs something to trigger it. The default trigger depends on the element type: click for buttons and links, change for inputs, and submit for forms. The hx-trigger attribute lets you override this and pick any browser event, such as keyup, mouseenter, focus, or load. The load trigger fires immediately when the element appears on the page, which is useful for lazy-loading content.

The hx-trigger attribute also supports modifiers. The delay:300ms modifier waits 300 milliseconds after the event before making the request. Without this on a search box, every single keystroke would fire a separate request. The changed modifier skips the request if the input value has not changed since the last one. Combining them as hx-trigger="keyup changed delay:300ms" is the standard pattern for live search.

There is also a special trigger value called every 2s. This makes an element automatically fire a request every two seconds without any user action. It is useful for dashboards that need to show live data like active user counts, and it requires no extra infrastructure beyond your existing server.

html
<!-- Default: click. These two are identical -->
<button hx-get="/data">Load</button>
<button hx-get="/data" hx-trigger="click">Load</button>

<!-- keyup: fires on every keypress — too many requests -->
<input hx-get="/search" hx-trigger="keyup">

<!-- Better: delay waits 300ms after typing stops -->
<input hx-get="/search" hx-trigger="keyup delay:300ms">

<!-- Best: also add "changed" to skip requests if value didn't change -->
<!-- This is the standard live-search combination -->
<input
  name="q"
  hx-get="/search"
  hx-trigger="keyup changed delay:300ms"
  hx-target="#results"
  placeholder="Search tasks..."
>

<!-- load: fires immediately when the page renders — great for lazy loading -->
<div
  hx-get="/dashboard/stats"
  hx-trigger="load"
  hx-target="this"       <!-- "this" means the element itself -->
>
  Loading stats...
</div>

<!-- mouseenter: fires when the mouse moves over the element -->
<div hx-get="/preview/1" hx-trigger="mouseenter" hx-target="#preview-pane">
  Hover for preview
</div>
html
<!-- Polling: fires a GET request every 2 seconds automatically -->
<!-- The FastAPI route returns a fresh HTML fragment each time -->
<div
  hx-get="/dashboard/active-users"
  hx-trigger="every 2s"
  hx-swap="innerHTML"
>
  Loading...
</div>

<!-- FastAPI route — returns a tiny HTML snippet, called every 2 seconds -->

FastAPI Returning HTML Fragments

When HTMX makes a request, your FastAPI route must return HTML, not JSON. You return a small Jinja2 template that renders just the fragment HTMX needs, not a full page. This is why a partials folder exists in the project structure: it holds these small, focused template snippets.

A useful pattern is detecting whether a request came from HTMX or from a browser navigating directly to the URL. HTMX adds a header called HX-Request: true to every request it makes. You can check for this header in your route and return a fragment for HTMX requests and a full page for direct browser visits. This lets the same URL work in both cases, which matters for bookmarks and browser history.

python
from fastapi import FastAPI, Request, Form
from fastapi.responses import HTMLResponse
from fastapi.templating import Jinja2Templates

app = FastAPI()
templates = Jinja2Templates(directory="templates")

tasks = [
    {"id": 1, "title": "Buy groceries", "done": False},
    {"id": 2, "title": "Write tests", "done": False},
]


@app.get("/tasks", response_class=HTMLResponse)
async def get_tasks(request: Request):
    # Always return just the fragment — HTMX swaps it into #task-list
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )


@app.post("/tasks", response_class=HTMLResponse)
async def create_task(request: Request, title: str = Form(...)):
    # Form(...) reads "title" from the POST body (multipart form data)
    new_task = {"id": len(tasks) + 1, "title": title, "done": False}
    tasks.append(new_task)
    # Return updated task list — HTMX replaces #task-list content
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )


@app.delete("/tasks/{task_id}", response_class=HTMLResponse)
async def delete_task(task_id: int):
    global tasks
    tasks = [t for t in tasks if t["id"] != task_id]
    # Return empty string — with hx-swap="outerHTML" on the <li>,
    # an empty response causes the element to disappear from the DOM
    return HTMLResponse(content="")
html
<!-- templates/partials/task_list.html -->
<!-- Fragment: no html/head/body. Just the <li> items. -->
{% for task in tasks %}
  <li id="task-{{ task.id }}" class="task-item{% if task.done %} done{% endif %}">
    <span>{{ task.title }}</span>
    <button
      hx-delete="/tasks/{{ task.id }}"
      hx-target="#task-{{ task.id }}"
      hx-swap="outerHTML"
    >✕</button>
  </li>
{% else %}
  <li class="empty">No tasks. Add one above.</li>
{% endfor %}
python
@app.get("/tasks", response_class=HTMLResponse)
async def get_tasks(request: Request):
    # Check if the request came from HTMX by reading the HX-Request header
    # HTMX always sends this header; a browser navigation does not
    is_htmx = request.headers.get("HX-Request")

    if is_htmx:
        # HTMX request: return just the fragment
        return templates.TemplateResponse(
            "partials/task_list.html",
            {"request": request, "tasks": tasks}
        )
    else:
        # Direct browser navigation: return the full page
        return templates.TemplateResponse(
            "index.html",
            {"request": request, "tasks": tasks}
        )

Live Search

Live search is one of the most useful things you can build with HTMX, and it takes very little code. The whole feature is one input element with three attributes and one FastAPI route. The user types, HTMX waits for them to pause using the delay:300ms modifier, checks if the value actually changed with the changed modifier, and then makes a GET request with the search text. FastAPI queries the data, renders a fragment with the matching results, and HTMX swaps it into the results container. No debouncing function, no fetch(), no DOM manipulation needed.

The name="q" attribute on the input controls how the query is sent. When HTMX makes a GET request from an input, it includes the input's name and current value as a query parameter. Typing "buy" in an input named "q" triggers GET /search?q=buy. In FastAPI you receive this as a plain query parameter with an empty string as the default to handle the case where the user clears the field.

html
<!-- The live search input -->
<!-- hx-trigger fires on keyup, but waits 300ms after typing stops -->
<!-- "changed" ensures the request only fires if the value actually changed -->
<input
  type="search"
  name="q"                                            <!-- sent as ?q=... in the GET request -->
  hx-get="/search"                                    <!-- call this URL -->
  hx-trigger="keyup changed delay:300ms"             <!-- on keyup, debounced 300ms, only if changed -->
  hx-target="#search-results"                        <!-- put the response here -->
  hx-swap="innerHTML"                                 <!-- replace the container's content -->
  placeholder="Search tasks..."
>

<!-- Container where results appear -->
<ul id="search-results">
  <!-- HTMX fills this in as the user types -->
</ul>
python
@app.get("/search", response_class=HTMLResponse)
async def search(request: Request, q: str = ""):
    # q comes from the ?q= query parameter in the GET request
    # Default to empty string so clearing the field returns all tasks
    if q:
        # Filter tasks where the title contains the search term (case-insensitive)
        results = [
            t for t in tasks
            if q.lower() in t["title"].lower()
        ]
    else:
        # Empty query — return all tasks (or return nothing, your choice)
        results = tasks

    # Return only the fragment — HTMX replaces #search-results content
    return templates.TemplateResponse(
        "partials/search_results.html",
        {"request": request, "results": results, "q": q}
    )
html
<!-- templates/partials/search_results.html -->
<!-- Fragment: just <li> items, no outer wrapper needed -->
{% if results %}
  {% for task in results %}
    <li>
      <!-- Highlight the matching part of the title -->
      {{ task.title }}
      {% if task.done %}
        <span class="badge">Done</span>
      {% endif %}
    </li>
  {% endfor %}
{% elif q %}
  <!-- Only show "no results" message if the user actually typed something -->
  <li class="empty">No tasks matching "{{ q }}"</li>
{% endif %}

Forms Without Page Reload

A standard HTML form causes a full page reload when submitted. The browser navigates away, the server sends back a whole new page, and the browser renders it from scratch. With HTMX, submitting a form sends a request in the background. The page stays in place and only the targeted section updates.

One important pattern to get right is resetting the form after a successful submission. When the user adds a task, the input field should clear itself. HTMX does not reset forms automatically. The standard approach is to add hx-on::after-request="this.reset()" as an attribute on the form, which clears the fields after each successful request.

Sending JSON vs form data: By default, HTMX sends form submissions as multipart form data (same as a native HTML form). Your FastAPI route reads fields with Form(...). If you need to send JSON instead, you can use the hx-ext="json-enc" extension, but this requires an extra HTMX extension script tag. For most HTMX apps, plain form data is the right choice — it's simpler and consistent with how standard HTML works.
html
<!-- Add-task form with HTMX -->
<form
  hx-post="/tasks"               <!-- POST to this URL on submit -->
  hx-target="#task-list"        <!-- put the response in #task-list -->
  hx-swap="innerHTML"           <!-- replace the list's content -->
  hx-on::after-request="this.reset()"  <!-- clear the form after each submit -->
>
  <input
    type="text"
    name="title"               <!-- HTMX sends this as "title" in the POST body -->
    placeholder="New task..."
    required
    autofocus
  >
  <button type="submit">Add Task</button>
</form>

<!-- The task list container -->
<ul id="task-list">
  {% include "partials/task_list.html" %}
</ul>

<!-- Mark-done pattern: PATCH request on checkbox change -->
<li id="task-{{ task.id }}">
  <input
    type="checkbox"
    {% if task.done %}checked{% endif %}
    hx-patch="/tasks/{{ task.id }}/toggle"
    hx-target="#task-{{ task.id }}"
    hx-swap="outerHTML"         <!-- replace the entire <li> with the updated one -->
  >
  {{ task.title }}
</li>
python
@app.patch("/tasks/{task_id}/toggle", response_class=HTMLResponse)
async def toggle_task(request: Request, task_id: int):
    # Find the task and flip its done state
    task = next((t for t in tasks if t["id"] == task_id), None)
    if not task:
        return HTMLResponse("", status_code=404)

    task["done"] = not task["done"]  # toggle

    # Return just the updated <li> row — HTMX replaces the old one
    # hx-swap="outerHTML" on the checkbox means the entire <li> gets replaced
    return templates.TemplateResponse(
        "partials/task_row.html",
        {"request": request, "task": task}
    )

Loading Indicators and CSS Transitions

When HTMX makes a request, there is a brief moment while it waits for the server to respond. For routes that query a database or call an external service, this delay can be noticeable. Without feedback, users might think the button did not work and click it again. HTMX handles this by adding the CSS class htmx-request to the element that made the request while the request is in flight. You can use that class in your CSS to dim the button or change its text.

The htmx-indicator pattern lets you show a separate spinner element during requests. You create a spinner element and give it the class htmx-indicator. HTMX hides it by default using opacity 0 and reveals it while a request runs. Point an hx-indicator attribute at your spinner's CSS selector and HTMX connects them automatically. No JavaScript state or conditionals in your code are needed.

When HTMX inserts new content into the page, it briefly adds the class htmx-added to the newly inserted elements. You can use this with a CSS fade-in animation to make new items appear smoothly instead of popping in abruptly. This small CSS addition makes the whole interface feel noticeably more polished.

html
<!-- The spinner is hidden by default (htmx-indicator class sets opacity: 0) -->
<!-- hx-indicator="#spinner" on the form makes HTMX show it during the request -->
<form
  hx-post="/tasks"
  hx-target="#task-list"
  hx-swap="innerHTML"
  hx-indicator="#spinner"       <!-- show this element while the request is in-flight -->
  hx-on::after-request="this.reset()"
>
  <input type="text" name="title" placeholder="New task...">
  <button type="submit">Add</button>
  <!-- The spinner element — htmx-indicator class hides it by default -->
  <span id="spinner" class="htmx-indicator">⏳</span>
</form>

<!-- Task list — new items fade in via CSS on the htmx-added class -->
<ul id="task-list">
  {% include "partials/task_list.html" %}
</ul>
css
/* HTMX hides indicators by default with opacity 0 */
/* When a request is in-flight, it sets opacity 1 on the indicator */
.htmx-indicator {
  opacity: 0;
  transition: opacity 0.2s ease;
}

/* HTMX adds this class during the request, removing it when done */
.htmx-request .htmx-indicator,
.htmx-request.htmx-indicator {
  opacity: 1;
}

/* Fade in newly inserted content */
/* HTMX adds htmx-added to elements it just inserted into the DOM */
.htmx-added {
  animation: fadeIn 0.3s ease;
}

@keyframes fadeIn {
  from { opacity: 0; transform: translateY(-4px); }
  to   { opacity: 1; transform: translateY(0); }
}

/* Dim the button while the request is in-flight */
/* htmx-request is added to the element that made the request */
button.htmx-request {
  opacity: 0.6;
  cursor: not-allowed;
  pointer-events: none; /* prevent double-submit */
}
html
<!-- A button that shows "Loading..." while the request is in-flight -->
<!-- Uses two spans: one visible by default, one visible during htmx-request -->
<button
  hx-post="/tasks"
  hx-target="#task-list"
>
  <!-- Shown normally, hidden during request (CSS: .htmx-request .default-text) -->
  <span class="default-text">Add Task</span>

  <!-- Hidden by default, shown during request -->
  <span class="htmx-indicator">Adding...</span>
</button>

HTMX + WebSockets

HTMX can also connect to a WebSocket server. With the hx-ws attribute, HTMX keeps a persistent connection open to your FastAPI backend. When the server sends a message, HTMX expects it to be an HTML fragment and swaps it into the right element on the page automatically. Instead of the user triggering a request, the server pushes updates whenever something happens.

The setup requires loading the HTMX WebSocket extension as a second script tag. On the FastAPI side you write a normal WebSocket route. The only difference from a regular WebSocket is what you send back: HTML strings instead of JSON. HTMX receives them and swaps them into the page. The inserted HTML can even contain HTMX attributes of its own, so new content can trigger further requests.

A typical use: when a new task is created, the server broadcasts an HTML fragment with the new task row to every connected browser tab. Each tab receives the fragment and HTMX appends it to the task list. Every open tab sees the new task appear in real time, with no polling and no page refresh.

hx-ws="connect:/ws" opens the WebSocket connection. hx-ws="send" on a form inside the same element sends form data to the server via that WebSocket connection instead of HTTP. You can use connect and send together on the same element, or use them independently.
html
<!-- Load the WebSocket extension alongside main HTMX -->
<script src="https://unpkg.com/htmx.org@1.9.12"></script>
<script src="https://unpkg.com/htmx.org@1.9.12/dist/ext/ws.js"></script>

<!-- hx-ext="ws" activates the WebSocket extension for this element -->
<!-- hx-ws="connect:/ws" opens a WS connection to ws://localhost:8000/ws -->
<div
  hx-ext="ws"
  hx-ws="connect:/ws"

  <!-- When the server sends HTML here, HTMX looks for an element -->

from fastapi import FastAPI, WebSocket, WebSocketDisconnect
from typing import List
import json

app = FastAPI()

# All currently connected WebSocket clients
connections: List[WebSocket] = []


@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()       # complete the handshake
    connections.append(websocket)  # track this client
    try:
        while True:
            # Wait for a message from this client
            # HTMX sends form data as a JSON string: {"title": "Walk the dog", "HEADERS": {...}}
            data = await websocket.receive_text()
            payload = json.loads(data)

            # Extract the title field from the form submission
            title = payload.get("title", "").strip()
            if not title:
                continue

            # Build the HTML fragment for the new task row
            new_id = len(tasks) + 1
            tasks.append({"id": new_id, "title": title, "done": False})

            # Craft the HTML to broadcast — HTMX uses the id to find where to swap it
            # hx-swap-oob="beforeend:#task-list" appends to the list on all clients
            fragment = f"""
            <li id="task-{new_id}" hx-swap-oob="beforeend:#task-list">
                <span>{title}</span>
            </li>
            """

            # Broadcast to ALL connected clients (including the sender)
            dead = []
            for conn in list(connections):  # iterate a copy in case list changes
                try:
                    await conn.send_text(fragment)
                except:
                    dead.append(conn)  # mark disconnected clients for cleanup
            for conn in dead:
                connections.remove(conn)

    except WebSocketDisconnect:
        # Client closed the tab or lost connection — remove from list
        connections.remove(websocket)

# Out-of-band (OOB) swaps: the server sends HTML that targets elements
# anywhere on the page, not just the current WebSocket container.
# hx-swap-oob="beforeend:#task-list" means: append this <li> to #task-list,
# regardless of where the WebSocket container is in the DOM.

async def broadcast_new_task(task: dict):
    """Send a new task row to every connected browser."""
    # The fragment uses hx-swap-oob so HTMX puts it in #task-list
    fragment = f"""
    <li
      id="task-{task['id']}"
      hx-swap-oob="beforeend:#task-list"
    >
      <span>{task['title']}</span>
      <button
        hx-delete="/tasks/{task['id']}"
        hx-target="#task-{task['id']}"
        hx-swap="outerHTML"
      >✕</button>
    </li>
    """

    dead = []
    for conn in list(connections):
        try:
            await conn.send_text(fragment)
        except:
            dead.append(conn)
    for conn in dead:
        connections.remove(conn)
