HTMX + FastAPI

Build dynamic, interactive UIs without writing JavaScript. HTMX lets HTML attributes trigger HTTP requests and swap content on the page — your FastAPI routes return HTML fragments instead of JSON, and HTMX puts them exactly where you want them.

1

What is HTMX?

Modern web development has a dirty secret: most of the JavaScript people write is just plumbing. You fetch data from an API, loop over the results, construct HTML strings, and stuff them into the DOM. It's the same pattern every time. React and Vue exist to manage this complexity, but they bring their own massive complexity — a build step, a bundler, component lifecycles, a virtual DOM, state management libraries, and hundreds of kilobytes of JavaScript before your app even starts. For many apps, especially server-rendered ones, this is enormous overkill.

HTMX takes a radically different approach: it extends HTML itself. Instead of writing JavaScript to call fetch() and then update the DOM, you add attributes directly to your HTML elements — hx-get="/tasks", hx-target="#task-list", hx-swap="innerHTML". HTMX reads these attributes, makes the HTTP request for you, and puts the server's response exactly where you told it to. Your FastAPI route doesn't return JSON — it returns a small chunk of HTML, called a fragment. HTMX swaps that fragment into the page. The result feels like a single-page app but your server just renders templates, exactly like it always did.

The philosophy is that HTML is already a powerful language for describing user interfaces. A link (<a href>) causes a GET request. A form (<form action method="post">) causes a POST request. HTMX just extends those ideas: any element can make any HTTP request, and the response can go anywhere on the page. You get the interactivity of JavaScript with almost none of the JavaScript. The entire HTMX library is about 14KB minified — smaller than a single React component in some projects.

What HTMX is not: It's not for apps that need heavy client-side state — think spreadsheets, real-time collaborative editors, complex data visualisations. For apps that are primarily about displaying and updating server-side data — task managers, dashboards, admin panels, CRMs — HTMX is a perfect fit. If your app was happily using Jinja2 templates, HTMX makes it dramatically more interactive with minimal effort.

Project Setup

HTMX is a single JavaScript file. You load it from a CDN with one script tag — no npm, no bundler, no build step. On the backend you need FastAPI, Uvicorn, and Jinja2. Jinja2 is the template engine that lets FastAPI render HTML files and inject Python variables into them. The project structure mirrors a standard server-rendered app: a templates/ folder for your HTML files and a static/ folder for CSS and images.

The key concept to grasp before writing any code: in an HTMX app, you have two kinds of templates. Full page templates render the entire HTML skeleton — the <html>, <head>, <body>, sidebar, navigation, everything. Fragment templates are tiny, partial HTML snippets — just a <ul> full of <li> items, or a single updated row, or a success message. HTMX requests return fragments. Browser navigation returns full pages. You'll create both kinds, and often a single Jinja2 template can do double duty using template inheritance and blocks.

python
from fastapi import FastAPI, Request
from fastapi.responses import HTMLResponse
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

app = FastAPI()

# Serve anything in static/ at the /static URL prefix
app.mount("/static", StaticFiles(directory="static"), name="static")

# Tell FastAPI where to find HTML template files
templates = Jinja2Templates(directory="templates")

# In-memory task list — we'll swap this for a database later
tasks = [
    {"id": 1, "title": "Buy groceries", "done": False},
    {"id": 2, "title": "Write tests", "done": False},
]


@app.get("/", response_class=HTMLResponse)
async def index(request: Request):
    # TemplateResponse renders the Jinja2 template and returns HTML
    # First arg: template filename. Second: dict of variables available in the template.
    # "request" is always required by Jinja2Templates in FastAPI.
    return templates.TemplateResponse("index.html", {"request": request, "tasks": tasks})

hx-get and hx-post

These two attributes are the foundation of HTMX. hx-get="/some-url" tells HTMX: when this element is triggered (clicked, by default), make a GET request to that URL and do something with the HTML response. hx-post="/some-url" does the same but sends a POST request. That's it. No JavaScript, no fetch(), no event listeners. Just an attribute on an HTML element.

The default trigger for most elements is a click. But HTMX is smart about defaults: on an <input>, the default trigger is the change event. On a <form>, it's submit. So hx-post="/tasks" on a form will fire when the user submits it, automatically include all the form fields in the POST body, and swap the response into the page — all without writing a single line of JavaScript.

What happens to the response? By default, HTMX takes the HTML response and puts it inside the element that made the request, replacing its children (innerHTML). You almost always want to override this with hx-target and hx-swap, which you'll learn in the next step. But knowing the default helps you understand what's happening when things don't look right.
html
<!-- Clicking this button makes a GET request to /tasks -->
<!-- The response HTML replaces the button's own content by default -->
<button
  hx-get="/tasks"
>
  Load Tasks
</button>

<!-- Clicking this marks task 1 as done via DELETE -->
<!-- HTMX supports all HTTP verbs: hx-get, hx-post, hx-put, hx-patch, hx-delete -->
<button
  hx-delete="/tasks/1"
>
  Delete Task 1
</button>
html
<!-- hx-post on a form fires on submit -->
<!-- HTMX serialises all form inputs into the POST body automatically -->
<form
  hx-post="/tasks"
>
  <input type="text" name="title" placeholder="New task...">
  <button type="submit">Add</button>
</form>

<!-- The FastAPI route receives "title" as a form field -->
<!-- It returns HTML (not JSON) and HTMX swaps it in -->
python
from fastapi import FastAPI, Request, Form
from fastapi.responses import HTMLResponse
from fastapi.templating import Jinja2Templates

app = FastAPI()
templates = Jinja2Templates(directory="templates")
tasks = []
next_id = 1


@app.get("/tasks", response_class=HTMLResponse)
async def get_tasks(request: Request):
    # Returns just the task list fragment, not a full page
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )


@app.post("/tasks", response_class=HTMLResponse)
async def create_task(request: Request, title: str = Form(...)):
    global next_id
    # Form(...) tells FastAPI to read "title" from the POST body, not from JSON
    tasks.append({"id": next_id, "title": title, "done": False})
    next_id += 1
    # Return the updated task list HTML — HTMX swaps it into the page
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )

hx-target and hx-swap

By default, HTMX puts the response HTML inside the element that made the request. That's rarely what you want — if a button triggers a GET request, you don't want the task list to appear inside the button. hx-target tells HTMX where to put the response instead. You give it a CSS selector, and HTMX finds that element on the page and uses it as the destination. The most common pattern is hx-target="#some-id" — you give a container a unique ID and point HTMX at it.

hx-swap controls exactly how the response HTML gets placed into the target. The default is innerHTML, which replaces everything inside the target with the new HTML. Other useful values: outerHTML replaces the target element itself (useful for updating a single row); beforeend appends the new HTML after the target's last child (useful for adding to a list); afterbegin prepends it; delete removes the target element entirely (useful for "remove this item" actions where the server responds with nothing); none does nothing with the response body but still processes response headers (useful for triggering other events).

html
<!-- The form that adds a new task -->
<form
  hx-post="/tasks"
  hx-target="#task-list"   <!-- put the response in the element with id="task-list" -->
  hx-swap="innerHTML"     <!-- replace everything inside that element -->
>
  <input type="text" name="title" placeholder="New task...">
  <button type="submit">Add</button>
</form>

<!-- This is the container HTMX targets -->
<!-- Its content will be replaced with the server's HTML response -->
<ul id="task-list">
  {% for task in tasks %}
    <li>{{ task.title }}</li>
  {% endfor %}
</ul>

<!-- Appending to a list: swap="beforeend" adds one <li> at a time -->
<form
  hx-post="/tasks/append"
  hx-target="#task-list"
  hx-swap="beforeend"     <!-- append the new <li> after existing items -->
>
  <input type="text" name="title">
  <button type="submit">Append</button>
</form>

<!-- Delete a row: the route returns empty body, swap="outerHTML" removes the <li> -->
<li id="task-1">
  Buy groceries
  <button
    hx-delete="/tasks/1"
    hx-target="#task-1"
    hx-swap="outerHTML"    <!-- replace the entire <li> with the response -->
                            <!-- if the response is empty, the <li> disappears -->
  >Delete</button>
</li>
html
<!-- templates/partials/task_list.html -->
<!-- This is a fragment — no <html>, <head>, or <body> tags -->
<!-- FastAPI returns this from /tasks, HTMX puts it inside #task-list -->
{% for task in tasks %}
  <li id="task-{{ task.id }}">
    <span>{{ task.title }}</span>
    <button
      hx-delete="/tasks/{{ task.id }}"
      hx-target="#task-{{ task.id }}"
      hx-swap="outerHTML"
    >
      ✕
    </button>
  </li>
{% else %}
  <li class="empty">No tasks yet.</li>
{% endfor %}

hx-trigger

Every HTMX request needs something to trigger it. The default trigger depends on the element — click for buttons and links, change for inputs and selects, submit for forms. hx-trigger lets you override this and specify exactly what event fires the request. You can use any browser event: keyup, mouseenter, focus, or even load (which fires immediately when the element appears on the page, useful for lazy-loading).

hx-trigger also supports modifiers that add intelligent behaviour. delay:300ms waits 300 milliseconds after the event fires before making the request — essential for keyup on a search box, because without it every single keystroke fires a request. changed is another modifier that prevents the request if the input value hasn't actually changed since the last request — so tabbing in and out of a field without typing anything doesn't fire a request. You can combine them: hx-trigger="keyup changed delay:300ms" is the standard live-search pattern.

There's also a special trigger value: every 2s turns an element into a polling machine — it fires a request every 2 seconds automatically. This is useful for dashboards showing live data like CPU stats or active users, where you want the server to push updates without using WebSockets. It's a blunt instrument but requires zero infrastructure.

html
<!-- Default: click. These two are identical -->
<button hx-get="/data">Load</button>
<button hx-get="/data" hx-trigger="click">Load</button>

<!-- keyup: fires on every keypress — too many requests -->
<input hx-get="/search" hx-trigger="keyup">

<!-- Better: delay waits 300ms after typing stops -->
<input hx-get="/search" hx-trigger="keyup delay:300ms">

<!-- Best: also add "changed" to skip requests if value didn't change -->
<!-- This is the standard live-search combination -->
<input
  name="q"
  hx-get="/search"
  hx-trigger="keyup changed delay:300ms"
  hx-target="#results"
  placeholder="Search tasks..."
>

<!-- load: fires immediately when the page renders — great for lazy loading -->
<div
  hx-get="/dashboard/stats"
  hx-trigger="load"
  hx-target="this"       <!-- "this" means the element itself -->
>
  Loading stats...
</div>

<!-- mouseenter: fires when the mouse moves over the element -->
<div hx-get="/preview/1" hx-trigger="mouseenter" hx-target="#preview-pane">
  Hover for preview
</div>
html
<!-- Polling: fires a GET request every 2 seconds automatically -->
<!-- The FastAPI route returns a fresh HTML fragment each time -->
<div
  hx-get="/dashboard/active-users"
  hx-trigger="every 2s"
  hx-swap="innerHTML"
>
  Loading...
</div>

<!-- FastAPI route — returns a tiny HTML snippet, called every 2 seconds -->

FastAPI Returning HTML Fragments

This is the backend side of the HTMX equation. When HTMX makes a request, your FastAPI route must return HTML, not JSON. For routes that serve HTMX requests, you return a small Jinja2 template that renders just the HTML fragment HTMX needs — not a full page, just the piece that belongs in the target element. This is why the partials folder exists in your project structure: it holds these small, single-purpose template snippets.

A very useful pattern is detecting whether a request came from HTMX or from a browser navigating directly. HTMX automatically adds a request header called HX-Request: true to every request it makes. You can check for this header in your FastAPI route and respond with either a full page (for direct navigation) or a fragment (for HTMX). This lets the same URL serve both use cases, which is important for browser history, bookmarkability, and graceful degradation when JavaScript is disabled.

python
from fastapi import FastAPI, Request, Form
from fastapi.responses import HTMLResponse
from fastapi.templating import Jinja2Templates

app = FastAPI()
templates = Jinja2Templates(directory="templates")

tasks = [
    {"id": 1, "title": "Buy groceries", "done": False},
    {"id": 2, "title": "Write tests", "done": False},
]


@app.get("/tasks", response_class=HTMLResponse)
async def get_tasks(request: Request):
    # Always return just the fragment — HTMX swaps it into #task-list
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )


@app.post("/tasks", response_class=HTMLResponse)
async def create_task(request: Request, title: str = Form(...)):
    # Form(...) reads "title" from the POST body (multipart form data)
    new_task = {"id": len(tasks) + 1, "title": title, "done": False}
    tasks.append(new_task)
    # Return updated task list — HTMX replaces #task-list content
    return templates.TemplateResponse(
        "partials/task_list.html",
        {"request": request, "tasks": tasks}
    )


@app.delete("/tasks/{task_id}", response_class=HTMLResponse)
async def delete_task(task_id: int):
    global tasks
    tasks = [t for t in tasks if t["id"] != task_id]
    # Return empty string — with hx-swap="outerHTML" on the <li>,
    # an empty response causes the element to disappear from the DOM
    return HTMLResponse(content="")
html
<!-- templates/partials/task_list.html -->
<!-- Fragment: no html/head/body. Just the <li> items. -->
{% for task in tasks %}
  <li id="task-{{ task.id }}" class="task-item{% if task.done %} done{% endif %}">
    <span>{{ task.title }}</span>
    <button
      hx-delete="/tasks/{{ task.id }}"
      hx-target="#task-{{ task.id }}"
      hx-swap="outerHTML"
    >✕</button>
  </li>
{% else %}
  <li class="empty">No tasks. Add one above.</li>
{% endfor %}
python
@app.get("/tasks", response_class=HTMLResponse)
async def get_tasks(request: Request):
    # Check if the request came from HTMX by reading the HX-Request header
    # HTMX always sends this header; a browser navigation does not
    is_htmx = request.headers.get("HX-Request")

    if is_htmx:
        # HTMX request: return just the fragment
        return templates.TemplateResponse(
            "partials/task_list.html",
            {"request": request, "tasks": tasks}
        )
    else:
        # Direct browser navigation: return the full page
        return templates.TemplateResponse(
            "index.html",
            {"request": request, "tasks": tasks}
        )

Live Search

Live search is the most compelling demonstration of what HTMX can do, and it's also the clearest illustration of how little code it takes. The entire feature is one input element with three attributes and one FastAPI route. The user types, HTMX waits for them to stop (the delay:300ms modifier), checks whether the value changed (the changed modifier), then makes a GET request to your search route with the query string. FastAPI queries the data, renders a fragment containing only the matching results, and HTMX swaps it into the target container. The user sees results appear as they type. No debouncing function, no fetch(), no DOM manipulation, no state management.

The name="q" attribute on the input is the key to how the query gets sent. When HTMX makes a GET request from an input element, it includes the input's name and value as query parameters. So typing "buy" in an input named "q" triggers GET /search?q=buy. In FastAPI, you receive this with a plain query parameter: async def search(q: str = ""). The empty string default handles the case where the user clears the field entirely.

html
<!-- The live search input -->
<!-- hx-trigger fires on keyup, but waits 300ms after typing stops -->
<!-- "changed" ensures the request only fires if the value actually changed -->
<input
  type="search"
  name="q"                                            <!-- sent as ?q=... in the GET request -->
  hx-get="/search"                                    <!-- call this URL -->
  hx-trigger="keyup changed delay:300ms"             <!-- on keyup, debounced 300ms, only if changed -->
  hx-target="#search-results"                        <!-- put the response here -->
  hx-swap="innerHTML"                                 <!-- replace the container's content -->
  placeholder="Search tasks..."
>

<!-- Container where results appear -->
<ul id="search-results">
  <!-- HTMX fills this in as the user types -->
</ul>
python
@app.get("/search", response_class=HTMLResponse)
async def search(request: Request, q: str = ""):
    # q comes from the ?q= query parameter in the GET request
    # Default to empty string so clearing the field returns all tasks
    if q:
        # Filter tasks where the title contains the search term (case-insensitive)
        results = [
            t for t in tasks
            if q.lower() in t["title"].lower()
        ]
    else:
        # Empty query — return all tasks (or return nothing, your choice)
        results = tasks

    # Return only the fragment — HTMX replaces #search-results content
    return templates.TemplateResponse(
        "partials/search_results.html",
        {"request": request, "results": results, "q": q}
    )
html
<!-- templates/partials/search_results.html -->
<!-- Fragment: just <li> items, no outer wrapper needed -->
{% if results %}
  {% for task in results %}
    <li>
      <!-- Highlight the matching part of the title -->
      {{ task.title }}
      {% if task.done %}
        <span class="badge">Done</span>
      {% endif %}
    </li>
  {% endfor %}
{% elif q %}
  <!-- Only show "no results" message if the user actually typed something -->
  <li class="empty">No tasks matching "{{ q }}"</li>
{% endif %}

Forms Without Page Reload

Standard HTML forms cause a full page reload on submit. You click submit, the browser navigates to the action URL, the server responds with a complete page, and the browser renders it from scratch. For a task manager, this means after every form submission the user sees the page flash and reload. With HTMX, form submission triggers an HTTP request in the background — the page stays where it is, only the targeted section updates.

There's one important pattern to get right with HTMX forms: resetting the form after a successful submission. When the user adds a task, the input field should clear itself. HTMX doesn't reset forms automatically. The standard approach is to return hx-on::after-request="this.reset()" as an attribute on the form, or better, to use a Jinja2 trick: return a fresh empty form along with the updated task list. This way the form is replaced by an identical-but-empty copy of itself.

Sending JSON vs form data: By default, HTMX sends form submissions as multipart form data (same as a native HTML form). Your FastAPI route reads fields with Form(...). If you need to send JSON instead, you can use the hx-ext="json-enc" extension, but this requires an extra HTMX extension script tag. For most HTMX apps, plain form data is the right choice — it's simpler and consistent with how standard HTML works.
html
<!-- Add-task form with HTMX -->
<form
  hx-post="/tasks"               <!-- POST to this URL on submit -->
  hx-target="#task-list"        <!-- put the response in #task-list -->
  hx-swap="innerHTML"           <!-- replace the list's content -->
  hx-on::after-request="this.reset()"  <!-- clear the form after each submit -->
>
  <input
    type="text"
    name="title"               <!-- HTMX sends this as "title" in the POST body -->
    placeholder="New task..."
    required
    autofocus
  >
  <button type="submit">Add Task</button>
</form>

<!-- The task list container -->
<ul id="task-list">
  {% include "partials/task_list.html" %}
</ul>

<!-- Mark-done pattern: PATCH request on checkbox change -->
<li id="task-{{ task.id }}">
  <input
    type="checkbox"
    {% if task.done %}checked{% endif %}
    hx-patch="/tasks/{{ task.id }}/toggle"
    hx-target="#task-{{ task.id }}"
    hx-swap="outerHTML"         <!-- replace the entire <li> with the updated one -->
  >
  {{ task.title }}
</li>
python
@app.patch("/tasks/{task_id}/toggle", response_class=HTMLResponse)
async def toggle_task(request: Request, task_id: int):
    # Find the task and flip its done state
    task = next((t for t in tasks if t["id"] == task_id), None)
    if not task:
        return HTMLResponse("", status_code=404)

    task["done"] = not task["done"]  # toggle

    # Return just the updated <li> row — HTMX replaces the old one
    # hx-swap="outerHTML" on the checkbox means the entire <li> gets replaced
    return templates.TemplateResponse(
        "partials/task_row.html",
        {"request": request, "task": task}
    )

Loading Indicators and CSS Transitions

When HTMX makes a request, there's a brief moment between the user action and the response arriving. For fast local servers, this is imperceptible. But for real routes that call a database or an external API, there can be a noticeable delay. Without any feedback, the user might think the button didn't work and click it again. HTMX has a built-in system for this: while any HTMX request is in-flight, it adds the CSS class htmx-request to the element that made the request. You can use this class in your CSS to show a spinner, change the button text, or dim the container.

The htmx-indicator pattern goes further: you create a separate element (usually a spinner SVG or animated dots) and give it the class htmx-indicator. HTMX hides it by default (opacity 0) and shows it (opacity 1) while any request is in-flight. You control which request shows which indicator using the hx-indicator attribute, pointing it at your spinner element's CSS selector. This is clean because the spinner is just an HTML element and a CSS class — no JavaScript state, no conditionals in your frontend code.

CSS transitions on HTMX swaps make the UI feel polished. When HTMX inserts new content, it briefly adds the class htmx-added to newly inserted elements. You can use this with a CSS keyframe animation to fade new items in. The swap also briefly has htmx-swapping on the outgoing content, letting you animate it out before the new content arrives. A simple transition: opacity 0.2s on your task items transforms the experience from abrupt replacement to smooth update.

html
<!-- The spinner is hidden by default (htmx-indicator class sets opacity: 0) -->
<!-- hx-indicator="#spinner" on the form makes HTMX show it during the request -->
<form
  hx-post="/tasks"
  hx-target="#task-list"
  hx-swap="innerHTML"
  hx-indicator="#spinner"       <!-- show this element while the request is in-flight -->
  hx-on::after-request="this.reset()"
>
  <input type="text" name="title" placeholder="New task...">
  <button type="submit">Add</button>
  <!-- The spinner element — htmx-indicator class hides it by default -->
  <span id="spinner" class="htmx-indicator">⏳</span>
</form>

<!-- Task list — new items fade in via CSS on the htmx-added class -->
<ul id="task-list">
  {% include "partials/task_list.html" %}
</ul>
css
/* HTMX hides indicators by default with opacity 0 */
/* When a request is in-flight, it sets opacity 1 on the indicator */
.htmx-indicator {
  opacity: 0;
  transition: opacity 0.2s ease;
}

/* HTMX adds this class during the request, removing it when done */
.htmx-request .htmx-indicator,
.htmx-request.htmx-indicator {
  opacity: 1;
}

/* Fade in newly inserted content */
/* HTMX adds htmx-added to elements it just inserted into the DOM */
.htmx-added {
  animation: fadeIn 0.3s ease;
}

@keyframes fadeIn {
  from { opacity: 0; transform: translateY(-4px); }
  to   { opacity: 1; transform: translateY(0); }
}

/* Dim the button while the request is in-flight */
/* htmx-request is added to the element that made the request */
button.htmx-request {
  opacity: 0.6;
  cursor: not-allowed;
  pointer-events: none; /* prevent double-submit */
}
html
<!-- A button that shows "Loading..." while the request is in-flight -->
<!-- Uses two spans: one visible by default, one visible during htmx-request -->
<button
  hx-post="/tasks"
  hx-target="#task-list"

HTMX + WebSockets

HTMX can also connect to a WebSocket server, and this is where it becomes genuinely powerful for real-time features. With the hx-ws attribute, HTMX maintains a persistent WebSocket connection to your FastAPI backend. When the server sends a message, HTMX expects it to be an HTML fragment and swaps it into the target element on the page — automatically, without any JavaScript. This is the opposite of the HTMX request model: instead of the user triggering a request, the server pushes updates to the client whenever it wants.

The setup requires the HTMX WebSocket extension, which is a separate script tag alongside the main HTMX script. On the FastAPI side, you write a normal WebSocket route — the same as you'd write without HTMX. The only difference is what you send: instead of JSON, you send HTML strings. HTMX receives them and swaps them into the page. The HTML you send can include HTMX attributes itself, so dynamically inserted content can also make requests — the whole system is composable.

A typical pattern: when a new task is created, the server broadcasts an HTML fragment containing the new task row to all connected WebSocket clients. Each browser tab receives the fragment and HTMX appends it to the task list. Every tab sees the new task appear in real-time, with no polling, no page refresh, and no JavaScript beyond loading the HTMX library.

hx-ws="connect:/ws" opens the WebSocket connection. hx-ws="send" on a form inside the same element sends form data to the server via that WebSocket connection instead of HTTP. You can use connect and send together on the same element, or use them independently.

  <!-- whose id matches the id in the message and swaps it in -->

  <!-- Task list: server pushes new <li>s that get appended here -->

  </ul>

  <form hx-ws="send">

    <button type="submit">Add</button>
  </form>
</div>
python
from fastapi import FastAPI, WebSocket, WebSocketDisconnect
from typing import List
import json

app = FastAPI()

# All currently connected WebSocket clients
connections: List[WebSocket] = []


@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()       # complete the handshake
    connections.append(websocket)  # track this client
    try:
        while True:
            # Wait for a message from this client
            # HTMX sends form data as a JSON string: {"title": "Walk the dog", "HEADERS": {...}}
            data = await websocket.receive_text()
            payload = json.loads(data)

            # Extract the title field from the form submission
            title = payload.get("title", "").strip()
            if not title:
                continue

            # Build the HTML fragment for the new task row
            new_id = len(tasks) + 1
            tasks.append({"id": new_id, "title": title, "done": False})

            # Craft the HTML to broadcast — HTMX uses the id to find where to swap it
            # hx-swap-oob="beforeend:#task-list" appends to the list on all clients
            fragment = f"""
            <li id="task-{new_id}" hx-swap-oob="beforeend:#task-list">
                <span>{title}</span>
            </li>
            """

            # Broadcast to ALL connected clients (including the sender)
            dead = []
            for conn in list(connections):  # iterate a copy in case list changes
                try:
                    await conn.send_text(fragment)
                except:
                    dead.append(conn)  # mark disconnected clients for cleanup
            for conn in dead:
                connections.remove(conn)

    except WebSocketDisconnect:
        # Client closed the tab or lost connection — remove from list
        connections.remove(websocket)

# Out-of-band (OOB) swaps: the server sends HTML that targets elements
# anywhere on the page, not just the current WebSocket container.
# hx-swap-oob="beforeend:#task-list" means: append this <li> to #task-list,
# regardless of where the WebSocket container is in the DOM.

async def broadcast_new_task(task: dict):
    """Send a new task row to every connected browser."""
    # The fragment uses hx-swap-oob so HTMX puts it in #task-list
    fragment = f"""
    <li
      id="task-{task['id']}"
      hx-swap-oob="beforeend:#task-list"
    >
      <span>{task['title']}</span>
      <button
        hx-delete="/tasks/{task['id']}"
        hx-target="#task-{task['id']}"
        hx-swap="outerHTML"
      >✕</button>
    </li>
    """

    dead = []
    for conn in list(connections):
        try:
            await conn.send_text(fragment)
        except:
            dead.append(conn)
    for conn in dead:
        connections.remove(conn)
