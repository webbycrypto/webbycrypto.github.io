API Documentation in FastAPI

FastAPI generates interactive docs automatically. Covers Swagger UI, ReDoc, customising route descriptions, response schemas, tags, versioning, and disabling docs in production.

1

Docs Out of the Box

FastAPI reads your route decorators and Pydantic models and builds an OpenAPI specification automatically. That specification powers two built-in doc UIs: Swagger UI at /docs (interactive, lets you send test requests) and ReDoc at /redoc (clean reading view). No extra packages, no configuration — they are on by default.

python
from fastapi import FastAPI

app = FastAPI()

@app.get("/users")
def list_users():
    return ["alice", "bob"]

@app.get("/items/{item_id}")
def get_item(item_id: int):
    return {"id": item_id}

# Swagger UI  — interactive, lets you send requests
# http://localhost:8000/docs

# ReDoc       — clean reading view, great for sharing
# http://localhost:8000/redoc

# Raw OpenAPI JSON — consumed by tools and generators
# http://localhost:8000/openapi.json
text
// Snippet from http://localhost:8000/openapi.json
{
  "openapi": "3.1.0",
  "info": { "title": "FastAPI", "version": "0.1.0" },
  "paths": {
    "/users": {
      "get": {
        "operationId": "list_users_users_get",
        // operationId is derived from the function name + path
        "responses": {
          "200": { "description": "Successful Response" }
        }
      }
    },
    "/items/{item_id}": {
      "get": {
        "operationId": "get_item_items__item_id__get",
        "parameters": [
          {
            "name": "item_id",
            "in": "path",
            "required": true,
            "schema": { "type": "integer" }
            // FastAPI inferred the type from the int annotation
          }
        ]
      }
    }
  }
}

Summary and Description

Every route in Swagger shows a one-line summary and an optional longer description. FastAPI reads these directly from the function's docstring and from the summary= and description= arguments on the decorator. Use the docstring for longer explanations — it supports Markdown.

python
from fastapi import FastAPI

app = FastAPI()

@app.get("/users/{user_id}")
def get_user(user_id: int):
    """
    ## Get a single user

    Returns the **full profile** for one user by their numeric ID.

    - Raises `404` if the user does not exist
    - The `password` field is never included in the response
    - Markdown is rendered directly in Swagger UI
    """
    return {"id": user_id, "name": "Alice"}

# FastAPI uses the first line of the docstring as the summary
# and the remaining lines as the longer description in /docs
python
from fastapi import FastAPI

app = FastAPI()

@app.get(
    "/users/{user_id}",
    summary="Get a single user",
    description="""
Returns the **full profile** for one user by their numeric ID.

- Raises `404` if the user does not exist
- The `password` field is never included in the response
""",
)
def get_user(user_id: int):
    return {"id": user_id, "name": "Alice"}

# If both a docstring AND summary=/description= are provided,
# the decorator arguments take precedence over the docstring.

Response Schema

The response_model argument tells FastAPI which Pydantic model describes the response body. FastAPI uses this to generate the schema in /docs and to filter out any extra fields before sending the response. If a route can return different things, you can use response_model=List[Item] or leave it off and document the shape manually.

python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

# Internal model — has password field
class User(BaseModel):
    id: int
    name: str
    email: str
    password: str

# Public response model — password deliberately excluded
class UserOut(BaseModel):
    id: int
    name: str
    email: str

@app.get("/users/{user_id}", response_model=UserOut)
def get_user(user_id: int):
    # Return a User with a password — FastAPI strips it automatically
    # because UserOut does not include that field
    return User(id=user_id, name="Alice", email="alice@example.com", password="secret")

# /docs shows only id, name, email in the response schema
python
from fastapi import FastAPI
from pydantic import BaseModel
from typing import List

app = FastAPI()

class UserOut(BaseModel):
    id: int
    name: str
    email: str

# response_model accepts any valid type annotation, including List
@app.get("/users", response_model=List[UserOut])
def list_users():
    return [
        {"id": 1, "name": "Alice", "email": "alice@example.com"},
        {"id": 2, "name": "Bob", "email": "bob@example.com"},
    ]

# Generated JSON schema in /docs:
// {
//   "type": "array",
//   "items": {
//     "$ref": "#/components/schemas/UserOut"
//   }
// }

Multiple Responses

Routes often return different HTTP status codes depending on what happens. The responses= argument documents each possible response with its status code, description, and schema. This does not change the actual behavior, it only adds the documentation so callers know what to expect.

python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class UserOut(BaseModel):
    id: int
    name: str

class ErrorDetail(BaseModel):
    detail: str

@app.get(
    "/users/{user_id}",
    response_model=UserOut,
    responses={
        404: {
            "description": "User not found",
            "model": ErrorDetail,
        },
        422: {
            "description": "Validation error — user_id must be a positive integer",
        },
    },
)
def get_user(user_id: int):
    if user_id != 1:
        raise HTTPException(status_code=404, detail="User not found")
    return UserOut(id=1, name="Alice")

# The 200 response comes from response_model=UserOut automatically.
# The responses= dict adds additional status codes to the docs.
python
from pydantic import BaseModel

# Define a structured error model so Swagger shows the exact shape
class ErrorDetail(BaseModel):
    detail: str

# /docs will render the 404 schema as:
// {
//   "description": "User not found",
//   "content": {
//     "application/json": {
//       "schema": {
//         "$ref": "#/components/schemas/ErrorDetail"
//       }
//     }
//   }
// }

# Tip: you can reuse the same ErrorDetail model across many routes.
# FastAPI de-duplicates it in the components/schemas section of
# openapi.json so it only appears once.

Tags and Groups

Without tags, all routes appear in a single flat list in /docs. Tags group routes by resource type so the docs are easy to navigate. You can set a tag on each individual route or on an entire router with a prefix.

python
from fastapi import FastAPI

app = FastAPI()

# These two routes will appear in a "users" section in /docs
@app.get("/users", tags=["users"])
def list_users():
    return []

@app.get("/users/{user_id}", tags=["users"])
def get_user(user_id: int):
    return {"id": user_id}

# These two routes appear in a separate "items" section
@app.get("/items", tags=["items"])
def list_items():
    return []

@app.post("/items", tags=["items"])
def create_item():
    return {}
python
from fastapi import FastAPI, APIRouter

app = FastAPI()

# Every route added to this router automatically gets the "users" tag
# and the /users URL prefix — no need to repeat them on each route
users_router = APIRouter(prefix="/users", tags=["users"])

@users_router.get("")
def list_users():
    return []

@users_router.get("/{user_id}")
def get_user(user_id: int):
    return {"id": user_id}

items_router = APIRouter(prefix="/items", tags=["items"])

@items_router.get("")
def list_items():
    return []

# Include both routers into the main app
app.include_router(users_router)
app.include_router(items_router)

Examples in Schema

Swagger UI shows the schema for request bodies, but it is even more useful when it shows a real filled-in example. You can add examples to Pydantic Field() calls and they appear directly in the /docs Try it out panel.

python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class CreateUser(BaseModel):
    name: str = Field(
        description="The user's full display name",
        examples=["Alice Nguyen"],
    )
    email: str = Field(
        description="A valid email address — used for login",
        examples=["alice@example.com"],
    )
    password: str = Field(
        description="Minimum 8 characters",
        examples=["hunter2secure"],
        min_length=8,
    )

@app.post("/users")
def create_user(user: CreateUser):
    return {"id": 1, "name": user.name}

# /docs pre-fills each field with its example value
# when the user clicks "Try it out"
python
from fastapi import FastAPI, Body
from pydantic import BaseModel
from typing import Annotated

app = FastAPI()

class CreateUser(BaseModel):
    name: str
    email: str

# openapi_examples provides named examples shown as a dropdown
# in the Swagger UI "Try it out" panel
@app.post("/users")
def create_user(
    user: Annotated[
        CreateUser,
        Body(
            openapi_examples={
                "personal": {
                    "summary": "Personal account",
                    "value": {"name": "Alice Nguyen", "email": "alice@example.com"},
                },
                "business": {
                    "summary": "Business account",
                    "value": {"name": "Acme Corp", "email": "billing@acme.com"},
                },
            }
        ),
    ]
):
    return {"name": user.name}

# The user can pick "personal" or "business" from a dropdown
# and Swagger pre-fills the request body with that example

API Versioning

As your API grows you will need to introduce breaking changes without breaking existing clients. The simplest approach is URL versioning: prefix all routes with /v1/ and deploy /v2/ alongside it when you make a breaking change. FastAPI makes this easy with APIRouter prefixes.

python
from fastapi import FastAPI, APIRouter

# v1 router — original shape, keep forever for old clients
v1_router = APIRouter(prefix="/v1/users", tags=["users v1"])

@v1_router.get("")
def list_users_v1():
    # Returns a flat list of names (old format)
    return ["alice", "bob"]

# v2 router — new shape, richer response object
v2_router = APIRouter(prefix="/v2/users", tags=["users v2"])

@v2_router.get("")
def list_users_v2():
    # Returns full objects (new format — breaking change from v1)
    return [
        {"id": 1, "name": "alice", "email": "alice@example.com"},
        {"id": 2, "name": "bob",   "email": "bob@example.com"},
    ]
python
from fastapi import FastAPI

# Option A: single app, both versions in one /docs page
app = FastAPI(title="My API")
app.include_router(v1_router)
app.include_router(v2_router)
# http://localhost:8000/docs  shows both v1 and v2 sections

# -----------------------------------------------

# Option B: separate FastAPI instances, separate /docs pages
v1_app = FastAPI(
    title="My API v1",
    docs_url="/v1/docs",
    openapi_url="/v1/openapi.json",
)
v1_app.include_router(v1_router)

v2_app = FastAPI(
    title="My API v2",
    docs_url="/v2/docs",
    openapi_url="/v2/openapi.json",
)
v2_app.include_router(v2_router)

# Mount both into one ASGI root app (e.g. with Starlette)
from starlette.applications import Starlette
root = Starlette()
root.mount("/v1", v1_app)
root.mount("/v2", v2_app)
# http://localhost:8000/v1/docs  — only v1 routes
# http://localhost:8000/v2/docs  — only v2 routes

Disable Docs in Production

The /docs and /redoc pages are great during development but you may want to disable them in production to reduce the attack surface. Pass docs_url=None and redoc_url=None to the FastAPI constructor. You can read an environment variable to decide at startup whether to enable them.

python
import os
from fastapi import FastAPI

ENV = os.getenv("ENV", "development")

# docs_url=None disables Swagger UI entirely
# redoc_url=None disables the ReDoc UI
# openapi_url=None also hides the raw JSON schema
app = FastAPI(
    docs_url=None if ENV == "production" else "/docs",
    redoc_url=None if ENV == "production" else "/redoc",
    openapi_url=None if ENV == "production" else "/openapi.json",
)

@app.get("/health")
def health():
    return {"status": "ok", "env": ENV}

# In development: /docs and /redoc are accessible
# In production:  /docs returns 404 — docs are invisible
text
# .env.development  — local machine
ENV=development

# .env.production   — VPS / cloud server
ENV=production

# Load with python-dotenv at startup:
# from dotenv import load_dotenv
# load_dotenv(".env.development")  # or pick based on a flag

# Or set directly in your systemd service file:
# [Service]
# Environment="ENV=production"

# Or export in your shell before starting uvicorn:
# export ENV=production
# uvicorn app.main:app --host 0.0.0.0 --port 8000

Generating a Client

Because FastAPI outputs a standard OpenAPI JSON file, tools can generate a typed client library for your frontend automatically. The openapi-ts tool reads /openapi.json and generates TypeScript types and fetch functions. This means your frontend always has the latest types without any manual work.

bash
# Start the FastAPI server first
uvicorn app.main:app --reload --port 8000

# In a second terminal, save the OpenAPI spec to a file
curl http://localhost:8000/openapi.json -o openapi.json

# Verify it looks right
cat openapi.json | python -m json.tool | head -40

# You can also commit openapi.json to your repo so the
# frontend team always has the latest spec, even offline.
# Add a CI step that runs this command and checks for drift.
bash
# Generate a typed TypeScript client from the saved spec
npx @hey-api/openapi-ts \
  -i openapi.json \
  -o src/client \
  -c fetch

# Generated file structure:
# src/client/
#   core/          — base fetch helpers and request options
#   types.gen.ts   — TypeScript interfaces for every schema
#   services.gen.ts — typed functions for every route
#   index.ts       — barrel export

# Example usage in your frontend after generation:
# import { getUser, createUser } from "./client";
# const user = await getUser({ path: { user_id: 1 } });
# Types are inferred automatically — no manual interfaces needed.

What's Next

You now have fully documented routes with descriptions, response schemas, grouped tags, examples, versioning, and the ability to generate a typed client.

OAuth2 in docs: FastAPI supports adding an Authorize button to /docs for testing JWT-protected routes. When you configure an OAuth2PasswordBearer or HTTPBearer scheme on your app, Swagger UI shows a lock icon on each protected route and a global Authorize button. See the Auth guide for the setup.
Postman and Insomnia: Both tools import OpenAPI JSON directly. Export your /openapi.json and import it to get every route pre-configured with the correct method, path, and parameter schema. Any time your API changes, re-export and re-import to keep your Postman collection current.
Custom docs title: Pass title="My API", version="2.0.0", and description="..." to the FastAPI() constructor to customise the header shown in /docs. The description supports Markdown, so you can include links, bold text, and tables in the top-level docs banner.
