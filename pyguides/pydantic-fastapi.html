Data Validation with Pydantic

Define the shape of your data and let FastAPI reject bad inputs automatically. Covers BaseModel, required and optional fields, Field() constraints, nested models, separate request and response schemas, custom validators, and reading the 422 error response.

1

What is Pydantic?

When a FastAPI route receives data from a user, Pydantic checks that it is the right type and shape before your function ever runs. Without validation, a user sending a string where you expect a number causes a crash deep inside your code. Pydantic lets you define a model class that describes exactly what the data should look like, and FastAPI automatically rejects anything that does not match with a clear error message.

python
from fastapi import FastAPI, Request

app = FastAPI()

@app.post("/items")
async def create_item(request: Request):
    body = await request.json()  # raw dict — no validation

    name  = body["name"]         # KeyError if caller forgets this field
    price = body["price"]        # could be a string "abc" — crashes below

    total = price * 1.2           # TypeError: can't multiply str by float
    return {"name": name, "total": total}

# Result: 500 Internal Server Error — the bug is buried inside your function.
# The caller has no idea which field was wrong or what format is expected.
python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    price: float

@app.post("/items")
def create_item(item: Item):
    # FastAPI validates the body BEFORE calling this function.
    # If "price" is "abc", FastAPI returns 422 automatically.
    # Your function only runs when the data is already valid.
    total = item.price * 1.2
    return {"name": item.name, "total": total}

# Bad input: {"name": "Widget", "price": "abc"}
# FastAPI returns: 422 Unprocessable Entity — before your code runs.

Your First Model

A Pydantic model is a class that inherits from BaseModel. Each class attribute is a field. The type annotation on each field tells Pydantic what to expect. FastAPI reads the JSON body of a POST request and fills in the model automatically.

python
from pydantic import BaseModel

class Item(BaseModel):
    name: str       # must be a string — required
    price: float     # must be a number — required
    in_stock: bool   # must be true or false — required

# Pydantic will also coerce compatible types:
# "3.5" (string) → 3.5 (float) if the string looks like a number.
# 1 (int) → True (bool), 0 → False.
python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    price: float
    in_stock: bool

@app.post("/items")
def create_item(item: Item):
    # FastAPI sees "item: Item" and knows to read the JSON request body.
    # It validates the body against the Item model automatically.
    # By the time this line runs, item.name is a str, item.price is a float.
    return {
        "received": item.name,
        "price_with_tax": item.price * 1.2,
        "available": item.in_stock,
    }

# POST body: {"name": "Notebook", "price": 4.99, "in_stock": true}
# Response:  {"received": "Notebook", "price_with_tax": 5.988, "available": true}

Optional Fields and Defaults

A field without a default is required. If the caller leaves it out, FastAPI returns a 422 error before your function runs. A field with a default is optional and uses that value when the caller does not provide it. Setting the default to None means the field is optional and has no value.

python
from pydantic import BaseModel
from typing import Optional

class Product(BaseModel):
    name: str                         # required — caller must include this
    description: Optional[str] = None  # optional — defaults to None if omitted
    quantity: int = 1                  # optional — defaults to 1 if omitted

# Minimum valid body:    {"name": "Pen"}
#   → description = None, quantity = 1

# Full body:             {"name": "Pen", "description": "Blue ink", "quantity": 10}
#   → all three fields filled in

# Missing required field: {}
#   → 422 error, function never runs
json
// POST /products with body: {} — "name" is missing
// FastAPI returns HTTP 422 Unprocessable Entity:

{
  "detail": [
    {
      "loc": ["body", "name"],  // path to the failing field: body → name
      "msg": "Field required",     // plain-English reason
      "type": "missing"           // machine-readable error code
    }
  ]
}

// Your function was never called. The rejection happened in FastAPI's
// request parsing layer before any of your code ran.

Field() — Constraints and Descriptions

Assigning Field() to a field adds validation rules beyond just the type. You can set a minimum length, a maximum value, a human-readable description, and an example value. The description and example appear automatically in the /docs page so the frontend developer can see what to send without reading your code.

python
from pydantic import BaseModel, Field

class Product(BaseModel):
    name: str = Field(
        min_length=2,           # reject strings shorter than 2 characters
        max_length=100,         # reject strings longer than 100 characters
        description="Product display name",
        examples=["Wireless Mouse"],
    )
    price: float = Field(
        ge=0.01,              # ge = greater than or equal — price must be at least 0.01
        le=99999.99,          # le = less than or equal — no astronomically large prices
        description="Price in GBP, excluding tax",
        examples=[29.99],
    )
    quantity: int = Field(
        default=1,             # optional field with a default value
        ge=1,                 # must order at least 1
        le=500,               # can't order more than 500 at once
        description="Units to order (1–500)",
    )

# {"name": "X", "price": 9.99}        → rejected: name too short (min_length=2)
# {"name": "Pen", "price": -1.00}     → rejected: price below ge=0.01
# {"name": "Pen", "price": 1.99}      → accepted: quantity defaults to 1
text
// What you see when you open http://localhost:8001/docs

Product

Nested Models

A Pydantic model can contain another Pydantic model as a field. FastAPI validates the whole structure recursively — if any nested field fails, the whole request is rejected with a clear error pointing to the exact path that failed.

python
from pydantic import BaseModel
from typing import Optional

class Address(BaseModel):
    street: str              # e.g. "12 Oak Lane"
    city: str                # e.g. "Bristol"
    postcode: str            # e.g. "BS1 4AA"

class User(BaseModel):
    name: str
    email: str
    address: Address          # nested model — Pydantic validates this recursively

# If "address.city" is missing, FastAPI returns:
# {"detail": [{"loc": ["body", "address", "city"], "msg": "Field required", ...}]}
# The loc path tells you exactly where inside the nested object the failure was.

from fastapi import FastAPI
app = FastAPI()

@app.post("/users")
def create_user(user: User):
    # user.address is a fully validated Address instance
    return {"name": user.name, "city": user.address.city}
json
// POST /users — valid request body:
{
  "name": "Alice",
  "email": "alice@example.com",
  "address": {           // nested object — matches the Address model
    "street": "12 Oak Lane",
    "city": "Bristol",
    "postcode": "BS1 4AA"
  }
}

// Invalid — "address.city" missing:
{
  "name": "Alice",
  "email": "alice@example.com",
  "address": {
    "street": "12 Oak Lane",
    "postcode": "BS1 4AA"
  }
}

// → 422 with loc: ["body", "address", "city"]

Request Model vs Response Model

The model you use to receive data from the user is often different from the model you return. A signup form receives a password, but you should never return the password in a response. Use a separate model for output and set response_model= on the route decorator. FastAPI filters the response through that model automatically, so fields not in the output model are silently dropped.

python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

# --- Input model: what the caller sends ---
class UserCreate(BaseModel):
    name: str
    email: str
    password: str    # received from the caller, never echoed back

# --- Output model: what the caller receives back ---
class UserOut(BaseModel):
    id: int
    name: str
    email: str
    # no "password" field — FastAPI will strip it from the response

@app.post("/users", response_model=UserOut)
# ↑ FastAPI filters the return value through UserOut before sending it
def create_user(user: UserCreate):
    # Pretend we saved to the DB and got back an ID.
    # Even though we return the password here, FastAPI drops it.
    return {
        "id": 42,
        "name": user.name,
        "email": user.email,
        "password": user.password,  # silently dropped by response_model
    }
json
// Request body sent by the caller:
{
  "name": "Alice",
  "email": "alice@example.com",
  "password": "s3cr3t!"
}

// Response body returned to the caller:
// "password" is completely absent — FastAPI filtered it out via response_model=UserOut
{
  "id": 42,
  "name": "Alice",
  "email": "alice@example.com"
}

// The filtering happens inside FastAPI — you don't need to manually delete
// the password from the dict you return. Anything not in UserOut is dropped.

@field_validator

The @field_validator decorator lets you run a custom Python function after the type check passes. Use it when the built-in Field() constraints are not enough. Raising a ValueError inside the validator automatically returns a 422 error with your message.

python
from pydantic import BaseModel, field_validator

class ContactForm(BaseModel):
    name: str
    email: str

    @field_validator("name")
    @classmethod
    def strip_whitespace(cls, value: str) -> str:
        # Runs after the type check confirms "name" is a string.
        # Strip leading/trailing spaces so "  Alice  " becomes "Alice".
        cleaned = value.strip()
        if not cleaned:
            raise ValueError("name cannot be blank")
        return cleaned  # return the cleaned value — Pydantic stores this

    @field_validator("email")
    @classmethod
    def check_email_format(cls, value: str) -> str:
        # Basic check — a real app would use the email-validator package.
        if "@" not in value:
            raise ValueError("must be a valid email address")
        return value.lower()  # normalise to lowercase while we're here

# {"name": "  Alice  ", "email": "ALICE@EXAMPLE.COM"}
# → name becomes "Alice", email becomes "alice@example.com"

# {"name": "   ", "email": "alice@example.com"}
# → 422: name cannot be blank
python
# When a validator raises ValueError, FastAPI catches it and returns 422.
# The message you write becomes the "msg" in the error response.

@field_validator("email")
@classmethod
def check_email_format(cls, value: str) -> str:
    if "@" not in value:
        raise ValueError("must be a valid email address")
    return value

# POST body: {"name": "Alice", "email": "not-an-email"}
# FastAPI returns HTTP 422:

"""
{
  "detail": [
    {
      "loc": ["body", "email"],
      "msg": "Value error, must be a valid email address",
      "type": "value_error"
    }
  ]
}
"""

Validation Errors

When Pydantic rejects an input, FastAPI returns HTTP 422 with a JSON body describing every field that failed. The loc field is a list showing exactly which field caused the problem. The msg field gives a plain-English description of what went wrong. Knowing this structure helps you write frontend code that displays the right error message to the user.

json
// POST /products with body: {"name": "X", "price": -5, "quantity": 0}
// Three separate validation failures — FastAPI reports ALL of them at once:

{
  "detail": [         // top-level key is always "detail"
    {
      "loc": ["body", "name"],   // ["body"] = came from request body, "name" = field name
      "msg": "String should have at least 2 characters",  // human readable
      "type": "string_too_short",                      // machine-readable code
      "input": "X"                                      // the value that was rejected
    },
    {
      "loc": ["body", "price"],
      "msg": "Input should be greater than or equal to 0.01",
      "type": "greater_than_equal",
      "input": -5
    },
    {
      "loc": ["body", "quantity"],
      "msg": "Input should be greater than or equal to 1",
      "type": "greater_than_equal",
      "input": 0
    }
  ]
}
js
async function submitProduct(data) {
  const res = await fetch("/products", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(data),
  });

  if (res.status === 422) {
    // Pydantic validation failed — read the error detail array
    const error = await res.json();

    error.detail.forEach(function(err) {
      // loc is an array like ["body", "name"] — take the last element
      const fieldName = err.loc[err.loc.length - 1];
      const message   = err.msg;

      // Display the message next to the right input
      const el = document.getElementById("error-" + fieldName);
      if (el) el.textContent = message;
    });

    return;
  }

  if (res.ok) {
    const result = await res.json();
    console.log("Created:", result);
  }
}

What's Next

You now know how to validate data coming into your routes and shape the data going out. The next step is connecting Pydantic models to your database layer so your ORM models and your API schemas stay in sync.

Pydantic + SQLAlchemy
Use separate schema models (Pydantic) and ORM models (SQLAlchemy). Your Pydantic model describes what the API accepts and returns. Your SQLAlchemy model describes the database table. The database guide shows how to wire them together so a route can read a row from the DB and return it through a Pydantic response model in one step.
model_config
Set model_config = ConfigDict(from_attributes=True) on a Pydantic model to build it directly from a SQLAlchemy ORM object. Without this setting, Pydantic only reads plain dicts. With it, you can write UserOut.model_validate(db_user) and Pydantic will pull the values from the ORM object's attributes automatically.
API docs
Every Field() description and example you write appears automatically in the interactive /docs page that FastAPI generates. If you want to customise the page title, add a logo, or organise routes into named groups using tags, see the API Docs guide for the full walkthrough.
