Logging in FastAPI

Print statements are not logs. Covers Python's built-in logging module, log levels, structured JSON logs, request ID middleware, writing to a file, and reading logs in production.

1

Why Not print()?

print() sends text to the terminal with no timestamp, no severity level, and no way to filter it. When your app runs in production you need to know when something happened, how serious it was, and which part of the app it came from. Python's built-in logging module gives you all of this for free without installing anything extra.

text
# Raw terminal output from print() — no metadata at all

user 42 logged in
fetching article https://example.com/article-1
hash mismatch detected
payment received
user 42 logged in
hash mismatch detected

# You have no idea when any of these happened,
# how urgent they are, or which module produced them.
# In production with multiple workers you cannot
# even tell which request triggered which line.
text
# Formatted log lines from Python's logging module

2024-03-15 09:12:04,231  INFO     app.routes.auth        user 42 logged in               pid=18432
2024-03-15 09:12:04,519  INFO     app.services.watcher   fetching https://example.com/1  pid=18432
2024-03-15 09:12:05,102  WARNING  app.services.watcher   hash mismatch detected          pid=18432
2024-03-15 09:12:07,880  INFO     app.services.payments  payment received drop=1000000   pid=18433
2024-03-15 09:12:09,004  INFO     app.routes.auth        user 42 logged in               pid=18434
2024-03-15 09:12:09,441  ERROR    app.services.watcher   hash mismatch detected          pid=18434

# Every line has: timestamp, level, module name, message, process ID.
# You can grep for WARNING, filter by module, or sort by time.

Basic Setup

You create a logger with a name using logging.getLogger(__name__). The __name__ variable automatically uses the module's file name, so each file's logs are labelled by where they came from. You call basicConfig() once at startup to set the minimum level and format string.

python
# app/main.py  — call basicConfig() once at startup
import logging
from fastapi import FastAPI

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s  %(levelname)-8s %(name)-30s %(message)s",
)

# Each module gets its own named logger via __name__.
# __name__ resolves to the module path, e.g. "app.main".
logger = logging.getLogger(__name__)

app = FastAPI()

@app.on_event("startup")
async def startup():
    logger.info("application started")
python
# app/routes/articles.py
import logging
from fastapi import APIRouter, Depends

logger = logging.getLogger(__name__)  # "app.routes.articles"

router = APIRouter()

@router.post("/articles/submit")
async def submit_article(url: str, user_id: int = Depends(get_current_user_id)):
    logger.info("article submitted url=%s user_id=%s", url, user_id)

    if already_registered:
        logger.warning("duplicate submission url=%s user_id=%s", url, user_id)

    try:
        result = await verify_and_anchor(url, user_id)
        logger.info("article anchored tx=%s", result.tx_hash)
        return result
    except Exception as exc:
        logger.error("anchor failed url=%s error=%s", url, exc)
        raise

Log Levels

Every log message has a severity level. The level you set as the minimum filters out everything below it. In production you usually want INFO or WARNING so debug messages do not flood your logs.

text
┌───────────┬───────┬─────────────────────────────────────────────────────┐
│ Level     │ Value │ When to use it                                      │
├───────────┼───────┼─────────────────────────────────────────────────────┤
│ DEBUG     │  10   │ Detailed dev info: loop counts, variable dumps,     │
│           │       │ SQL queries. Disabled in production.                │
├───────────┼───────┼─────────────────────────────────────────────────────┤
│ INFO      │  20   │ Normal events: app started, user logged in,         │
│           │       │ request processed, payment received.                │
├───────────┼───────┼─────────────────────────────────────────────────────┤
│ WARNING   │  30   │ Something unexpected but app is still running:      │
│           │       │ rate limit hit, config value missing (using default)│
├───────────┼───────┼─────────────────────────────────────────────────────┤
│ ERROR     │  40   │ Something failed and needs attention: DB query       │
│           │       │ failed, external API returned 500, task crashed.    │
├───────────┼───────┼─────────────────────────────────────────────────────┤
│ CRITICAL  │  50   │ App may not recover: cannot connect to DB at all,   │
│           │       │ out of disk space, corrupted config on startup.     │
└───────────┴───────┴─────────────────────────────────────────────────────┘

Setting level=INFO means DEBUG messages are silenced.
Setting level=WARNING means both DEBUG and INFO are silenced.
python
import logging

# Set the root logger level — affects all loggers unless overridden.
logging.basicConfig(level=logging.INFO)

# Override the level for a specific named logger.
# This module will show DEBUG messages even if root is INFO.
logging.getLogger("app.services.watcher").setLevel(logging.DEBUG)

# Silence a noisy third-party library.
# uvicorn.access logs every HTTP request — often too verbose.
logging.getLogger("uvicorn.access").setLevel(logging.WARNING)

# Silence SQLAlchemy query echo without disabling your own logs.
logging.getLogger("sqlalchemy.engine").setLevel(logging.WARNING)

# Read level from an environment variable so you can change it
# without redeploying. Defaults to INFO if not set.
import os
log_level = getattr(logging, os.getenv("LOG_LEVEL", "INFO").upper(), logging.INFO)
logging.basicConfig(level=log_level)

Log Format

The format string controls what every log line looks like. Adding the process ID and thread name is useful when you run multiple workers. Adding the file name and line number makes it easy to jump straight to the code that logged the message.

python
import logging

# Format A — minimal: timestamp + level + message
# %(asctime)s   human-readable timestamp (2024-03-15 09:12:04,231)
# %(levelname)s severity label (DEBUG, INFO, WARNING, ERROR, CRITICAL)
# %(message)s   the string passed to logger.info() etc.
FORMAT_A = "%(asctime)s  %(levelname)-8s  %(message)s"

# Format B — standard: adds logger name so you know which module logged it
# %(name)s      logger name, usually the module path e.g. app.routes.auth
FORMAT_B = "%(asctime)s  %(levelname)-8s  %(name)-30s  %(message)s"

# Format C — verbose: adds file name, line number, and process ID
# %(filename)s  source file name (articles.py)
# %(lineno)d    line number inside that file
# %(process)d   OS process ID — essential when running multiple workers
FORMAT_C = (
    "%(asctime)s  %(levelname)-8s  %(name)-30s  "
    "%(filename)s:%(lineno)d  pid=%(process)d  %(message)s"
)

logging.basicConfig(level=logging.INFO, format=FORMAT_B)
text
# The same log call — logger.info("user logged in user_id=42") —
# rendered with each format above.

## Format A (minimal)
2024-03-15 09:12:04,231  INFO      user logged in user_id=42

## Format B (standard — recommended for most apps)
2024-03-15 09:12:04,231  INFO      app.routes.auth                user logged in user_id=42

## Format C (verbose — useful when debugging production issues)
2024-03-15 09:12:04,231  INFO      app.routes.auth                auth.py:87  pid=18432  user logged in user_id=42

# With Format C you can open auth.py line 87 immediately.
# The pid lets you correlate lines from the same worker process.

JSON Logs

Plain text logs are easy to read in a terminal but hard to search in a log aggregator like Datadog, Logtail, or CloudWatch. JSON logs put every field in a named key so the aggregator can filter, sort, and graph your logs without parsing strings.

python
# pip install python-json-logger
import logging
from pythonjsonlogger import jsonlogger

def setup_json_logging():
    logger = logging.getLogger()
    logger.setLevel(logging.INFO)

    handler = logging.StreamHandler()

    # The format string lists the fields to include in every JSON object.
    # %(asctime)s   → "asctime": "2024-03-15 09:12:04,231"
    # %(name)s      → "name": "app.routes.auth"
    # %(levelname)s → "levelname": "INFO"
    # %(message)s   → "message": "user logged in user_id=42"
    formatter = jsonlogger.JsonFormatter(
        "%(asctime)s %(name)s %(levelname)s %(message)s"
    )
    handler.setFormatter(formatter)
    logger.addHandler(handler)

setup_json_logging()

# Extra keyword arguments become top-level JSON keys.
# This is much better than embedding values in the message string.
logger = logging.getLogger(__name__)
logger.info("user logged in", extra={"user_id": 42, "plan": "pro"})
logger.warning("rate limit hit", extra={"user_id": 42, "endpoint": "/articles/submit"})
text
# Each call produces a single JSON object on one line.
# Formatted here for readability — actual output is one line.

{"asctime": "2024-03-15 09:12:04,231", "name": "app.routes.auth", "levelname": "INFO", "message": "user logged in", "user_id": 42, "plan": "pro"}

{"asctime": "2024-03-15 09:12:05,880", "name": "app.routes.articles", "levelname": "WARNING", "message": "rate limit hit", "user_id": 42, "endpoint": "/articles/submit"}

# In a log aggregator you can now:
#   filter WHERE levelname = "ERROR"
#   filter WHERE user_id = 42
#   count GROUP BY endpoint
#   alert WHEN ERROR count > 10 in 5 minutes
# None of this requires regex — the fields are already named.

Request ID Middleware

When multiple requests are being handled at the same time, log lines from different requests get mixed together. A request ID is a unique value generated for each incoming request and added to every log line that request produces. This lets you filter all logs for a single request in one query.

python
# app/middleware/request_id.py
import uuid
from contextvars import ContextVar
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request

# ContextVar is safe for async code — each coroutine gets its own value.
# Without ContextVar a plain global would be overwritten by concurrent requests.
request_id_var: ContextVar[str] = ContextVar("request_id", default="-")

class RequestIDMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        # Honour an upstream request ID if already set (e.g. by a load balancer).
        req_id = request.headers.get("X-Request-ID") or str(uuid.uuid4())
        token = request_id_var.set(req_id)
        try:
            response = await call_next(request)
            # Echo the request ID back so callers can match it to their own logs.
            response.headers["X-Request-ID"] = req_id
            return response
        finally:
            request_id_var.reset(token)

# app/main.py — register the middleware
from fastapi import FastAPI
from app.middleware.request_id import RequestIDMiddleware

app = FastAPI()
app.add_middleware(RequestIDMiddleware)
python
# app/middleware/request_id.py — add a log filter that injects the ID
import logging
from app.middleware.request_id import request_id_var

class RequestIDFilter(logging.Filter):
    """Injects the current request_id into every log record."""
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get("-")
        return True

# app/main.py — attach the filter to the root logger
import logging
from app.middleware.request_id import RequestIDFilter

root_logger = logging.getLogger()
root_logger.addFilter(RequestIDFilter())

# Add %(request_id)s to your format string so it appears in every line.
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s  %(levelname)-8s  %(name)-30s  req=%(request_id)s  %(message)s",
)

# Sample output:
# 2024-03-15 09:12:04,231  INFO      app.routes.auth   req=a3f1c2d9-...  user logged in user_id=42
# 2024-03-15 09:12:04,519  INFO      app.services      req=a3f1c2d9-...  fetching hash
# All lines for one request share the same req= value — easy to grep.

Log to a File

By default logs only go to the terminal. In production you usually want them written to a file too so they survive a terminal session ending. Python's RotatingFileHandler automatically starts a new log file when the current one reaches a size limit, keeping only the last N files to avoid filling the disk.

python
import logging
from logging.handlers import RotatingFileHandler

LOG_FORMAT = "%(asctime)s  %(levelname)-8s  %(name)-30s  %(message)s"

def setup_logging():
    root = logging.getLogger()
    root.setLevel(logging.INFO)

    formatter = logging.Formatter(LOG_FORMAT)

    # Stream handler — logs go to stdout (terminal / systemd journal).
    stream_handler = logging.StreamHandler()
    stream_handler.setFormatter(formatter)

    # Rotating file handler — logs go to a file that rolls over at 5 MB.
    # maxBytes=5*1024*1024 → roll over when file reaches 5 MB
    # backupCount=3         → keep app.log, app.log.1, app.log.2, app.log.3
    #                         then delete the oldest
    file_handler = RotatingFileHandler(
        "/var/log/myapp/app.log",
        maxBytes=5 * 1024 * 1024,
        backupCount=3,
    )
    file_handler.setFormatter(formatter)

    # Attach both — logs appear in the terminal AND the file.
    root.addHandler(stream_handler)
    root.addHandler(file_handler)

setup_logging()
text
# Common log directory on Linux — create it and set permissions.

sudo mkdir -p /var/log/myapp
sudo chown www-data:www-data /var/log/myapp   # or your app's user

# After some time the directory will contain up to 4 files:

/var/log/myapp/
  app.log       ← current file, actively written
  app.log.1     ← previous file (most recent rollover)
  app.log.2     ← one older
  app.log.3     ← oldest kept — next rollover deletes this

# With backupCount=3 and maxBytes=5 MB,
# the maximum disk space used is 4 × 5 MB = 20 MB.
# Adjust both values based on your log volume.

# If you deploy with systemd you can also read logs via:
journalctl -u myapp.service -f

Reading Logs

Once logs are in a file you need to be able to search them. For JSON logs the jq command line tool is the fastest way to filter and extract fields. For plain text logs grep works fine.

bash
# Print every log line (pretty-printed)
jq '.' /var/log/myapp/app.log

# Print only the message field from every line
jq '.message' /var/log/myapp/app.log

# Filter: show only ERROR and CRITICAL lines
jq 'select(.levelname == "ERROR" or .levelname == "CRITICAL")' /var/log/myapp/app.log

# Filter: show all logs for a specific request ID
jq 'select(.request_id == "a3f1c2d9-84b1-4e2a-9f3d-0c1b2e3f4a5b")' /var/log/myapp/app.log

# Filter: show all logs for user_id 42
jq 'select(.user_id == 42)' /var/log/myapp/app.log

# Extract only timestamp and message from ERROR lines
jq 'select(.levelname == "ERROR") | {asctime, message}' /var/log/myapp/app.log

# Count errors per endpoint in the last hour (pipe through sort)
jq -r 'select(.levelname == "ERROR") | .endpoint' /var/log/myapp/app.log \
  | sort | uniq -c | sort -rn
bash
# Find all ERROR lines
grep "ERROR" /var/log/myapp/app.log

# Find lines containing a specific user ID
grep "user_id=42" /var/log/myapp/app.log

# Find all lines from a specific module
grep "app.routes.auth" /var/log/myapp/app.log

# Case-insensitive search for a keyword
grep -i "payment" /var/log/myapp/app.log

# Show context: 2 lines before and after each match
grep -B 2 -A 2 "ERROR" /var/log/myapp/app.log

# Show the last 50 lines of the log file
tail -n 50 /var/log/myapp/app.log

# Follow the log live as new lines are written (Ctrl-C to stop)
tail -f /var/log/myapp/app.log

# Follow live and highlight ERROR lines
tail -f /var/log/myapp/app.log | grep --color=always -E "ERROR|$"

What's Next

You now have structured logs with levels, JSON formatting, request IDs, file rotation, and the tools to search them.

Sentry
For tracking exceptions with full stack traces and alerting, use Sentry. It integrates with FastAPI in a few lines using sentry_sdk.init() and the StarletteIntegration. Sentry groups repeated errors together so you can see how often each unique crash occurs rather than reading thousands of identical log lines.
Log aggregators
Services like Logtail, Datadog, and CloudWatch ingest your JSON log files and give you a searchable UI, dashboards, and alerting. You point them at your log file or pipe stdout to their agent. Because your logs are already JSON, no parsing configuration is needed — every field is immediately queryable.
Audit logs
For compliance you sometimes need an audit log — a separate logger that records who did what and when. Keep it in its own file using a dedicated FileHandler on a logger named "audit", separate from your application logs. Audit log entries should never be deleted by rotation — use a TimedRotatingFileHandler with a long retention period or ship them to immutable storage.
