Hashing Passwords with bcrypt

The first rule of auth: never store what the user typed. Learn why plaintext passwords are catastrophic, what bcrypt does to protect them, and how to build a register + login flow in FastAPI that does it correctly.

1

Why Never Store Plaintext Passwords

If you store password = "hunter2" in your database and your database gets breached — through a SQL injection attack, a leaked backup, a compromised cloud bucket — the attacker now has every user's password in plain text. Because most people reuse passwords, one breach hands them access to your users' email, banking, and everything else. This happens constantly. The solution is to never store the actual password at all.

Real cost of plaintext: The RockYou breach (32 million plaintext passwords), Adobe (153 million, poorly encrypted), LinkedIn (117 million SHA-1 hashes with no salt — cracked in days). Every major breach that became a long-term problem stored passwords incorrectly.
What you store instead: A one-way hash. You can check if a password is correct by hashing it again and comparing. But you cannot reverse the hash to get the original password. Even if the database is stolen, the attacker gets hashes — not passwords.
2

What bcrypt Does

bcrypt is a password hashing algorithm designed in 1999 specifically to be slow. Regular hash functions (SHA-256, MD5) are designed to be fast — a GPU can compute billions per second. bcrypt's slowness makes brute-force attacks impractical: even with a powerful computer, it takes too long to try millions of guesses.

text
Input:   "hunter2"  +  salt  +  cost factor
Output:  "$2b$12$eImiTXuWVxfM37uY4JANjQ..."

SALT
  A random string added to the password before hashing.
  Every user gets a different salt, so two users with the
  same password get different hashes. Prevents "rainbow table"
  attacks (pre-computed hash lookup tables).
  bcrypt stores the salt IN the hash string — you don't manage it.

COST FACTOR (rounds)
  Controls how slow the hash is to compute.
  Default is 12. Each +1 doubles the time.
  12 = ~250ms on a modern CPU. Fast enough for login, slow for attackers.
  Increase over time as hardware gets faster.

ONE-WAY
  You cannot reverse "$2b$12$eImi..." back to "hunter2".
  To verify: hash the input again with the same salt,
  compare the results. bcrypt handles this automatically.
3

Install passlib

passlib is the standard Python library for password hashing. It wraps bcrypt (and other algorithms) with a clean API and handles salting automatically. The [bcrypt] extra installs the bcrypt C library for speed.

bash
pip install passlib[bcrypt]

# Quick test in Python REPL:
from passlib.context import CryptContext
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
hashed = pwd_context.hash("hunter2")
print(hashed)
# $2b$12$eImiTXuWVxfM37uY4JANjQuu... (different every time — the salt changes)
print(pwd_context.verify("hunter2", hashed))   # True
print(pwd_context.verify("wrong",   hashed))   # False
Why not hashlib? Python's built-in hashlib has SHA-256, SHA-512, etc. These are cryptographic hash functions — fine for checksums and signatures, but wrong for passwords. They're too fast (easily bruted) and don't handle salting automatically. Always use bcrypt, scrypt, or Argon2 for passwords.
4

hash_password() Helper

Create a module-level CryptContext once, then wrap it in two simple functions. Centralising this means if you ever change the algorithm, you change it in one place.

python
# auth.py — password helpers (keep separate from routes)
from passlib.context import CryptContext

# schemes=["bcrypt"] → use bcrypt as the algorithm
# deprecated="auto"  → if you add a new scheme later, old hashes auto-upgrade on next login
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(plain: str) -> str:
    """Hash a plaintext password. Returns a bcrypt hash string."""
    return pwd_context.hash(plain)
    # Returns something like: "$2b$12$eImiTXuWVxfM37uY4JANjQ..."
    # The salt is embedded in this string — you don't store it separately
    # Every call returns a DIFFERENT hash even for the same input (different salt)

verify_password() Helper

verify() extracts the salt from the stored hash, re-hashes the input with that salt, and compares. You never handle the salt yourself — passlib manages it. The comparison uses a timing-safe method to prevent timing attacks.

python
def verify_password(plain: str, hashed: str) -> bool:
    """Check that plain matches the stored hash. Returns True/False."""
    return pwd_context.verify(plain, hashed)
    # passlib: extracts salt from hashed, re-hashes plain, compares
    # Uses hmac.compare_digest internally — safe against timing attacks

# Usage:
# stored = hash_password("hunter2")       → store this in DB
# verify_password("hunter2",  stored)     → True
# verify_password("wrong",    stored)     → False
# verify_password("Hunter2",  stored)     → False  (case-sensitive)
Timing attack: A naive hash(input) == stored comparison leaks information — it returns faster when the first characters don't match, letting an attacker narrow down the hash character by character. hmac.compare_digest() always takes the same time regardless of where the strings diverge. passlib uses this automatically.

User Model

The User table stores the email and the bcrypt hash — never the original password. is_active lets you soft-disable an account without deleting it. email_verified is added in the Email Verification guide.

python
from sqlalchemy import Column, Integer, String, Boolean, DateTime
from datetime import datetime, timezone
from database import Base

class User(Base):
    __tablename__ = "users"

    id              = Column(Integer, primary_key=True, index=True)
    email           = Column(String, unique=True, nullable=False, index=True)
    hashed_password = Column(String, nullable=False)
    # NEVER add a "password" column — only hashed_password
    is_active       = Column(Boolean, default=True)
    # is_active=False → account suspended; blocked at login
    created_at      = Column(DateTime, default=lambda: datetime.now(timezone.utc))

Register Route

Three steps: check the email isn't already taken, hash the password, insert the user. Never store the plaintext password even temporarily — hash it immediately and discard the original.

python
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session
from database import engine, get_db, Base
import models
from auth import hash_password, verify_password

app = FastAPI()
Base.metadata.create_all(bind=engine)

@app.post("/register", status_code=201)
def register(email: str, password: str, db: Session = Depends(get_db)):
    # 1. Check email not already registered
    existing = db.query(models.User).filter(models.User.email == email).first()
    if existing:
        raise HTTPException(status_code=400, detail="Email already registered")

    # 2. Hash the password immediately — never store the plaintext
    user = models.User(
        email=email,
        hashed_password=hash_password(password),  # hash here, not later
    )

    # 3. Save to database
    db.add(user)
    db.commit()
    db.refresh(user)

    # Return the user without the hash — never expose hashed_password in responses
    return {"id": user.id, "email": user.email, "created_at": user.created_at}
Never return hashed_password in a response. The hash is one-way but it's still a secret. If you ever accidentally log or expose it, it can be used in a pass-the-hash attack. Keep it out of all API responses and logs.

Login Route

Login fetches the user by email, verifies the password against the stored hash, checks the account is active, and returns success. In the next guide (JWT), login returns a token instead of just a message.

python
@app.post("/login")
def login(email: str, password: str, db: Session = Depends(get_db)):
    # 1. Find the user
    user = db.query(models.User).filter(models.User.email == email).first()

    # 2. Verify password (also handles "user not found" case)
    if not user or not verify_password(password, user.hashed_password):
        # Same error for wrong email OR wrong password — don't reveal which
        raise HTTPException(
            status_code=401,
            detail="Invalid email or password",
            headers={"WWW-Authenticate": "Bearer"},
        )

    # 3. Check account is active
    if not user.is_active:
        raise HTTPException(status_code=403, detail="Account suspended")

    # For now: return a plain success message
    # In auth-jwt.html: return {"access_token": ..., "token_type": "bearer"}
    return {"message": "Login successful", "user_id": user.id}
text — why the same error message
If login returns "Email not found" for unknown emails and
"Wrong password" for known emails, an attacker can use it
to enumerate valid email addresses in your system.

They send 10,000 emails from a breach list:
- "Email not found" → not registered here
- "Wrong password"  → registered! Now they know to target this one.

Always return the SAME error for both cases:
  "Invalid email or password"

This gives the attacker no information about which part was wrong.
The user experience is slightly worse — but security wins here.
